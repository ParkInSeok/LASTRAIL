<a id="scope"></a>
## 1. 목표와 바꾸지 않는 규칙

**운영자는 기존 Admin에서 점검을 설정하고, 서버가 접근·거래를 제어하며, 앱/홈페이지는 같은 공개 상태를 표시한다.** 별도 운영 사이트·CMS·고객문의 도구를 만들지 않는다. 개발·통합·실기기·내부테스트·점검 리허설은 DEV 하나에서 수행한다. 향후 공개 데모의 PROD는 별도이며 DEV 데이터를 일반 공개하지 않는다.

점검은 Notice type=MAINTENANCE 게시, adsEnabled=false, 데이터 배포/롤백, 인증 만료와 서로 다르다. 공지를 게시한 것만으로 게임을 닫지 않으며, 점검 해제는 광고 ON·새 밸런스 자동 적용·약관 동의를 뜻하지 않는다.

기존 게임 진입 owner와 서버 admission을 확장한다. 같은 일을 판정하는 경쟁하는 두 번째 로그인/점검 승인 서비스를 만들지 않는다. 공개 상태는 표시를 위한 것이며 게임 진입/쓰기를 승인하는 근거는 기존 서버 gate다.

점검 화면은 실제 상황을 설명해야 한다. 모든 503/통신오류를 '정기 점검'이라고 추측하지 않고, 확인된 점검·갑작스러운 장애·상태 조회 실패를 구분한다. 예정 종료 시각은 예측이며 도달만으로 자동 입장시키지 않는다.

<a id="service-policy"></a>
## 2. 서비스별 점검 범위 — 권장 설계

전역 bool 하나로 앱·웹·관리도구·callback을 모두 차단하지 않는다. 하나의 MaintenancePlan에서 대상과 동작을 명시하고, 서버가 실효 상태를 산출한다. Admin에는 다음 사전 구성을 제공하되 적용할 실제 기능을 미리 보여준다.

| 상황 | 실효 gameMode | 실효 webMode | 사용자 안내 |
|---|---|---|---|
| 정상 | NORMAL | NORMAL | 정상 서비스 |
| 게임 사전 차단 | DRAINING | NORMAL | 새 작전 불가, 기존 승인 작전 마무리 안내 |
| 게임 본점검 | MAINTENANCE | NORMAL | 앱 점검 화면, 웹은 상단 게임 점검 배너와 정상 공개 콘텐츠 |
| 커뮤니티/웹 쓰기 점검 | NORMAL 또는 기존 값 | READ_ONLY | 공개 자료 열람, 실제 중단된 글·댓글·문의 제출 등 잠금 |
| 웹 전체 점검 | NORMAL 또는 기존 값 | MAINTENANCE | 일반 웹 페이지를 정적 안내로 대체; 게임은 독립 판정 |
| 게임·웹 동시 점검 | MAINTENANCE | MAINTENANCE | 앱·웹 각각의 안내, 독립 상태 읽기와 가능한 공지 유지 |

웹 점검이 게임까지 닫거나 게임 점검이 위키까지 닫히는 것은 명시 대상으로 선택했을 때뿐이다. 단, 인증·DB·스토리지 등 공유 의존성이 중단되면 실제 영향을 미리 계산하고 사용 불가능한 기능을 정상이라고 표시하지 않는다.

문의, 공지 읽기, 상태 읽기, 지급 원결과 조회, 공급자 callback, Admin 접근은 요청 종류별로 분리한다. 허용이라고 정한 경로도 저장소/인증이 실제로 동작해야 한다. 접근 허용과 접수 성공은 다르다.

웹 READ_ONLY에서 신규 일반 사용자 쓰기는 서버에서 차단한다. 게임이 정상인 조합이라면 게임 정산까지 웹 읽기 전용 필터로 막지 않는다. 공급자 callback·운영 명령은 공개 웹 게시글 쓰기와 같은 분류로 처리하지 않는다.

<a id="admin-maintenance"></a>
## 3. Admin 데이터·상태·운영 명령

### 3.1 논리 데이터

실제 DTO/endpoint 이름은 기존 서버 계약을 읽고 매핑한다. 아래 표는 새 논리 모델이지 현재 API 필드의 존재를 주장하는 것이 아니다.

| 필드 | 의미 |
|---|---|
| maintenanceId / policyRevision | 점검 ID와 대상 문맥의 단조 증가 정책 개정 |
| environment / applicationId / serviceScope | 현재 DEV, 향후 PROD의 적용 대상. 내부 상태 공개 금지 |
| planState | DRAFT / SCHEDULED / ACTIVE / COMPLETED / CANCELLED |
| effectiveGameMode / effectiveWebMode | §2의 현재 동작. 공개 상태의 표시값과 서버 gate가 같은 원정책을 참조 |
| title / summary / noticeId | 안전한 공개 제목·요약과 선택적인 공식 Notice 연결 |
| drainStartsAt / startsAt | 신규 출격 사전 차단 시각과 본점검 시작 시각. 서버 시간 기준 |
| estimatedEndAt | 표시용 종료 예정 시각, 미정이면 null. 자동 해제 조건 아님 |
| completedAt / cancelledAt | 관리자가 실제 해제/취소한 확정 시각 |
| existingRunPolicy | 기본 DRAIN_THEN_PRESERVE 또는 명시 EMERGENCY_PRESERVE. 세부는 §4 |
| effectiveCapabilities | 문의·로그인·조회 등 실제 허용 상태. 클라이언트 입력으로 결정하지 않음 |
| publishedAt / updatedAt / serverTime / validUntil | 공개 상태의 신선도·판정 시점과 다음 검증 기한 |
| retryAfterSeconds | 재조회 최소 대기 제안. 종료 보장 시각과 별개 |
| actor / reason / expectedRevision / idempotencyKey | 운영 권한·경합 방지·감사·원요청 결과, 공개 응답에서는 제외 |

시간은 UTC 저장, Admin 기본 편집·한국어 표시에는 Asia/Seoul과 시각 기준을 명시한다. 일정에 날짜가 없거나 시각만 있어 사용자가 다른 날짜로 해석하게 두지 않는다.

### 3.2 수명과 전환

`DRAFT → SCHEDULED → ACTIVE → COMPLETED`, 예약 취소는 CANCELLED다. 예정된 drainStartsAt부터 DRAINING, startsAt부터 MAINTENANCE를 서버 시간으로 평가한다. 게임을 대상으로 하지 않은 계획은 게임 상태를 바꾸지 않는다. 수동 즉시 시작도 동일 정책 개정·감사·서버 검증을 거친다.

서버가 startsAt에 도달했는지 요청 시에도 검사하므로 예약 실행 worker가 늦었다고 새 작전을 통과시키지 않는다. 상태 snapshot에 예정 전환 시각을 함께 담더라도 이 값은 클라이언트의 입장 권한이 아니다. 공개 문구 반영 지연과 실제 차단 효력 시점은 구분한다.

**종료 예정 시각이 지나도 Admin이 실제 해제하기 전까지 점검 상태를 유지**한다. 지연 시 '종료 시간 재안내 예정'과 마지막 확인 시각을 표시한다. 연장·조기 종료는 새 revision으로 기록하고 캐시를 갱신한다. 별도 점검 해제 없이 공지를 삭제/만료시켜 차단을 풀지 않는다.

같은 환경·서비스 범위의 겹치는 계획은 초기 버전에서 게시를 거절한다. 게임과 웹처럼 겹치지 않는 계획은 병존할 수 있지만 실제 제어 대상의 교집합을 검증한다. 이를 통해 상태 우선순위를 임의로 덮어쓰지 않는다.

### 3.3 관리자 작업

기존 Admin에 예약/즉시 시작/사전 차단/연장/취소/종료/표시 미리보기/적용 상태 확인을 추가한다. 환경·영향 기능·진행 작전 수·미확정 거래·공개 링크 준비 상태를 변경 전에 표시한다.

변경에는 역할별 권한, expectedRevision, 사유, 동일 요청 키를 요구하고 정책·감사·원결과를 원자 기록한다. 이후 공개 snapshot 배포는 outbox 등 복구 가능한 전달로 관리하고 '저장됨'과 '모든 표면에 반영됨'을 같은 성공으로 표시하지 않는다. 소비자별 revision/오류를 Admin에서 확인한다.

실제 점검 gate를 바꾸는 명령과 설명 공지를 편집하는 명령을 구분한다. UI에서 함께 수행할 수 있어도 중간 실패를 표시하고 복구한다. Admin 자체를 일반 사용자용 점검 middleware로 막아 점검 해제도 못 하는 구성을 피한다. 운영 인증·권한은 그대로 강제하고 공개 우회 bool은 두지 않는다. 의존 인프라 전체가 중단되면 Admin도 항상 동작한다고 보장하지 않으며, 사전 공개 snapshot을 유지하고 인프라 복구 후 Admin에서 정상화한다.

<a id="recovery"></a>
## 4. 진행 중 작전·거래 보호 — 권장 기본안

### 4.1 계획 점검

**사전 신규 출격 차단 → 기존 승인 작전 마무리 허용 → 본점검에서 미완료 작전 보존**을 기본 흐름으로 제안한다. 사전 차단 시간/완료 유예 길이는 임의 수치를 넣지 않고 실제 작전 길이와 운영 준비에 맞춰 설정한다.

DRAINING은 로그인·로비 안내/조회가 가능한 상태로 두되 새 작전 START·신규 광고 시작·새 결제 시작을 막는 안이다. 사전 차단 전에 서버가 승인한 run은 필요한 노드/선택/장비/종료 정산을 원래 버전으로 이어갈 수 있어야 한다. 모든 POST를 막아 기존 작전이 증강 선택에서 멈추게 하지 않는다. 새로 만든 클라이언트 시각이 아니라 서버의 최초 승인과 cutoff를 대조한다.

START와 차단 전환이 경합하면 서버의 동일 승인 경계에서 순서를 확정한다. 차단 이후의 신규 시작은 run/입장비용/시작보급을 생성하지 않는 확정 거절이고, 차단 전에 접수된 동일 요청은 원결과를 재현한다. 응답 유실은 확정 거절의 증거가 아니다.

### 4.2 본점검·긴급 점검

신규 로그인/게임 진입은 점검 화면으로 차단하고, 기존 세션의 실제 쓰기 허용은 별도로 검사한다. 클라이언트가 본점검을 확인하면 중앙 SimulationClock의 별도 점검 hold를 사용해 다음 안전한 tick 경계에서 전투·주행·게임플레이 타이머를 정지하고 복구 가능한 상태를 저장하는 안이다. 즉시 전환이 필요한 긴급 점검은 사전 drain 없이 이 보존 흐름으로 진입한다.

점검의 적용을 아직 관측하지 못한 클라이언트가 정확히 같은 순간에 멈춘다고 약속하지 않는다. 서버는 매 승인/쓰기에서 현재 gate를 확인하고, 클라이언트는 부트·복귀·로비·노드 전환과 제한된 상태 확인 경로에서 갱신한다. 전투의 매 공격마다 상태 API를 호출하지 않는다.

기존 원문이 증명하는 것은 일부 로컬 rail checkpoint 및 시작/종료 저널이다. **모든 적·HP·투사체·효과·난수의 강제 종료 후 복원이 이미 구현됐다는 의미가 아니다.** 본점검 중단을 제품에 연결하기 전에 전체 전투 checkpoint와 멱등 결과 복구를 검증해야 한다. 미지원 상태에서 복구 성공을 표시하거나 긴급 정지의 안전성을 확정하지 않는다.

| 당시 상태 | 동작 |
|---|---|
| 시작 전 | 새 작전 차단. 비용/보상 소모 없음 |
| 로컬 전투 중 | 안전 경계 정지·검증된 checkpoint 저장. 저장 확인 전 씬 파괴 금지 |
| 저장 실패 | 실제 실패·재시도·앱 종료 시 위험 안내. '안전하게 저장됨' 문구 금지 |
| 노드 보상/증강/합성 승인 대기 | 원키·본문·기회·버전 보존. 새 요청/재추첨/임의 소모 취소 금지 |
| 종료/보상은 접수됐지만 응답 유실 | 원결과 조회. 점검 때문에 새 지급 거래 생성 금지 |
| 작전/조회 저장소 중단 | 가능한 로컬 메타데이터 보존, 서비스 회복 후 원계약대로 확인 |
| 이미 확정된 지급 | 유지. 점검/롤백은 회수·재지급 사유 아님 |

점검이 [04 §6](04_COMBAT_RUN.md#discard)의 **복구 불가 구형 형식에 대한 작전 폐기 예외를 발동시키지는 않는다.** 계정/토큰/보상 저널/정상 cache도 삭제하지 않는다. 저장 성공은 실제 저장소 응답을 확인해 표시하고, 동기화 대기와 로컬 저장 완료를 구분한다.

### 4.3 정산·callback·기한

원결과 조회·유효 거래 복구는 저장소가 정상인 범위에서 기존 권한·기한을 유지하며 제공한다. DB 쓰기를 중지했다면 완료 보장을 하지 않고 원증빙을 보존한다. 공급자 callback은 일반 게임 로그인/웹 게시 차단과 분리하되, 서명·거래 소유·원기한 검증을 생략하지 않는다.

callback을 즉시 처리할 수 없으면 사전 검증한 내구성 수신 경로로 접수한 경우에만 성공 수신 응답을 보낼 수 있다. 그 경로도 불능이면 공급자와 합의한 실패/재전달 계약을 따르며, 유실시키고 200으로 성공 처리하지 않는다. 새 대체 지급이나 새로운 SSV 기한 연장을 추정하지 않는다.

오래된 저장 작전의 수명·만료 정리는 [04 §12](04_COMBAT_RUN.md#run-expiry)의 **확정된 J11 정책**을 참조한다. 서버가 확인한 게임 중단만 보정하고, 광고/구매/정산 기한은 직접 바꾸지 않는다. 기본 수명 72시간·복구 후 최소 24시간 재개 기회·원인별 입장 비용 반환은 2026-09-21 사용자 승인 사항이다. 조사 보관은 [15](15_LOG_RETENTION.md#retention-matrix)의 승인된 정책을 따르며, 이 문서는 별도 보관 숫자를 중복 정의하지 않는다. 실제 계약 확인/구현과 원거래 처리 확인 전 고객에게 보정·환급 완료를 표시하지 않는다.

### 4.4 정상 복귀

관리자 해제와 최신 서버 admission 확인 후 기존 인증·콘텐츠·밸런스 검증을 다시 수행한다. 기존 작전은 시작 당시 balanceVersion/content/프리셋을 유지하고, 미확정 동작은 원결과를 확인한다. 점검 종료만으로 자동 POST·무료 재추첨·보상 재수령을 하지 않는다.

점검 hold 해제는 다른 hold를 지우지 않는다. 증강 선택·사용자 일시정지·백그라운드 정지가 남아 있다면 전투는 계속 정지한다. 벽시계로 흘러간 점검 시간을 게임플레이 시뮬레이션에 한꺼번에 따라잡기로 적용하지 않는다. 점검 상태는 일반 Notice 읽음과도 분리한다.

## 5. 클라이언트 점검 화면 기획

### 5.1 준비 위치와 표시 우선순위

점검 기본 화면·필수 글꼴·버튼·로고의 최소 자산·연결 실패 문구는 **설치된 앱의 로컬 bootstrap 의존성**에 둔다. 인증 성공, 원격 Main/공지 이미지/Addressables 다운로드, 위키 API 조회가 선행 조건이어서는 안 된다. 원격 이미지는 선택 장식이며 실패해도 읽을 수 있게 한다.

기존 원문의 초기 loading/login/error/update 로컬 예외를 확장하는 신규 요구다. 기존 maintenance retry 테스트가 전체 점검 UI·실기기 복구까지 완료했다는 뜻은 아니다. 기존 PlayerEntry/ResourceBootstrap 소유자를 그대로 사용한다.

일반 공지는 안전한 로비 이후지만, 게임 진입을 막는 점검 화면은 로그인 전 표시가 가능하다. 진행 중에는 기존 UI 위에 보호 안내를 표시하고 §4의 보존 결과에 따라 전환한다. 계정/화면 generation을 확인해 뒤늦은 응답이 정상 화면을 다시 가리거나 다른 계정에 반영되지 않게 한다.

### 5.2 기본 세로 화면

| 위치 | 내용 |
|---|---|
| 상단 | LAST RAIL 로고·환경 표시(DEV에서만 내부 표시) |
| 주 제목 | '서비스 점검 중입니다' 또는 실제 장애/미확인 상태에 맞는 문구 |
| 요약 | 점검 사유·영향 기능. 서버 내부 오류나 비공개 운영 메모 제외 |
| 일정 | 시작 시각, 종료 예정 시각 또는 '종료 시간 미정', 시간대 명시 |
| 갱신 상태 | 마지막 상태 확인 시각, 지연 여부 |
| 작전 안내 | 실제로 확인된 로컬 저장/동기화 대기/저장 실패를 구분한 상태별 문구 |
| 기본 동작 | '상태 다시 확인' — 단일 진행·서버 retry-after/재시도 제한 준수 |
| 보조 동작 | '점검 안내 보기' — 승인된 상태/공지 URL, 실패해도 기본 문구 유지 |
| 이탈 동작 | '타이틀로' 등 안전한 경로. 기록 삭제/강제 로그아웃 아님 |

**예시 문구(실제 일정/저장 성공을 주장하는 값 아님):**

> 서비스 점검 중입니다.
> 점검 내용: [공개 요약]
> 점검 시작: [서버 시각과 시간대]
> 종료 예정: [예정 시각 / 미정]
> [저장 상태가 확인된 경우에만 작전 보관 안내]
> [상태 다시 확인] [점검 안내 보기]

DRAINING은 전면 차단 화면 대신 로비/전투 배너로 '새 작전 시작 제한, 기존 작전은 안내된 범위에서 마무리 가능'을 보여준다. 점검 종료 예상 카운트다운이 0이 되어도 정상 입장으로 바꾸지 않는다. 진행률 데이터가 없으면 가짜 %/무한 다운로드 spinner를 쓰지 않는다.

### 5.3 오류·캐시·접근성

신뢰 가능한 점검 payload가 없고 통신만 실패하면 '서버에 연결할 수 없습니다'로 표시한다. 마지막 검증된 점검 정보가 있으면 '마지막 확인 정보'로 구분하고, 만료된 정상 snapshot만으로 입장을 허용하지 않는다. 일반 HTML 503, 잘못된 JSON, 다른 환경 응답도 앱이 안전하게 처리해야 한다.

재확인은 안전한 상태 GET만 자동화 후보로 두고, 기본은 명시 버튼·서버 지연 준수다. 자동 조회를 넣는다면 제한된 간격·jitter·동시요청 1개·백그라운드 중단을 구현 계약에 명시한다. 인증/작전/문의 POST를 상태 재확인에 함께 재실행하지 않는다.

기본 720×1280 비율, safe area, 360×640·360×480 같은 작은 표면, 긴 한글/영문, 글자 확대, 키보드/스크린리더를 검증한다. 상태는 색만으로 구분하지 않으며 버튼이 화면 밖으로 밀리지 않게 한다. 문구가 길면 본문 내부를 스크롤하고 필수 버튼은 접근 가능하게 유지한다. 고대비·단순 2D 전술 톤을 사용하되 새 원화/시안 이미지를 이 문서에서 생성한 것은 아니다.

## 6. 홈페이지 점검 화면 기획

### 6.1 게임 점검만 하는 경우

홈페이지 자체가 정상이라면 위키·확률·공지·정책을 닫지 않는다. 전체 페이지 상단에 게임 상태 배너를 두고 점검 상세로 연결한다. 커뮤니티/문의도 실제 의존성이 정상인 경우에만 유지한다. '게임 점검 = 홈페이지 전체 폐쇄'를 기본으로 삼지 않는다.

배너 예: **'게임 점검 중 · 종료 예정 [시각/미정] · 자세히 보기'**. 일반 페이지 본문과 URL은 유지하고 각 표면에서 같은 maintenanceId/revision을 사용한다.

### 6.2 웹 읽기 전용

공개된 정적 정보는 그대로 제공하고 실제 중단된 글·댓글·문의 작성에는 사용 불가 이유를 표시한다. 서버도 동일 쓰기를 차단한다. 클릭 가능한 폼으로 받은 내용을 저장하지 못했는데 '접수 완료'로 안내하지 않는다. 서버에 확정된 기존 문의/게시 기록은 보존한다.

### 6.3 홈페이지 전체 점검

동적 앱·API·DB가 없어도 열리는 **가벼운 정적 HTML 점검 본문과 최소 CSS/이미지**를 웹 배포 산출물에 함께 준비한다. API가 실행되어야 SPA가 그리는 오류 화면 하나만 두는 것으로 끝내지 않는다. 게임 운영 데이터의 공개 승인은 여전히 필요하다.

| 위치 | 내용 |
|---|---|
| 상단 | LAST RAIL 로고/공식 사이트 표식 |
| 주 제목 | '홈페이지 점검 중입니다' |
| 상태 카드 | 게임 상태와 홈페이지 상태를 분리 표시 |
| 본문 | 공개 사유, 시작/예정 종료, 마지막 갱신 시각 |
| 동작 | '상태 새로고침', '점검 공지'. 실제 이용 가능한 링크만 제공 |
| 하단 | 유지 가능한 정책/문의 안내. 실제 미등록 연락처 생성 금지 |

임시 차단한 기존 URL은 `503 Service Unavailable`과 가능한 `Retry-After`를 반환하는 안이다. 모든 URL을 영구 redirect하거나 200 성공으로 같은 점검 문구에 바꾸지 않는다. 별도의 정상 상태 설명 자원 `/status`가 실제 독립적으로 서비스되면 그 URL의 정상 응답은 200일 수 있다. 게임 API의 정상 상태 조회 또한 읽기 성공이면 200이되 본문의 게임 가용성은 MAINTENANCE일 수 있다. 이것이 차단된 사용자 작업의 성공을 뜻하지 않는다.

일시 점검을 noindex/404/410로 처리하지 않는다. 장기 폐쇄는 임시 503을 무기한 유지하는 것이 아니라 별도 운영·검색 정책으로 검토한다. robots.txt는 일반 페이지 점검 치환에 묶지 않고 실제 정책을 정상 제공한다. 기술 근거는 §10의 IETF/Google 문서이며 실제 HTTP 설정 검증은 후속이다.

### 6.4 상태 안내의 의존성 분리

Admin/서버가 만든 공개용 MaintenanceStatus를 불변 파일과 현재 index로 발행해, 가능한 한 게임 API·DB와 다른 제공 경로에서 읽게 한다. 별도 운영 CMS를 만드는 것이 아니라 같은 Admin 원문의 읽기 전용 복제본이다. DNS/CDN 등 공유 인프라까지 모두 중단돼도 항상 조회 가능하다고 보장하지 않는다.

public snapshot에는 공개 일정·사유·revision·갱신/유효시각·서비스 상태만 포함한다. 운영 우회 계정·내부 메모·비밀키·미공개 DEV 경로는 포함하지 않는다. DEV 상태는 승인된 DEV 접근 경계 안에서 검증하고, 향후 PROD 공개 상태가 DEV 정보를 직접 읽지 않게 한다.

공개 상태가 지연되면 마지막 갱신 시각과 stale 상태를 표시한다. 서버 gate보다 오래된 NORMAL이 접속 권한이 되지 않으며, 클라이언트의 로컬 clock만으로 끝난 점검으로 판단하지 않는다. stale 응답·동시 점검 전환을 고려한 TTL/재검증/캐시 purge를 정하고, 점검 해제 뒤 캐시된 503이 장기간 남지 않는지 검사한다.

## 7. 논리 API·미들웨어 책임

| 연산 | 대상과 책임 |
|---|---|
| PreviewMaintenance | Admin에서 대상·시각·영향 기능·진행 run·복구 가용성·앱/웹 화면 검수 |
| Save/Schedule/ActivateMaintenance | 기존 Admin 권한, expectedRevision, 사유·키·감사·서버 시간 검증 |
| Extend/Complete/CancelMaintenance | 동일 권한·경합 검증. 완료는 명시 해제이며 예약 종료시각의 자동 추측 아님 |
| ReadServiceStatus | 인증 전 가능한 최소 공개 상태 읽기. 환경/표면별 공개 범위·rate limit·신뢰 출처 |
| ExistingClientAdmission | 최신 점검 gate를 기존 앱 승인에 매핑. 새 경쟁 owner 금지 |
| ExistingGameWrites | 신규 START와 기존 run/거래의 유효 복구를 분리해 검사 |
| ExistingPublicWebWrites | READ_ONLY/MAINTENANCE에서 일반 신규 쓰기 차단 |
| PublishStatusProjection | 같은 Admin 정책에서 공개 최소 snapshot을 발행, 실패/지연은 운영 화면에 표시 |

503는 일반적으로 과부하와 예정 점검 모두에 쓰일 수 있으므로, 가능하면 기계 판독 가능한 서비스 상태와 maintenanceId/revision을 반환한다. 클라이언트는 503 숫자만 보고 원인·종료시각을 만들어내지 않는다. JSON이 아닌 edge 응답도 안전한 통신 실패 화면으로 처리한다.

점검 gate를 알지 못하는 구형 앱에는 기존 지원 가능한 admission 차단과 기본 오류 표시를 유지한다. 새 UI/상태를 요구하는 빌드는 빌드 지원 계약에서 검증한다. 전역 조작 bool만으로 구형 앱에 새 점검 화면 코드가 생기지 않는다.

상태별 공개 응답·점검 원문·서버 쓰기 gate는 같은 policyRevision을 참조하지만 네트워크 전달을 하나의 원자적 트랜잭션이라고 주장하지 않는다. 상태가 불일치할 때는 게임 쓰기 권한을 서버가 최종 판단하고 화면은 신선도·재시도를 제공한다.

## 8. 필수 인수 시나리오 — 아직 실행하지 않은 요구사항

| 시나리오 | 검증할 결과 |
|---|---|
| STG 정리 | 현행 부트/배포/환경 입력에서 STG 미사용. 과거 문서·fixture·임시 staging 파일을 무작정 삭제하지 않음 |
| 신규 설치 중 점검 | 로그인·원격 Main·공지 이미지 없이 로컬 안내 표시 |
| 게임만 점검 | 게임 진입 차단, 실제 정상인 위키/확률/공지 읽기 유지 |
| 웹만 점검 | 해당 웹 기능 차단, 정상 게임까지 임의 차단하지 않음 |
| 전체 DB/API 중단 | 정적 안내/마지막 상태 가능 여부 확인, 실패 시 거짓 정상·접수 성공 없음 |
| START와 drain 경합 | 비용/작전 1회 또는 확정 0차감 거절, 기존 원키 결과 일관성 |
| 기존 작전 중 강제 중단 | checkpoint 저장 확인·실패 구분, 선택/효과/난수/타이머 복구 검증 |
| 합성/리롤/보상 응답 유실 | 원키·버전·원결과 유지, 재추첨/복제/삭제 없음 |
