# LAST RAIL | 조사 로그·증빙 보관 및 파기 정책

외부 조사일: **2026-09-21**. 운영 정책 승인일: **2026-09-21**. 상태: **사용자의 “ㄱㄱ”에 따라 유형별 보관·아카이브·조사 보류 정책 승인 / 실제 개인정보 적용 범위·기산점 검토 및 구현·배포 전**. 이 문서는 공개 자료의 사실과 LAST RAIL이 채택한 운영 정책을 구분한다. 사용자의 정책 승인은 법률 적합성 인증이나 실제 서버 적용을 뜻하지 않으며, 업계 공통 표준이라고 주장하지 않는다.

## 1. 재개 수명과 조사 보관을 구분

[04 저장 작전 만료](04_COMBAT_RUN.md#run-expiry)의 72시간은 2026-09-21 별도 사용자 승인으로 확정된 재개 가능 기간이다. 게임 중단 보정·원인별 비용 처리의 전문도 04에서 관리한다. 플레이어가 만료 작전을 재개할 수 없게 하는 것과, 서버가 부정이용/고객문의/지급오류 조사를 위해 증거를 보관하는 것은 별개다.

**종전의 종결 후7일 체크포인트 정리안은 폐기한다.** 마지막 상태와 핵심 행위는 아래 승인된 유형별 기간으로 분리 보관한다. 조사용 아카이브가 있다고 만료 작전의 재개 권한이 생기거나 복구를 보장하지 않는다. 로그만으로 전투의 완전한 결정적 재현이 가능하다고 가정하지 않는다.

공개 개인정보처리방침으로 회사의 모든 디버그 로그·DB 백업·프레임 데이터의 실제 TTL을 파악할 수는 없다. 따라서 아래14/90/180일·1년 등은 업계 평균이 아니라 LAST RAIL이 이번에 채택한 운영 기간이다.

개인정보처리시스템에 접속하는 운영자 등의 기록(정보주체 제외)은2026-07-01 시행 안전성 확보조치 기준 제8조에서 기본1년 이상,5만명 이상 개인정보 처리·고유식별정보/민감정보 등 해당 조건에서는2년 이상을 요구한다[S4]. 이는 일반 이용자의 게임 접속·전투 기록에 일괄 적용하는2년 의무가 아니다.

개인정보 보호법 제21조는 목적 달성/보유기간 경과 등으로 불필요해진 개인정보의 파기와, 다른 법률 때문에 보존하는 자료의 분리보관을 규정한다[S5]. 회사 운영에 필요한 기간·법정 보존 대상·개인정보 삭제요청을 함께 검토한다. 단순 hash 처리 또는 계정ID 대체는 자동으로 익명정보가 되지 않는다.

## 3. LAST RAIL 보관기간 — 운영 정책 승인

**총 보관기간은 빠른 조회 기간을 포함한다.** 예를 들어30일+180일=210일이 아니라,처음30일은 빠른 조회·나머지150일은 아카이브다. 달/년은 달력 기준 기간이며90일/365일과 임의 치환하지 않는다.

소비자 분쟁3년·거래5년은 해당 법정기록의 보존 문제다. 이번에 승인한 작전요약3년과 핵심행위1년은 운영판단이며 법정 의무로 주장하지 않는다. 실제 서비스 출시 전 처리방침의 목적·항목·기간 및 위탁/접근권한과 일치시켜야 한다.

DEV에는 우선 합성 테스트계정/자료를 사용한다. 실제 내부테스터 정보가 포함되면 DEV라는 이유로 개인정보 규칙을 면제하지 않는다. 실제 사용자/거래 데이터는 DEV와 PROD 사이에 복사하지 않으며,검증 산출물도 개인정보없는 코드/설정/통계와 사용자 로그를 구분한다.

## 4. 조사에 필요한 최소 핵심 이벤트

하나의 사건을 `환경·경제범위·runId·accountId·nodeId·operationId`로 연결한다. 서버 시각,실제 앱 versionCode,밸런스/콘텐츠/서버빌드ID,노드/웨이브 식별,행위 종류,원요청 digest/키,처리 revision,검증결과를 기록한다.

장비는 원재료ID/성급/카테고리/태그/고유효과/시술계수,소모 후 결과ID와 결과값,추첨정책 버전·적격 풀 식별·실제 확정결과를 남긴다. 미리보기는 난수를 소비하지 않으며 실제 확정거래만 증거가 된다. 마나/에너지 스킬은 실제 비용·전후 잔량·쿨타임·실행 성공을,쿨타임형은 자원 없는 상태를 그대로 기록한다.

보상/비용은 해당 원장 transactionId에 연결하고,로그가 지급권한을 대신하지 않는다. 반복 실행 가능한 원시 토큰·비밀번호·인증코드·Authorization·전체 구매토큰·문의 본문은 로그에 넣지 않는다. 문의 본문은 권한있는 고객문의 저장소에만 보관하고 로그에는 ticketId만 둔다. 기존 현재세션 enum 진단 producer를 무단 raw-stack 업로더로 확장하지 않는다.

## 5. 저장·아카이브·파기

빠른 조회 영역에는 목록/인덱스와 최근 상세를 두고,오래된 상세는 접근 제한된 오브젝트 아카이브에 압축해 둔다. 이전 완료·읽기 복구·체크섬·보유기한 메타데이터를 검증한 후 hot 사본을 정리한다. 비용절감을 이유로 아직 아카이브하지 않은 원본을 먼저 삭제하지 않는다.

Admin은 최근검색·오래된자료복원요청·조사case연결·보존기한·삭제보류를 한 화면에서 다룬다. 복원한 임시 사본은 원래 기한을 연장하지 않으며 조회를 마친 뒤 정리한다. 별도 홈페이지 백오피스를 만들지 않는다.

만료한 run은 읽기전용 종결요약으로 남는다. 로그/스냅샷이 보관돼도 live run으로 다시 주입하거나 재지급하지 않는다. 180일 뒤 checkpoint가 없어도 1년 핵심행위·3년 최소요약으로 조사할 수 있지만,전체 재현이 항상 가능하다는 뜻은 아니다.

## 6. 조사 보존 보류(hold)

미해결 고객분쟁·수사요청·보안사건이 실제 존재하면 운영자가 **사건ID·대상범위·사유·권한·설정자·재검토기한**을 남기고 관련 기록만 삭제 보류한다. 삭제 보류의 재검토 주기는30일이다. 모든 계정의 전체 로그를 이유없이 무기한 보류하지 않는다.

조사종결 뒤 원래 기한을 다시0부터 세지 않는다. 원래 보존기간이 지났고 다른 적법한 근거가 없으면 파기한다. 불만/분쟁의 법정 기록으로 필요한 최소 증거는 별도 case 자료로 이관하고 그 목적에 맞게 관리한다. 계정삭제 요청에서도 법적 보존 자료는 제한된 목적의 별도 저장으로 분리한다.

미완료 정산·소유권·중복지급 방지 tombstone은 일반 로그 TTL로 삭제하지 않는다. 유효 영구 광고 스킵의 권리 상태는 거래 증빙5년과 다른 수명이다. 기한이 지난 원요청 ID가 조회되지 않는다고 새로운 보상을 생성하지 않도록 폐쇄된 대상/원거래를 판정하는 경계를 유지한다. 수명 종료와 파기 설계는 실제 영수증/상품 계약과 함께 검증한다.

## 7. 개인정보와 운영 통제

보존기간을 길게 잡는 대신 최소필드·필요목적·운영자권한·암호화·조회/다운로드감사·삭제명세가 필요하다. 일반UI 숨김이나 DB soft-delete만으로 개인정보 파기완료를 표시하지 않는다. 인덱스·오브젝트·임시조회사본·백업에 삭제를 전파하고 백업복원 뒤에도 삭제가 되돌아오지 않게 한다.

불변 보존을 설정할 때 적법한 최소기간과 범위를 정한다. 개인정보를 근거없이 영구 immutable로 잠그는 안은 아니다. Admin 조회/변경 기록에는 열람한 정보주체·수행업무·시각·접속정보를 담되 비밀번호나 문의본문은 다시 복제하지 않는다.

Suspicious Players/Review Queue와 자동증거수집은 가능하지만 **Permanent Ban은 기존Admin에서 권한있는 운영자가 직접 검토해 수동으로만 실행**한다. 보존기간 연장이 자동 제재 허용을 의미하지 않는다.

## 8. 검증·출시 경계

보관기간 계산(월/년/윤년),동시 만료·정산·hold,아카이브 이동 실패,조회 복원,권한 없는 export,탈퇴/삭제요청의 파기전파,backup복원 후 삭제명세 재적용,이미 삭제된 영수증의 재지급 차단을 검증한다. 체크리스트는 테스트 결과가 아니다.

보관 기간과 정책은 사용자 승인을 받았다. 이번 산출물은 그 승인을 문서·작성용 데이터에 반영한 것이며 서버 storage lifecycle·DB migration·실사용자 데이터 이동/삭제·개인정보 적합성 인증을 수행하지 않았다. 실제 출시·활성화 전에는 처리방침·법정 기록별 범위/기산점·접근권한·아카이브/파기 구현 검증을 완료해야 한다. 72시간 재개 수명·장애 시간 보정·비용 반환은 이후 별도 사용자 지시로 승인되었으며 [04 §12](04_COMBAT_RUN.md#run-expiry)를 따른다. 이 승인은 본 문서의 보관기간이나 개인정보·법정 기록 검토 범위를 변경하지 않는다.

### 8.1 서버·Admin 연결 계약

아래 명칭은 책임을 구분하는 설계명이며 기존 API 경로나 구현 완료 주장이 아니다. 운영 화면은 기존 Admin만 사용한다.

| 작업 | 필수 계약 |
|---|---|
| 증거 검색·읽기 | 운영자 권한·환경·사건 범위 검사, 접근 목적과 열람 감사. 실제 존재하는 자료와 이미 파기된 자료를 구분한다. |
| 오래된 증거 복원 | 아카이브 객체·해시·보유기한을 검증하고 제한된 임시 사본으로 읽는다. 원래 보유기한·작전 재개권한·보상 권한을 변경하지 않는다. |

### 3. 최소 데이터·범위
서버 인증에서 계정을 확정하고 환경은 배포 설정/원권위로 기록한다. 클라가 전송한 환경/계정 문자열을 권위로 쓰지 않는다. 이벤트에는 고정 분류·허용된 기능 단계·빌드/앱·플랫폼 버전·발생 시각/서버 수신 시각·발생 횟수·필요 최소 상관관계를 사용한다. 계약이 제공하지 않는 필드는 확장 검증 후 사용한다.
미확인/미수집을 0으로 넣지 않는다. 장비명/채팅/문의 본문/원응답/토큰/쿠키/원구매자료·사용자 로컬 전체경로는 제외. 디버그 복사용 진단 전문은 자동 업로드 payload가 아니다. raw stack이 필요한 특정 조사에는 기존 별도 승인·선별 수집 절차를 적용한다.
계정·환경·세대가 확인된 때 수집한 이벤트만 그 계정 경로로 전달한다. 로그인 전 로컬 전역 큐를 나중에 로그인한 계정에 귀속시켜 업로드하지 않는다. 계정 변경 시 이전 전송 작업을 격리하고 원계정 보관·복구 계약 없는 이벤트는 새 계정으로 이동시키지 않는다.

### 4. 반복·전송·오프라인
원오류가 발생한 자리에서는 최소 고정 데이터만 기록한다. threaded callback에서 Unity 객체 접근/네트워크/디스크 저장을 직접 하지 않는다. 전송 owner가 메인 스레드 또는 해당 계약에 맞는 안전한 실행 경계에서 비동기 전송한다.
같은 오류/빌드/기능 단계/귀속 범위의 짧은 반복은 첫·마지막 시각과 횟수로 집계하고 서로 다른 원거래의 핵심 실패를 무조건 합치지 않는다. 초기 구현은 기존 상한을 초과하지 않는다: 서버1~25events, 현재 전송 pending25, 로컬 전역 큐100/64KiB/7일·분당60은 각각 다른 계층의 현행 값이며 하나의 업로드 보장으로 해석하지 않는다. 로컬 전역 큐의 자동 전송은 이번안에도 포함하지 않는다.
연결 복구/기존 안전한 flush 시점에 제한된 배치로 전달하고 매프레임 전송/무한 즉시 재시도 금지. timeout/5xx는 원키·동일 본문을 보존한 제한 재시도/결과 확인,429는 기존 서버 대기 지시와 backoff,401은 기존 인증 복구 후 원계정 일치 확인. 확정 형식 거절은 같은 잘못된 payload를 무한 재전송하지 않는다. 실제 지연/횟수는 기존 client 제한을 조사한 뒤 계약으로 확정하며 이번 문서로 새 임의 값을 발행하지 않는다.
중요 경제 명령의 journal을 진단 큐가 밀어내지 않는다. 서버 수신 불명 상태에서 새키로 같은 이벤트를 중복 생성하지 않는다. 영수증 확인 후 제거 실패가 새 재전송 원인이 되지 않게 기존 receipt 경로를 유지한다.
오프라인 내구 보관을 확장하려면 원계정/환경·최소 정제 payload·동일 키/버전·상한을 먼저 맞춘다. 현재 receipt 메타만 있는 범위를 원본문 재전송 가능하다고 주장하지 않는다. 보관 불가/가득 참이면 안전한 진단 누락 계수를 남기되 플레이·보상 복구를 막지 않는다.

### 5. 오류 보고 실패와 종료
로그 업로드 오류가 다시 같은 로그 업로더를 호출하는 재귀를 막는다. 업로드 실패를 사용자 전면 팝업으로 반복 표시하거나 전투/보상 진행을 기다리게 하지 않는다. 원기능이 실패한 경우 그 기능에 필요한 사용자 안내는 유지한다.
앱 백그라운드/종료 시 최소 로컬 보관을 시도할 수 있지만 종료 지연/전송 성공을 보장하지 않는다. OS 강제 종료·OOM·네이티브 crash는 관리 callback으로 포착되지 않을 수 있다. 다음 실행의 불완전 종료 흔적은 '비정상 종료 가능성'이며 실제 crash 확정 로그가 아니다. 별도 native crash 수집은 현재 미지원/미검증 범위로 명시한다.

### 6. 운영 조회·보존
기존 ops 오류 조회 경로에서 환경·빌드·고정 코드·기능 단계·기간·발생 수/영향 계정을 연결한다. 새로운 자동 경보·알림 전송은 별도 운영 기준 없이 만들지 않는다. 중요 거래 진실은 원장/receipt, 오류 기록은 조사 보조다.
15의 오류·크래시 요약30일 빠른조회/총90일, 선택 상세 디버그14일, 핵심 행위/종결/거래별 기존 수명을 그대로 적용한다. 진단 큐7일과 서버 보존90일은 다른 범위다. 개인 정보 없는 합성 자료로 dev/prd 설정·권한 분리를 검증하며 실제 사용자 로그를 dev에 복사하지 않는다.

### 7. 검수·담당·완료 경계
Server: 기존 ingest의 version/고정 필드/정제·상한/멱등/인증·환경/receipt 검증. Unity: 기능별 producer·안전 수집·귀속/중복/수명·부하·실제 Player 전송. Admin: 검증 공급된 필드의 기존 조회 소비만. Plan: 보고 대상·제외·상태/수용 기준.
필수 사례는 준비/저장/필수자산 실패, 같은 오류 폭주, 다른 원거래 분리, 오프라인→복귀, 서버 수신후ACK유실,429/401/5xx/형식오류, 로그 전송 자체 실패, 계정교체·환경전환, 큐 포화·디스크 실패, 앱 실제 종료/재시작이다. 원게임 상태/보상 불변·민감값 미전송·중복 수신 방지·일반 화면 기술정보 미노출·무한 재귀/프레임 정지/메모리 증가 없음이 기준이다.
합성 오류를 실제 PRD 구성 Player→격리 서버로 보내 DB/원receipt까지 연결 검증하고, 실제 PRD 수신 여부는 배포 승인/환경에서 따로 확인한다. 단위/fixture 합격을 PRD 동작 완료로 보고하지 않는다. 전체 오류 coverage와 native crash 미지원은 별도 명시한다.
이번은 신규 상세 제안. 제품 코드·큐 등록·실제 로그 전송/PRD 배포는 수행하지 않았다.

## 운영자 오류 조회·묶음·처리 상세안 — 2026-10-19 / 신규 제안
목적: 들어온 오류의 영향과 원거래를 파악하고 조사/수정/검증을 구별한다. 기존 Admin ErrorLogsPage/opsErrorLogContract 및49 ops-error-logs 계약을 재사용한다. 확인된 현재 계약은 목록/요약/상세 GET과 OPS_ERROR_LOG_READ 권한이며 처리 상태 변경 API는 해당 원문에 미구현으로 명시돼 있다. status 필드 존재를 변경 기능 완료로 해석하지 않는다.

1. 목록: 기존 환경/기간·severity/status·고정 errorCode·앱/서버버전·서비스 필터 유지. 오류 묶음에는 첫/최근 발생·집계 기간·발생 횟수와 수집 상태 표시. 미수집/조회 실패는 오류0으로 표시하지 않는다. Admin의 기술 정보는 업무상 필요하므로 게임 사용자 UI 제한을 그대로 적용하지 않는다.
2. 묶음: 환경+서비스/코드+기능 단계+빌드/계약 버전의 검증된 조합을 기본 후보로 삼고 원메시지 문자열 유사도만으로 묶지 않는다. 다른 환경은 분리, 버전 간 비교는 별도 필터. 원이벤트는 보존하고 묶음은 조회 투영이다. 한 페이지의 항목 수를 전체 발생 수로 표현하지 않는다. 서버 occurrenceCount 집계와 이벤트 개수·영향 계정 수를 별도 표시하며 미공급 계정 집계는 추정하지 않는다.
3. 상세: 정제된 오류 요약→시간순 관련 상태→연결 원거래/receipt→조사 메모 순서. 원장/계정 조회는 각 권한을 재검사한다. 로그 읽기 권한만으로 결제/개인정보 전문을 열지 않는다. 개발 복사와 동일한 최소 정제 기준의 조사 요약 복사를 제공하되 고객 정보는 업무상 필요한 범위만 허용한다.
4. 상태 제안: 새 오류→조사 중→수정 검증 중→해결. 기존 OPEN/ACKNOWLEDGED 등 실제 저장 enum과 매핑을 Server가 확정하며 단순 UI 이름 변경으로 새 상태를 구현하지 않는다. 해결에는 수정 빌드/근거/검증 결과가 필요하고 로그가 잠시 안 들어온 것만으로 자동 해결하지 않는다. 대상 수정 버전에서 재발하면 기존 사건에 재발 표식과 신규 발생을 연결, 옛 버전 재발은 수정 실패와 구분한다. 자동 영구 무시/자동 삭제는 추가하지 않는다.
5. 상태 변경: 별도 권한·사유·예상 버전·담당/시각·전후 상태 감사가 필요. READ 권한을 WRITE로 자동 확대하지 않는다. 명령 응답에 최종 상태/버전을 포함하고 성공 직후 중복 GET 없이 소유 Model 갱신. 동시 담당 변경은 충돌/최신값을 반환하며 덮어쓰기 금지. 정확 API/권한 매핑은 신규 승인 후 Server가 공급한다. 오류 해결은 보상 재지급/원장 수정/환불 동작이 아니다.
6. 조회 재사용: 같은 환경/필터/페이지의 유효 목록과 상세를 메모리로 재사용, 뒤로가기 자체는 재조회 사유 아님. 운영자 명시 새로고침/조건 변경/권한 변경·실무효화에만 조회. 화면에 집계 기준 시각·필터를 표시하고 상시 폴링/자동 알림 발송은 이번 범위에서 추가하지 않는다. 페이지/필터 버퍼는 제한하고 오래된 응답이 새 환경 화면을 덮지 않는다.
7. 검수: dev/prd 격리·권한 회수·마스킹·미수집vs0·집계/페이지 일치·다른 원거래/버전 묶음·동시 상태 변경·재발·늦은 응답·감사 보존·복사 검증. 원로그 보존15 기간과 조사 상태 수명을 구분하고 해결됐다는 이유로 원영수증을 삭제하지 않는다. 서버 검증 계약→Admin 소비→실화면/권한/수용 검증 순서. 신규 제안으로 실행큐·상태 변경 API·운영 처리/알림 미실행.

## 오류 수정 재검증·재발 판정 상세 — 2026-10-19 / 신규 제안
<a id="ops-error-fix-verification-proposal-20261019"></a>
목적: 앞 승인안의 '수정 검증 중→해결'을 증거로 판단한다. 신규 별도 오류 관리 시스템을 만들지 않고 기존 사건 상세/QA 링크·상태 변경 계약을 사용한다. 아래 수용 기준과 표시 연결이 제안이며 운영 배포/자동 경보 승인은 아니다.

### 1. 해결 범위의 고정
사건별로 원오류 코드/기능 단계·환경, 최초 확인 빌드/플랫폼, 재현 조건·기대/실제 결과, 수정 대상 버전과 영향 범위를 남긴다. 계정/원거래는 권한 있는 최소 참조만 사용한다. 재현되지 않은 현상은 '원인 미확인'으로 남기고 코드 변경만으로 해결 처리하지 않는다.
클라이언트 버전만 비교하지 않는다. 앱/서버/콘텐츠·계약 중 원인에 실제 영향을 준 버전 조합을 기록한다. 버전 문자열 사전순으로 수정 포함 여부를 판단하지 않고 검증된 빌드/릴리스 매핑을 사용한다.

### 2. 검증 단계
원재현 근거 → 수정 범위 확인 → 같은 조건 재시험 → 관련 실패/복구·회귀 확인 → 지원 범위 해결 판정.
최소 근거: 원증상 로그 또는 재현 기록, 수정 빌드/변경 식별, 재현 입력과 기대값, 실제 검증 결과, 미검수 환경. 모든 오류에 인위적인 자동 RED 시험을 의무화하지 않으며 실제 확보한 근거를 구분한다.
예: 수령 응답 유실이라면 정상 수령만 확인하지 않고 서버 commit후ACK유실/원키 재생·중복지급0·이미수령 표시/로컬 저장 실패까지 해당 수정 경계를 확인한다. 기기종속 오류는 해당 플랫폼/기기에서 재검증하고 Editor 통과를 모바일 전체 해결로 확대하지 않는다.

### 3. 코드 검증과 운영 적용 구별
'수정 검증 중'에는 검증 통과 여부와 운영 적용 여부를 별도 표시한다. 격리 시험 통과는 '시험 환경 검증 완료', 미배포는 '운영 미적용'으로 유지하며 PRD 해결로 표시하지 않는다.
'해결'은 대상 환경/지원 버전에 수정이 실제 적용된 근거와 필요한 회귀 검증이 있을 때 권한 있는 담당자가 명시 변경한다. 배포가 필요 없는 설정 원인이면 실제 적용된 설정 버전/근거를 사용한다. 실제 사용자 트래픽이 없다는 이유로 해결을 영구 보류하지는 않되, 운영 자연발생 재관찰 여부는 '미관찰'로 별도 표시한다.
오류0건은 수집 정상 여부·분모/기간이 없으면 개선률 근거가 아니다. 수집 비활성/누락/서버 지연은 '관찰 불충분'. 미지원 전체 크래시 수집을 정상으로 간주하지 않는다. 근거 없는 24/72시간 무발생 자동 해결 기준을 도입하지 않는다.

### 4. 재발 분류
수정이 포함된 검증 대상 버전에서 동일 조건/서명 오류 발생 → 재발 후보로 표시하고 담당자가 원인 일치 확인 후 '조사 중'으로 되돌린다. 상태 변경 감사에 이전 해결 근거와 재발 이벤트를 보존한다.
옛 미수정 버전의 뒤늦은 업로드는 '구버전 발생'으로 분리한다. 서버 수신 시각과 클라 발생 시각을 모두 사용하되 클라시각 단독으로 확정하지 않는다. 버전/시간이 불명확하면 재발 여부 미확인. 같은 코드지만 다른 원인이라면 관련 신규 사건으로 분리하고 원사건을 임의 재해결하지 않는다.
동일 해결 사건에 조사 메모·상태 변경이 경합하면 예상버전 검사, 실패한 변경을 성공 표시하지 않는다. 자동 재실행/보상/환불과 연결하지 않는다.

### 5. 조사 화면과 데이터
상세에 '영향 범위 / 수정 대상 / 검증 근거 / 적용 환경 / 남은 제한'을 짧게 표시하고 원QA/변경 링크로 연결한다. 기검증된 목록·상세의 데이터 재사용, 변경 성공 응답으로 상태/감사 버전 갱신. 증거 파일 전문을 오류 기록에 중복 저장하지 않는다. 링크 권한/존재를 확인하고 접근 불가를 검증 완료로 표시하지 않는다.
임의 링크를 자동 실행/다운로드하지 않는다. 권한 있는 원근거 조회만 제공한다. 조사 요약 복사에도 해당 범위와 '시험 통과/운영 미적용/재관찰 미확인' 구분을 포함한다.

### 6. 수용 기준·후속
정상 해결/미배포/관찰부족/구버전 지연/수정버전 재발/버전 미확인/다른원인·권한회수/동시 변경 사례를 검증한다. 전체 해결률을 페이지 내 사건 수로 계산하지 않는다. 상태 변경은 로그·원장 TTL을 늘리거나 원증거를 삭제하지 않는다.
Server는 버전/상태·감사·동시성 계약, Admin은 기존 상세의 근거/표시·입력, 실제 수정 담당은 재현/회귀 QA를 소유한다. 기존 승인 조사 기능과 중복 구현하지 않고 신규 상세 승인 후 실제 계약 공급 단위에 결속한다. 현재 문서 저장만, 실행큐/운영 상태 변경/알림 없음.
