# LAST RAIL | 문의·현재 세션 진단·영수증 복구

> 현행 대조: 2026-09-21. 이 세션의 최신 사용자 결정이 우선한다. 기존 구현 증거는 해당 원문의 시점/범위로 유지하며, 판단 대기는 [00](00_INDEX.md#open-decisions)에서 관리한다.


범위: 문의 UI/제출·서버 원본·Admin 처리 경계, 현재 프로세스 오류 producer, 문의·오류의 재시작 receipt 조회. 작전 BodyJson 저장과는 다른 계약이며 [04](04_COMBAT_RUN.md)를 침범하지 않는다. 검증은 [문서 안내](00_INDEX.md#qa)에 모았다.

## 1. 문의 제출

인증된 호출자 소유자가 문의 화면을 연다. 첫 제출 시 category·content·설치 build·작성/제출 시각·idempotency key를 고정한다. 클라이언트의 문의 본문과 draft는 프로세스 메모리에서만 보관하고 디스크 저널에는 저장하지 않는다. 서버가 정상 접수한 문의 본문은 서버의 Support 데이터로 저장하여 권한 있는 Admin에서 조회한다. 로컬 본문 영속화 금지는 서버 문의 저장 금지가 아니다. 계정 변경은 늦은 응답을 차단하며 draft를 다른 계정에 넘기지 않는다.

확정 ticket ID 없이는 성공으로 표시하지 않는다. 동일 프로세스의 불확실 전송은 원본문·원키 재시도 또는 receipt 조회로 확인한다. NOT_FOUND/404는 불확실 상태이지 거절·취소·새 키 POST 허가가 아니다. 확정 거절 뒤 수정 흐름과 불확실한 요청을 분리한다.

패널은 category·여러 줄 본문·개인정보 주의·전송/닫기·cooldown·조회 동작을 제공한다. 닫았다고 불확실 상태를 없애지 않는다. 익명 route, 첨부, raw log, 실제 이메일 발송 약속은 추가하지 않는다. 초기 계획의 HTTP 미연결은 후속 실제 local HTTP 검증으로 보완됐으므로 별도 현행 장애로 되살리지 않는다. [R09](00_INDEX.md#r09) [R10](00_INDEX.md#r10)

## 2. 현재 세션 진단

CurrentSessionErrorRuntime가 현재 프로세스의 bounded queue와 client를 소유한다. profile/story 준비 오류는 원래 generation 확인 뒤 enum으로 기록하고, 인증 실패는 이 producer에서 제외한다. raw text/stack 입력이나 전역 로그 listener를 추가하지 않는다.

요청은 body·key를 고정해 명시 재시도한다. 동시 flush는 하나의 작업으로 합치며 오래된 계정/세대 요청은 HTTP 없이 제거한다. 지원 문의와 같은 build snapshot capture를 사용한다. 이전 프로세스의 무소유 crash queue·영속 error 기록을 현재 세션 POST로 가져오거나 재귀속하지 않는다. [R10](00_INDEX.md#r10)

## 3. 영속 receipt 저널

| 항목 | 규칙 |
|---|---|
| 저장 위치 | 앱 private의 별도 원자적 암호화 receipt 파일. 인증 payload slot을 읽거나 덮거나 지우지 않는다. native crypto를 사용하되 receipt domain prefix로 구분한다. |
| 저장 데이터 | 원계정·원키·kind/category·build·작성/제출 시각의 immutable metadata만 저장한다. |
| 금지 데이터 | 문의 본문/draft·오류 text/stack·event HTTP body·토큰은 저장하지 않는다. |
| 순서 | metadata 저장 성공 뒤 POST한다. 같은 key의 metadata 변경을 거부한다. |
| 재시작 | 현재 계정의 원키 receipt GET만 복원한다. 본문이 없는 문의는 POST/편집 재제출할 수 없고, 옛 오류를 현재 event POST queue에 넣지 않는다. |
| 조회 결과 | FOUND면 metadata 제거가 가능하다. 실패/404는 held 유지. 임의 TTL·자동 새 키·서버 purge 보장을 만들지 않는다. |
| 용량·손상 | 기록 한도 64개. receipt 파일 제한 524288 bytes. full/corrupt/unavailable을 빈 저장소로 처리하지 않는다. |

동일 계정 refresh의 새 Bearer는 가능하지만 타계정 기록을 조회하지 않는다. 교체된 소유자는 이전 lookup을 기다린 뒤 자기 범위로 조회하며 늦은 결과가 새 소유자에 전달되지 않는다. 장치 기본 구성에 암호화가 없으면 실패를 드러내고, fake crypto는 제품 fallback이 아니다. [R11](00_INDEX.md#r11) [R12](00_INDEX.md#r12) [R14](00_INDEX.md#r14)

## 4. 복구 화면과 사용자 선택

날짜가 있는 held 기록, receipt 조회, 새로고침, 명시적으로 별개인 새 문의, 별도 확인 후 로컬 metadata 삭제를 제공한다. 미해결 기록 하나가 계정의 모든 문의를 막지 않도록 새 문의는 빈 본문으로 시작한다. 기존 불확실 문의를 새 키로 재전송하는 기능은 아니다.

용량이 찼을 때도 기록 선택/삭제와 미전송 독립 draft를 보존한다. 삭제는 서버 취소·거절이 아니며 이 기기의 조회 단서를 잃는다는 안내를 한다. 선택·닫기/재열기·새 문의 전환에도 서버 cooldown을 유지한다. 손상은 retry/close로 표시하고 조용히 초기화하지 않는다. [R12](00_INDEX.md#r12)

## 5. 홈페이지·커뮤니티 문의 경계 — U7

[11](11_WEBSITE_COMMUNITY.md#community)의 공개 건의/공략과 계정·결제·보안·원로그가 포함되는 비공개 문의를 분리한다. 공개 글에서 ticket/body/계정 정보를 자동 추출해 공개 상태로 옮기지 않는다. 웹 제출을 기존 support owner에 연결할 때에도 원요청·계정 결속·영수증 확인의 실제 계약을 보존한다.

홈페이지 FAQ·알려진 문제·계정 삭제 요청은 신규 설계다. 새 웹 인증 adapter·삭제/보존 정책이 구현됐다고 보지 않으며 기존 메타데이터-only receipt 저널에 공지 본문·게시글·개인정보를 추가하지 않는다. 개인정보·권리신고·공개 제보의 세부 정책은 [11](11_WEBSITE_COMMUNITY.md)에 한 번만 둔다.

## 6. 앱·홈페이지 접수와 Admin 처리 — U8

이전 [support API](49_SERVER_API_CONTRACTS.md#source-b678a199237246c2)의 reply/assign/close 미제공은 당시 구현 경계다. 아래 답변·처리 상태 요구는 서버 명령과 본인 공개 조회 계약으로 연결해야 한다. 기존 SUPPORT_READ의 읽기 권한을 답변·담당변경·내부메모·재화 지급 권한으로 확대하지 않는다. repair preview/approve/execute 후보를 이미 존재하는 endpoint로 표시하지 않는다. 기존 문의/진단의 필드·길이·요청 제한·원키 receipt·권한별 상세 DTO는 원문 전문을 보존한다.

운영 책임은 [10 §0](10_LIVEOPS_NOTICES.md#admin-operations)을 따른다. 기존 Support 서버 데이터와 Game/Admin API를 재사용한다. 웹 전용 문의 DB·운영 페이지나 외부 고객센터 서비스를 별도 전제로 추가하지 않는다.

**앱/홈페이지 접수 → 서버 검증·문의 저장 → 접수 ID 반환 → 기존 Admin 목록/상세 조회 → 운영자 답변·상태 변경 → 서버 저장 → 본인에게 공개한 결과 조회**로 연결한다. 사용자 접수 화면과 운영 처리 화면은 별개이며 모두 같은 문의 원본을 참조한다.

| 경계 | 필요한 계약 |
|---|---|
| 접수 | 인증된 소유자·환경에 결속한다. 분류·본문·기존 작성/제출 시각·키·제공 가능한 빌드 정보는 기존 계약을 유지한다. 웹 접수라는 이유로 임의 Android versionCode를 만들지 않는다. 웹 출처 필드는 기존 DTO와 합의한 확장으로만 추가한다. |
| 서버 원본 | 접수 본문/원요청 identity와 후속 처리 상태·사용자용 답변·Admin 내부 메모를 논리적으로 구분한다. 답변 작성이 접수 본문이나 원키를 덮어쓰지 않는다. 새 물리 테이블/경로는 기존 계약 확인 전 확정하지 않는다. |
| Admin 처리 | 목록·상세·분류/기간/버전/계정 검색을 재사용한다. 답변·상태·담당/메모는 기존 기능 확인 후 필요한 것만 확장하며, 역할·대상 환경·변경 이력·중복 요청을 서버에서 검사한다. |
| 사용자 결과 | 자기 문의의 접수·공개 답변·허용된 처리 상태만 조회한다. 전체 문의 목록·타계정 상세·내부 메모는 노출하지 않는다. 기존 receipt FOUND는 접수 확인이지 답변 완료가 아니다. |
| 전달 방식 | 기본안은 앱/웹의 본인 문의 조회다. 이메일·푸시 발송은 별도 승인/구현 없이 약속하지 않는다. |

상태 코드나 답변 API는 원문에서 확인된 것으로 가장하지 않는다. 문의 제출/receipt 조회 계약과 고객응대 상태/답변 계약을 별도로 확인하고 호환되게 확장한다. 공개 커뮤니티 건의와 비공개 문의를 자동 변환하지 않고, 로컬 receipt 삭제도 서버 문의 취소·삭제로 취급하지 않는다.

[R10](00_INDEX.md#r10)은 실제 로컬 Hono/sql.js에서 문의 저장과 Admin 목록·상세 조회를, [R12](00_INDEX.md#r12)는 원문의 단일 저장·원키 receipt 복구를 보고했다. 웹 접수·운영 답변·본인 답변 조회·원격 운영까지 완료했다는 증거는 아니며 이번 갱신도 문서 편집만 수행했다.


## 7. U9 점검 중 고객문의·접수 복구

문의 접수 가능 여부는 게임 점검과 독립적으로 [12](12_SERVICE_MAINTENANCE.md#service-policy)의 실제 서버 가용성을 반영한다. 게임만 점검하며 문의 저장이 정상이라면 기존 인증된 앱/웹→서버→Admin 경로를 유지한다. 인증/저장소도 중단됐다면 제출을 비활성화하고 이유를 표시한다.

폼을 열거나 임시로 입력했다는 이유로 접수 번호·성공 메시지를 만들지 않는다. 이미 접수 여부가 불명확한 문의는 원 receipt/key 규칙을 보존하며 문의 본문을 새로 디스크에 적재하는 오프라인 큐를 임의 추가하지 않는다. 운영자가 실제로 등록하지 않은 연락처·외부 서비스를 임의 대안으로 제시하지 않는다.

## 문의 답변 작성 폼 v1 — 2026-10-01 / 작성 초안

사용자 요청에 따라 기존 Admin 문의 상세에서 사용할 답변 폼·템플릿을 준비했다. 실제 화면/서버 변경·발송 없음. 신규 폼 운용은 검토용 초안이며 확인한 서버 동작과 구분한다.

### 확인한 실제 계약
Server apps/admin-api/src/support-processing-routes.ts 및 packages/common/src/support-ticket-service.ts를 읽었다. GET/POST /v1/admin/support/tickets/:ticketId/processing, 별도 처리 권한, expectedRevision 및 Idempotency-Key, OPEN/IN_REVIEW/CLOSED, publicReply/internalNote 각각 trim 후1~2000자(선택 필드) 지원. CLOSED→다른 상태는 거절한다. 고객 DTO는 최신 비어 있지 않은 공개 답변을 조회하며 운영 이력과 내부 메모는 별도다. 이는 소스 확인이며 실서버 호출 검증 결과가 아니다.

### 폼 구성
| 영역 | 항목·동작 |
|---|---|
| 읽기 전용 문의 요약 | 문의ID·분류·접수 시각·현재 상태·문의 본문·현재 공개 답변. 계정/빌드 정보는 권한상 허용된 기존 DTO만 사용 |
| 고객 답변 | ‘문의 작성자에게 표시됩니다’ 안내, 템플릿 선택, 일반 텍스트 입력, 글자수. HTML 입력/첨부/메일 발송 기능 추가 없음 |
| 처리 상태 | 접수=OPEN / 검토 중=IN_REVIEW / 종료=CLOSED. 기본은 현재 상태, 답변 작성만으로 종료를 자동 선택하지 않음. 종료된 문의는 종료만 선택 가능 |
| 고객 표시 미리보기 | 고객 답변과 고객에게 허용된 상태만 표시. 내부 메모·운영자 ID/내부 판단 제외. 기존 답변이 있으면 새 답변이 최신 표시를 대체함을 안내 |
| 내부 메모 | 별도 영역 ‘운영자 전용 · 고객에게 표시되지 않습니다’, 일반 텍스트 입력. 고객 답변에서 자동 복사하지 않음 |
| 실행 버튼 | 공개 답변 명령 ‘답변 등록’, 내부 전용 명령 ‘내부 메모 저장’, 답변 없는 상태 변경 ‘상태 저장’. 요청 중 중복 실행 차단. 닫기는 미저장 입력이 있을 때만 폐기 확인 |

### 명령·입력 규칙
- 답변 등록은 publicReply 필수, 선택한 status와 expectedRevision을 함께 보낸다. 내부 메모가 입력돼 있으면 같은 명령에 명시 포함하고 두 값이 한 번 저장되는지 검증한다.
- 내부 메모 저장은 internalNote만 보내고 상태는 현재 서버 상태를 유지한다. 고객 답변 초안은 전송하지 않는다. 상태 저장은 status만 변경하며 작성 중인 답변/메모가 있으면 먼저 저장하거나 지우도록 안내하여 누락을 막는다.

## 게임 내 문의와 오류·거래 상황 연결 — 2026-10-19 / 신규 제안
목적: 사용자가 기술 로그를 해석하거나 복사하지 않고도 겪은 문제를 신고하고 운영자는 허용된 원기록으로 조사한다. 기존 문의 접수/원키 receipt·본인 조회/공개 답변/내부 메모 분리·종료 정책을 재사용한다. dev 개발 진단 복사 기능을 일반 사용자 화면에 노출하지 않는다. 새 원격제어/첨부/채팅/자동환불/외부알림은 포함하지 않는다.
이 안은 게임 내 진입·최소 상황 연결의 신규 제안이다. 기존 홈페이지 문의 흐름과 같은 명령을 재사용할 수 있는 실제 인증/호출 경계는 구현 전 확인한다. 문의 API에 이미 상황 연결 필드가 있다고 가정하지 않는다.

### 1. 진입과 작성
기존 설정의 고객지원에서 문의 작성/내 문의로 진입. 실제 진행 차단 안내에는 필요할 때 '문의하기' 보조 입력을 제안하며 매 정상 거절에 표시하지 않는다. 전투 중 진입은 기존 메뉴/일시정지 규칙을 따르고 문의창이 임의 시간정지/재개 권한을 만들지 않는다.
작성 화면은 기존 분류·본문과 '함께 보내는 상황 정보' 요약. 사용자는 상황과 기대 행동을 자연어로 적고 발생 시각/화면·앱 버전 등 최소 요약을 확인한다. 입력은 기존 DTO 제한을 유지, 새로운 필수 장문 질문/ID 입력을 요구하지 않는다. 진단 상세 수치·API/버전 hash는 일반 화면에 숨긴다.

### 2. 연결 정보와 선택
서버 인증으로 확정하는 접수자 신원은 필수. 선택 상황 정보는 확인된 발생 시각·기능/화면·앱 버전·원작전/거래 참조·명시 오류의 안전 참조만 허용하며 작성 시 포함/제외를 확인할 수 있게 한다. 원거래 상태가 불명이라면 불명으로 전달한다.
전체 로그/원JSON·스택·인벤 전체·클립보드·기기파일·스크린샷 자동 수집은 하지 않는다. 일반 사용자에게 전체 계정ID/멱등키를 복사하게 하지 않는다. 상황을 첨부하지 않아도 기존 문의 접수는 가능해야 한다.
서버는 참조의 계정/환경/권한을 검증한다. 클라가 제출한 run/receipt ID를 믿고 타계정 기록을 연결하지 않는다. 누락/만료/접근불가 참조는 접수 오류와 구분할 수 있는 명시 계약이 필요하며 타계정 존재를 노출하지 않는다. 문의 본문을 오류 로그에 복제하지 않는다.

### 3. 기존 정보 재사용
현재 소유 Model/원receipt·이미 확보한 안전 오류 식별자를 사용한다. 문의창 열기 위해 전투/장비/보상 정보를 다시 조회하지 않는다. 기본 진입에 새 진단 업로드를 필수 선행으로 만들지 않는다.
작성 시작 시 사건 맥락을 고정하고 다음 노드/다른 run으로 이동했다고 원문의 상황이 바뀌지 않게 한다. 보낼 내용이 바뀌면 제출 전에 사용자에게 확인 가능한 요약을 갱신한다. 원문의 미확정 거래 상태는 접수 순간의 관찰이지 서버 최종 판정이 아니다.
동일 계정 내 임시 초안은 기존 허용 수명에서 보존, 계정 전환 후 새 계정에 초안/상황 참조를 붙이지 않는다. 유효한 내 문의 목록/상세는 기존 데이터 재사용, 실제 권한/버전 변경·명시 새로고침·최초 정보 부재 때 필요한 조회만 수행한다. 이는 과거 '재진입 자체 재조회' 문구보다 최신 공통 데이터 규칙을 우선한 설계다.

### 4. 접수·유실·오프라인
명시 '보내기' 1회 → 기존 접수 명령·원키/본문 보관 → 확정 ticketId/접수 상태를 응답으로 반영. 충분한 응답 뒤 접수 확인용 중복 GET 없음. 접수 중 중복 입력 차단, 자동 새키 재접수 금지.
네트워크가 없으면 '아직 전송되지 않았어요'와 초안을 표시하고 자동 접수 완료로 안내하지 않는다. 응답 유실은 '접수 결과 확인 필요'로 원키/receipt 복구. 확정 거절과 결과 불명을 구분한다. 앱 종료 후 초안/원요청 복구는 실제 보관 계약이 충족된 범위만 제공하며 무조건 보존을 약속하지 않는다.
사용자 설명의 추가/수정은 미접수 초안에서만. 확정 접수 이후 후속은 기존 새 문의+원문의 번호 방식 유지; 기존 문의를 몰래 덮어쓰거나 새 실시간 댓글 기능을 만들지 않는다.

### 5. 운영자 조사
Admin의 기존 문의 상세에서 '관련 상황'을 정제 표시하고 원오류/거래를 각 권한으로 조회한다. 고객지원 열람 권한이 ops 로그/결제·계정 상세 권한을 자동 부여하지 않는다. 원기록 없음/보존기한 종료/권한 없음은 확인 가능한 범위만 표시하고 오류0/거래없음으로 단정하지 않는다.
문의 상태와 오류 사건 상태는 별개. 오류 해결 표시가 문의 자동 종료/공개 답변 발송/보상 지급을 실행하지 않는다. 운영자가 기존 공개 답변·최종 설명을 확인해 처리하며 원오류/거래 링크는 고객 공개 답변에 자동 삽입하지 않는다.
자동 신고·로그 전송과 고객의 명시 문의를 구분한다. 오류 보고가 이미 있어도 문의가 자동 작성되지는 않는다.

### 6. 검수·담당
사용자 정상 작성/상황 제외/본문 제한·취소/다음노드 이동·계정교체·오프라인·commit후ACK유실/동일키재생·원기록 만료/타계정참조 거절·문의접수 성공과 상황 연결 불가 구분·운영자 권한차이·공개/내부 정보 분리·재진입 API를 검증한다.
권장 모바일 화면은 기존 입력/스크롤·하단 안전 영역을 재사용하며 키보드가 보내기/전송상태를 가리지 않아야 한다. 원거래에 변화·추가차감/자동보상0이 수용 기준.
Server는 기존 support 계약의 최소 참조/권한·원자 접수/원키 응답, Unity는 기존 메뉴/작성·소유상태 연결, Admin은 검증된 참조 소비, Plan은 사용자 흐름/수용 기준 담당. 실제 연결 계약 준비 전 소비 큐 선등록하지 않는다. 신규 상세 미승인, 코드/실접수/타채팅 지시 없음.

## 게임 문의 상황 연결 승인 — 2026-10-19

## 고객 문의로 발견한 버그 제보 보상 상세안 — 2026-10-19 / 신규 경제 제안
목적: 실제 결함 발견/재현에 기여한 사용자에게 감사하고 원손실은 별도 근거로 복구한다. 보상 종류/수치/심사·지급 규칙 모두 신규 제안이며 구현/실지급 권한이 아니다. 기존03 문의·15 오류사건·35/47 경제 원장/원권한을 재사용한다.

### 1. 두 지급 목적
피해 복구: 사라진 장비·미지급 보상·잘못 차감된 비용 등 원거래/실제 손실 근거를 확인하여 기존 복구 계약으로 처리. 최초 제보 여부와 무관하며 확인된 피해자를 제보 경쟁에서 탈락했다는 이유로 제외하지 않는다. 금액을 감사 보상표로 대신하지 않고, 원장 복구가 확정되지 않은 항목은 별도 검토한다.
제보 감사: 결함 확인에 기여한 대가. 아래 FREE 크리스탈 후보표를 사용하며 유료 잔액/결제 실적·등급으로 처리하지 않는다. 복구와 감사는 별도 원인/원장/receipt로 표시하고 각각 중복 방지한다. 동일 피해 전체 보상과 개별 원거래 복구의 겹침은 원보상 정책에서 차감/중복 허용 여부를 확인하고 임의 이중복구하지 않는다.

### 2. 감사 보상 후보표
| 등급 | 실제 영향 기준 | 최초 유효 발견 기여 보상 후보 |
|---|---|---|
| 경미 | 오탈자·표시 어긋남 등 진행/판정에 영향 없는 확정 결함 | FREE 크리스탈50 |
| 일반 | 일부 기능 오작동, 우회 가능하나 조작/정보 확인에 영향 | FREE 크리스탈150 |
| 주요 | 전투/퀘스트 진행 차단·반복 강제종료·실제 효과/보상 불일치 | FREE 크리스탈300 |
| 중대 | 광범위 접속/진행 장애·저장 손실·경제 무결성 문제 | FREE 크리스탈500 |
수치는 초기 제안이며 현재 제보량/발행량 실측으로 적정성이 검증된 값이 아니다. 등급은 사용자 불만 강도·문의 수·결제액이 아니라 확인된 영향/지원 범위/재현 근거로 판정. 같은 오류코드라도 원인이 다른 결함은 별도 사건. 보안 제보는 공개 재현/타인 자료 접근을 요구하지 않고 기존 권한 있는 비공개 조사로 분리; 이 표로 별도 보안 포상 제도를 신설하지 않는다.
월발행 예상 = 50×경미건수 +150×일반건수 +300×주요건수 +500×중대건수 + 추가기여 보상. 실제 eligible 사건/기여자 수가 없으므로 월총액/매출 영향은 미확인. 예산 이유로 이미 확정한 지급을 몰래 축소하지 않으며 변경표는 명시 시행 버전 이후 적용한다.

### 3. 중복·공동 기여
지급 단위는 문의 건수가 아닌 결함 사건ID+기여자 계정+보상 종류. 같은 원인의 재접수/여러 화면/같은 수정의 변형을 각각 지급하지 않는다.
최초 유효 제보는 단순 접수 시간만이 아니라 결함을 특정/확인할 수 있는 핵심 정보가 갖춰진 최초 시점으로 판정. 개발자 수준의 원인 분석·로그 제출은 요구하지 않는다. 기존 문의에 충분한 정보가 이미 있었으면 운영자 확인이 늦었다는 이유로 순위를 바꾸지 않는다.
기지급 결함의 단순 중복/이미 알려진 문제 반복은 감사 보상 제외하되 피해 복구는 별도. 이미 알려진 결함이라도 새 재현 조건·플랫폼·핵심 원인 단서를 제공해 실질 조사에 기여했다면 추가 기여 인정 후보. 추가 기여 보상은 해당 등급의50%(25/75/150/250) 제안, 동일인 동일 사건은 총 해당 등급 상한. 서로 독립된 유효 최초 기여가 동시성 때문에 순위를 확정하기 어려우면 근거를 남겨 공동 최초로 각각 기본액 지급 제안. 단순 다계정 추측으로 제외하지 않으며 결탁/반복 악용은 확인된 근거로 별도 판단한다.
기여 인정·등급 상향 시 이미 지급한 액수와 비교하여 부족분만 지급. 원인 사건 병합/분리는 감사 이력과 원지급을 보존하며 자동 재지급/자동 회수하지 않는다.

### 4. 제외·심사 경계
미재현은 허위 제보가 아니다. 확인 중으로 두고 필요한 최소 추가 정보를 기존 새 문의/원번호 연결 방식으로 요청한다. 정상 규칙·단순 선호/밸런스 의견·재현 기여 없는 반복 문의는 감사 대상에서 제외할 수 있으나 이유를 안내한다.
자신이 유발한 피해를 확대하거나 반복 부당취득한 경우 보상으로 유인하지 않는다. 단, 우연한 발견·최소 재현·선의 제보를 동일 취급하지 않고 기존 약관/증거에 따른 별도 판단. 감사 자격 심사만으로 원거래 권리/정상 문의 권한을 자동 박탈하지 않는다.
제보 접수는 보상 확정이 아니다. 수정 배포가 오래 걸려도 결함·기여·등급이 확인되면 감사 지급 심사를 진행하는 안을 권장한다. 실제 피해 복구는 원상태 확인이 별도로 필요하다.

### 5. 상태·원자 지급
감사 보상 상태: 심사 중→대상 확정/대상 아님→지급 처리 중→지급 완료. 응답유실은 결과 확인 필요이며 새 지급 건을 만들지 않는다. 문의 처리종료·오류 해결·감사 지급·피해 복구 각각 독립 상태.
