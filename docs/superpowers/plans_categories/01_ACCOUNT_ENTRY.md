# LAST RAIL | 계정·인증·로비 진입

> 현행 대조: 2026-09-21. 이 세션의 최신 사용자 결정이 우선한다. 기존 구현 증거는 해당 원문의 시점/범위로 유지하며, 판단 대기는 [00](00_INDEX.md#open-decisions)에서 관리한다.


범위: 인증 상태, 계정 준비, 가입·연결, 실제 Main/로비 연결. 다운로드·콘텐츠 승인·업데이트 규칙은 [02](02_CONTENT_UPDATE.md)에 둔다. 출처와 검증 결과는 [문서 안내](00_INDEX.md)를 따른다.

## 1. 진입 흐름과 책임

`서버 진입 승인 → 인증 복원/명시 로그인 → 안전한 토큰 저장 → 이름·프로필·스토리 준비 → 필수 콘텐츠 준비 확인 → Main 로드·로비 바인딩 → 로딩 종료`

인증과 콘텐츠 다운로드는 병행할 수 있으나, 로비는 두 준비 조건을 모두 충족해야 한다. ResourceBootstrap이 PlayerEntryRuntime와 기존 단일 PlayerAuthOwner를 소유한다. 화면은 세션을 만들거나 토큰 저장 권한을 별도로 갖지 않는다. 취소·계정/세대 변경 이후의 응답은 이전 소유자의 상태를 새 화면에 반영하지 못한다. 안전한 저장 성공 전에 새 세션을 채택하지 않는다. [R03](00_INDEX.md#r03) [R04](00_INDEX.md#r04) [R05](00_INDEX.md#r05)

## 2. 인증 저장·재시도

| 항목 | 규칙 |
|---|---|
| 안전 저장소 읽기 | `Loaded / Missing / Corrupt / Unavailable / ReadError`를 구분한다. 오류를 빈 저장소나 신규 게스트 생성 허가로 바꾸지 않는다. `Missing`만으로 자동 게스트를 만들지도 않는다. |
| 저장 형식 | 기존 Keystore 암호화 payload를 버전 envelope로 확장한다. 현재 세션과 최대 1개의 pending auth operation을 보존하며 기존 세션 payload 이행을 지원한다. |
| 최초 전송 | 암호학적 난수 operation key를 먼저 영속 저장한다. 확인된 서버 계약의 `Idempotency-Key` 길이는 16–128자다. |
| 성공 | 토큰 저장은 세션 교체와 pending 제거를 원자적으로 처리한다. 저장 실패·취소·종료로 원요청을 새 키로 바꾸지 않는다. |
| replay | 동일 guest/session 또는 동일 old-refresh/key 복구는 접수된 세션이 ACTIVE·미만료인 범위다. `auth_replay_expired`는 새 게스트 생성이 아니다. 키 없는 호출은 replay-safe로 취급하지 않는다. |
| 불확실성 | receipt 404는 조회 시점에 접수 기록이 없다는 뜻일 뿐, 이전 송신이 이후 접수될 가능성을 없애지 않는다. 임의 새 요청을 만들 근거가 아니다. |

토큰·키의 평문 파일/PlayerPrefs/로그 저장, raw exception 저장, 별도 token vault를 추가하지 않는다. 구형 모호한 `LoadAsync` 대신 소유자는 typed `ReadAsync`를 사용한다. [R03](00_INDEX.md#r03) [R04](00_INDEX.md#r04)

응답 파싱은 잘린 JSON·중복 필드·후행 내용을 거부하고 임의 타입 역직렬화를 허용하지 않는다. 해당 인증 복구 작업은 이 검증을 위해 프로젝트의 Newtonsoft `3.0.2`를 명시적으로 고정했다고 기록한다. [R03](00_INDEX.md#r03)

## 3. 가입·현재 계정 연결·비밀번호 초기화

가입은 로컬 인증 부재가 확인된 상태에서, 연결은 기존 인증 계정의 소유자 아래에서 수행한다. 미완료·취소된 연결이 기존 게스트를 로그아웃시키거나 교체하면 안 된다.

| 흐름 | 요청·완료 규칙 |
|---|---|
| 이메일 검증 | `PASSWORD_REGISTER` 또는 `PASSWORD_LINK`와 `recoveryEmail`을 사용한다. 연결의 start/confirm은 Bearer 인증이다. 확인 코드는 **8자리 문자열**로 보존한다. |
| 가입·연결 | `loginId / password / recoveryEmail / verificationChallengeId`만 전송한다. 검증 후 세션은 기존 런타임이 안전하게 저장·채택한다. |
| 비밀번호 초기화 | 시작은 `loginId / recoveryEmail`, 완료는 `loginId / recoveryEmail / verificationCode / newPassword`. 성공 후 로그인으로 돌아가며 토큰 저장·자동 로그인은 하지 않는다. |
| 응답 유실 | 가입·연결의 확정 여부는 명시적인 동일 ID 비밀번호 로그인으로 확인한다. 연결은 원래 accountId와 일치해야 한다. 새 credential POST, 계정 병합·교체·새 receipt endpoint를 만들지 않는다. |
| 사용된 challenge | 확인 응답 유실을 로컬 검증 성공으로 간주하지 않는다. 같은 challenge의 사용된 증명을 서버가 받아들이는지는 별도 서버 경계다. |

서버의 일반적인 reset 시작 응답을 계정 존재나 메일 배달 증거로 보지 않는다. 만료·서버 retry delay·단일 진행·취소를 처리하고, 자동 메일 재전송이나 백그라운드 비밀번호 재시도를 하지 않는다. 비밀번호·검증 값은 저장/로그에 남기지 않으며 입력을 비운다. 실제 Register/Reset/Link 동작은 기존 modal에 연결하고 이름 입력 전에 credential modal을 닫는다. [R06](00_INDEX.md#r06) [R07](00_INDEX.md#r07)

## 4. 이름·프로필·스토리 준비

`GET /v1/profile`과 `GET /v1/story-progress`를 같은 계정·취소 세대에서 수집한다. 명시적인 `displayName=null`이면 최초 이름 입력을 요구하지만, 누락·조회 실패를 미등록 이름으로 간주하지 않는다. 프로필은 계정 일치와 비음수 commander XP 등을 검증한다. 인증 오류에는 저널 기반 refresh 1회와 재조회 1회를 허용하고, 최종 실패는 로그인/복구로 돌린다.

정상 응답의 `none/order0/initial operation`은 초기 서버 상태일 수 있다. 해금 권위는 서버에 있다. `MissionNarrativeCatalog`의 기존 `ActOneMissionNarrativeFixtures/CreateActOne`은 표시용 compiled fallback이며, 배포된 외부 현지화 패키지나 해금·보상 권한이 아니다. 별도 bundle/tutorial-read/registrationReady/revision 필드는 요구하지 않는다. ## 5. Main 씬과 로비 바인딩

로컬 시작 씬은 `Assets/_LASTRAIL/Scenes/ResourceBootstrap.unity`다. 상주 bootstrap이 인증·네트워크·조정자·EventSystem을 유지한다. Main은 `Assets/_LASTRAIL/Scenes/Main.unity` 주소의 원격 필수 씬이며 `remote_launch_required`와 `launch_required`에 포함된다.

Main에는 MainSceneRoot와 초기 비활성 ContentMount를 두고, 인증/네트워크 소유자·EventSystem·카메라/오디오 리스너·직접 원화/프리팹 참조를 중복 배치하지 않는다. 승인 locator의 SceneInstance/IResourceLocation으로 로드해 기존 MissionShellScreen과 presenter·계정 연결·문의 동작을 재사용한다. 바인딩 성공 뒤에만 release 완료, Main 표시, bootstrap 숨김을 수행한다.

진입/정리는 공용 lease로 직렬화한다. 대기 중 prefab 작업을 먼저 끝낸 뒤 Main을 unload하고, 실패한 정리는 원래 lease를 보존해 명시 재시도한다. 중복 열기가 첫 진입을 무효화하지 않으며, Main 누락은 bootstrap 재시도로 남긴다. [R20](00_INDEX.md#r20) [R21](00_INDEX.md#r21)

## 6. 현재 기록과 남은 연결

9/7 감사의 저장 게스트 이름 취소·비밀번호 실패 후 취소 문제는 안전 저장소 재확인과 직렬화 복구로 수정됐다고 후속 보고됐다. 같은 감사의 네트워크/캐시 문제는 [02](02_CONTENT_UPDATE.md)의 현행 규칙을 따른다. 과거 감사 항목을 현재 결함으로 중복 등록하지 않는다. [R19](00_INDEX.md#r19) [R21](00_INDEX.md#r21)

자료상 Google 실제 SDK/설정·런타임 연결과 영속 logout/account switch는 미완료다. 로컬 무효화가 자격 증명을 지우는 로그아웃은 아니며, 계정 병합·게스트 삭제·조용한 교체를 허용하지 않는다. 새 Main은 당시 기존 빌드 카탈로그에 없었고 준비 manifest도 오래된 상태였다. 실제 출시 화면의 composite 설명 레이어 정리와 기기 검증도 로컬 바인딩 성공과 별도다. [R05](00_INDEX.md#r05) [R21](00_INDEX.md#r21)

## 7. 광고 없는 첫 출시·접속 공지·웹 계정 연결 — U7

신규 운영 정책은 [10](10_LIVEOPS_NOTICES.md)이 소유한다. 공지 조회/표시는 기존 인증·닉네임·프로필·콘텐츠 준비 소유자를 대체하지 않는다. 자동 팝업은 최초 안전한 로비 바인딩 이후에만 열고 공지 실패로 로비를 막지 않는 안이다. 정확한 읽음/재노출 규칙은 [10 §5](10_LIVEOPS_NOTICES.md#popup)를 참조한다.

광고 설정의 실패는 인증 실패가 아니며, 유효한 광고 허용 확인 전 SDK를 시작하지 않는다. 홈페이지 인증은 [11](11_WEBSITE_COMMUNITY.md#community)의 별도 웹 세션 연결이 필요하고, 게임 게스트나 토큰을 임의 병합/복제하지 않는다. 추가된 정책은 설계이며 기존 인증의 실제 구현 완료 범위를 변경하지 않는다.


## 8. U9 점검 진입·복귀 경계

게임 점검 차단은 일반 공지 팝업과 다르다. [12](12_SERVICE_MAINTENANCE.md#client-screen)의 로컬 점검 화면은 인증·필수 원격 콘텐츠 전에 표시할 수 있으며 기존 ResourceBootstrap/PlayerEntry 소유자를 재사용한다. 503/통신실패를 모두 계정 만료로 바꾸지 않고 토큰·게스트·미확정 요청을 보존한다.

점검 해제 후에는 상태 화면의 NORMAL만으로 Main에 들어가지 않고 새 admission·인증·프로필·콘텐츠 준비를 거친다. 이전 세대의 점검/정상 응답은 새 계정 상태를 덮지 못한다. 점검 중 운영 우회는 별도 서버 권한·감사 대상이며 클라이언트 bool로 허용하지 않는다.

### 3. 초반 플레이 흐름과 건너뛰기

첫로비→출격준비→기존적격성조회→사용자명시START→실작전→결과검증/정산→로비. 연료지불·정비·합성·투자·출격은항상기존사용자명령이며가이드가자동클릭/명령전송하지않는다. 출격준비에서지휘실을건너뛰어도미사용1P만남기고합법적출격은가능하다.

안내는한번에1개. 진행중안내에서 '다음' 또는 '나중에'로넘기고닫기/앱종료를콘텐츠완료로취급하지않는다. 우선순위는원요청복구/강제서비스상태→현재필수선택→현재새기능안내→로비추천안내. 기존공통모달미술과해당화면을사용한다. 화면에없는버튼을가리키거나대상찾기를전역객체검색으로우회하지않는다.

첫전투안내는기존입력/속도·집중대상·지원·궁극기의실지원기능만설명. 별도튜토리얼모드/적/무료연료를신설하지않고이미있는전용1wave훈련은원계약대로따른다. 일반모드의기존메뉴/선택hold는유지하지만가이드가새전투정지권한을만들지않는다. 월드보스안내는출발전에제공하며전투180초를멈추지않는다.

### 4. 월드보스 자격 — 신규 승인 요청

추천 진입조건: 지휘관Lv≥10 AND 서버확정 일반/스토리 정상승리≥1. 유효지원프로필의승리만증거로사용,튜토리얼/무효/자발포기/퀘스트패배종료실적/로컬QA는승리증거가아니다. 구프로필승리도실계정의권위있고유효한원영수증이면인정하되테스트/손상기록은자동승격하지않는다. 특정스토리분기나특정요원/상위특성 보유를강제하지않는다.

위두조건은입장자격이고,실제START에는활성이벤트·콘텐츠지원·적격편성/역할·티켓·주간마감·기존run제약을다시검사한다. 자격조건확정은실서버계정상태의거래/검증으로기록한다. 두조건이완성된시각을eligibilityAt으로고정하고WB4 초기2/이후05시+2/상한10을적용,화면최초열기/로그인을자격시각으로쓰지않는다. 정확05시충족은초기2만,같은경계중복없음. 이벤트가닫혀있어도자격과입장적격은다르며티켓회계는원WB4대로진행한다.

기존자격이있는계정은새조건미달이란이유로회수/티켓초기화/중복초기2장금지. 구미자격계정의두조건증거가이미있으면이행확정시1회자격부여,불확실한과거날짜로무제한소급티켓지급하지않는다. 실제이행자격시각·원잔액보존은Server가계약/QA로확인한뒤적용한다. 이미확정된자격의오류/무효정정은검토대상이며클라이언트자동잠금/회수로처리하지않는다.

### 5. 안내 상태·복귀 계약

안내키는계정+안내ID+콘텐츠버전. 상태는미적격→안내가능→표시중→확인/보류로분리하고실제기능해금과다른데이터로둔다. 필수선택이아닌가이드는보류해도기능을계속쓸수있다. 보류한안내는다음화면마다재팝업하지않고해당기능도움말에서재열기,이후로비에서는작은안내진입표시만허용하는안이다.

표시중앱종료는확인완료가아니다. 재진입시원run/원START부터복구하고현재화면에유효한안내만다시제공한다. 결과검증중에는해금성공/레벨업을예측하지않는다. 계정변경시이전안내/비동기응답/강조영역해제. 읽기표시실패는도움말재노출문제일뿐강화차감/티켓/보상실패로연결하지않는다.

기존계정은지원되는기능을다시잠그거나모든신규유저안내를강제하지않는다. 실제추가된포탑레벨등새기능안내만별도버전으로제공하며전체튜토리얼재수행을요구하지않는다. 표시갱신이입력명령을다시발행하지않도록Controller→View 갱신과View의사용자의도를분리한다.

### 7. 담당·승인 경계

기존Vex/Lv1포인트/Lv25상위조건은유지사항이다. 안내순서/보류·재노출/기존계정처리와월드Lv10+첫승리·자격시각/이행처리는신규추천으로승인대기다. 영구경제v03의성장속도수치는아직제안이므로 '3일차월드해금' 같은달성일을확정하지않는다.

승인후Server가실해금/소유/eligibilityAt/티켓경계계약을소유하고 S-02/S-04 및포탑S-06과중복을대조한다. Direction은기존승인화면의안내상태·독립요소만보완,Unity는실계약후Guide Controller·화면콜백/수명을연결한다. 선행완료→후속큐등록규칙대로진행하며승인전실행큐추가/기존계정변경없음.

다음상세기획4는기본5인외요원이며,실제명단·기존해금·역할·스킬을먼저대조한다. 코어반복수급·전원승급경제는로스터와묶은별도잔여로유지한다.
