# LAST RAIL | Admin 운영 경계·광고 스위치·접속 공지

작성/검토: 2026-09-21. 상태: **사용자 요구 U7·운영 일원화 U8·환경/점검 U9 연결 + 광고 OFF 화면 후속 설계안**. 코드·DB·SDK·스토어·원격 활성화는 수행하지 않았다.

사용자가 명시한 요구: 첫 공개 버전은 광고 없이 데모 느낌으로 제공하고 서버 값으로 광고 ON/OFF를 제어한다. Admin에서 공지를 등록하고 클라이언트가 조회하며, 처음 접속했을 때 팝업으로 보여준다. 홈페이지의 공지와 같은 원문을 사용하도록 연결한다.

J08/J09에서 **광고 스킵 비보유자 BASIC_ONLY·보유자 혜택 유지·첫 데모 광고스킵 신규판매 숨김·새 공지별 첫 안전 로비 팝업1회**를 승인했다. 새 논리 필드명과 기술 구현은 계약 연결안이다. 광고 없는 출시가 모든 결제의 중단, 무료 광고 보상 지급, 계정 초기화, 무료 무제한 연료를 뜻한다고 해석하지 않는다. U9에 따라 STG는 폐기하고 개발·통합·실기기 검증은 DEV에서 전부 수행한다. 실제 공개 출시는 향후 PROD 별도 승인 단계다.

담당 경계: 보상 계산·SSV·원자 정산은 [06](06_REWARDS_ROULETTE.md), 영구권은 [07](07_AD_SKIP.md), 선택/리롤은 [05](05_AUGMENTS.md), 밸런스 배포는 [08](08_BALANCE_RELEASE.md), 홈페이지 공개·커뮤니티는 [11](11_WEBSITE_COMMUNITY.md)가 소유한다.

## 0. 운영은 기존 Admin Console로 일원화 — U8 확정

사용자 지시: 운영 기능은 모두 기존 Admin Console에서 처리한다. 앱·홈페이지는 사용자 입력과 조회를 맡고, 서버가 데이터를 저장·검증하며, 운영자는 Admin에서 조회·답변·변경·게시한다. 홈페이지용 별도 운영 백오피스, 별도 고객센터 관리 도구, 별도 공식 위키 CMS를 만들지 않는다. 기존 Admin 안의 메뉴·기능 확장으로 연결한다.

**사용자 앱/홈페이지 → 사용자용 서버 API → 서버 데이터 → Admin용 API·기존 Admin Console**이 기본 경계다. Admin도 DB를 브라우저에서 직접 수정하지 않고, 서버가 운영자 권한·환경·변경 조건을 검증하는 관리 명령을 사용한다. 처리 결과는 서버에 저장한 뒤 사용자에게 허용된 부분만 다시 조회하도록 제공한다.

| 운영 분야 | 기존 Admin의 담당 | 사용자 앱·홈페이지의 담당 |
|---|---|---|
| 고객문의·진단 | 문의/오류 목록·상세·검색, 담당/처리 상태·답변·내부 메모 | 문의 접수·접수 확인, 본인에게 공개한 처리 결과 조회. 상세 경계는 [03](03_SUPPORT_DIAGNOSTICS.md#admin-support) |
| 공지·FAQ·알려진 문제·상태 안내 | 작성·검수·게시·예약·철회 | 공개/대상 범위에 맞는 조회, 앱 공지 확인 |
| 서비스 점검 | [12](12_SERVICE_MAINTENANCE.md)의 점검 예약·시작·연장·해제·감사 | 공개 상태 조회·점검 화면·재확인. 별도 운영 시스템 없음 |
| 광고 운영 | adsEnabled 변경과 감사·미완료 거래 확인 | 승인된 현재 정책에 맞게 표시·실행 |
| 위키·확률·밸런스 | 원본 검증·공개 투영 검수·발행·승격·롤백 | 승인된 공개 버전만 읽기. 수치 원본은 [08](08_BALANCE_RELEASE.md) |
| 커뮤니티 신고·제재 | 신고 큐·검토·숨김/복원·수동 제재·이의제기 처리 | 본인 글/댓글 작성·수정·삭제, 신고·개인 차단. 서버 권한 검사 필수 |
| 계정·권리 요청 | 비공개 요청 조회·본인 확인·승인된 처리 명령 | 인증된 신청·본인 처리 결과 확인 |

운영 행위에는 서버의 역할별 권한과 변경 이력을 적용한다. 내부 메모·신고자 정보·비공개 문의는 공개 응답에 포함하지 않는다. 요청 접수·예약 게시 실행·기한 만료·캐시 갱신 같은 승인된 서버 자동 처리는 유지한다. 'Admin에서 운영'이 모든 서버 처리를 사람이 매번 실행한다는 뜻은 아니다.

문의 답변 자체를 재화 지급 명령으로 취급하지 않는다. 보상 조정이 필요한 경우 기존 별도 권한·원장·중복 방지 명령을 사용하며 새 지급 기능을 이번 정정으로 추가하지 않는다. 영구 계정 제재는 기존대로 권한 있는 운영자가 직접 검토 후 수동 실행한다.

이 절은 운영 책임의 확정이며 기능 구현 완료 선언이 아니다. 문의 서버 저장·Admin 조회의 기존 로컬 증거는 [R10](00_INDEX.md#r10)·[R12](00_INDEX.md#r12)에 있고, 웹 연결·답변·상태·개별 관리 기능은 실제 계약/구현을 확인해 확장한다. 이후 J08/J09에서 광고 OFF 혜택과 팝업 빈도를 개별 승인했다. 그 내용은 §2·§5가 소유한다.

## 1. 광고 스위치와 밸런스 버전의 분리

운영자가 바꾸는 광고 마스터 값은 **`adsEnabled: boolean` 하나**다. 최초 광고 없는 공개 프로필은 false로 준비한다. false를 구매권 보유와 같은 뜻으로 사용하지 않는다.

이 값은 작전 고정 BalanceVersion 본문이 아니라 별도 **RuntimePolicy**에 둔다. 밸런스는 작전 중 고정되지만 광고 중단은 새 광고 요청부터 반영되어야 하기 때문이다. 작전 시작에 기록한 광고 설정은 진단 이력이지 현재 광고 시작 권한이 아니다.

| 논리 필드 | 의미 |
|---|---|
| environment / applicationId / platform / channel | [08](08_BALANCE_RELEASE.md)의 서버 승인 문맥. 현재 DEV, 향후 PROD; STG/STAGE는 폐기 |
| runtimePolicyRevision | 해당 문맥의 단조 증가 개정 번호. 롤백도 새 번호 |
| adsEnabled | 광고 노출을 허용할지 정하는 유일한 마스터 스위치 |
| effectiveAt / expiresAt / serverTime | 적용 시점·클라이언트 허용 유효기간·서버 시간. 실제 기간은 구현 계약에서 명시 |
| updatedBy / changeReason / requestId | 관리자 감사와 재시도 동일성. 클라이언트 공개 응답에는 필요한 표시 정보만 투영 |

서버 문맥당 현재 정책은 하나만 존재한다. 운영 설정에 밸런스의 하위 버전코드 탐색을 그대로 적용하지 않는다. 모든 지원 앱에 같은 OFF가 적용되어야 하며, ON일 때는 빌드 등록의 광고 처리 지원 여부를 추가 검사한다. DEV와 향후 PROD 설정은 서로 독립이다. 데이터 승격으로 adsEnabled=true까지 자동 복제하지 않는다.

### 1.1 실제 사용 가능 조건

`실제 광고 가능 = adsEnabled AND 현재 서비스의 신규 광고 허용 AND 서버 승인된 광고 지원 빌드 AND 유효한 광고 기능/배치 설정 AND 공급자 사용 가능 AND 필요한 동의·연령 처리가 완료됨`

여러 광고 마스터 스위치를 만들자는 의미가 아니다. 운영 값 하나와 실제 기능의 준비 조건을 구분한다. 실제 광고 SDK가 없는 빌드는 true를 받아도 UNAVAILABLE이며, 서버 값이 SDK나 C# 코드를 설치하지 않는다.

DEV에서 통합·실기기 ON을 시험할 때도 승인된 테스트 광고/격리 공급자만 사용한다. 라이브 광고 클릭·실지급을 검증의 전제로 삼지 않는다. 향후 PROD ON은 별도 출시·개인정보·공급자·스토어 검증 후 승인한다.

### 1.2 클라이언트 동작

부트 때는 광고를 기본 비활성 상태로 둔다. 서버 승인 문맥의 유효한 정책을 받은 후에만 필요 동의 흐름과 SDK 준비를 진행한다. false 또는 정책 미확인 상태에서는 광고 SDK 초기화·미리 로드·광고 요청·노출을 시작하지 않는다. SDK/중개 SDK의 자동 초기화 경로와 manifest 의존성도 실제 빌드에서 확인해야 한다.

캐시된 true만으로 새 프로세스에서 광고를 시작하지 않는다. 부트·포그라운드 복귀·로비의 안전 경계·광고 버튼 사용 전에 정책의 유효성을 확인한다. 네트워크 실패·만료·잘못된 응답·다른 환경 캐시이면 **광고만 비활성**하고 정상 기본 보상·이미 승인된 전투·무료 규칙을 막지 않는다. 기존 게임 진입/통신 요건은 그대로이며 오프라인 신규 작전을 새로 허용하지 않는다.

false를 확인하면 새 로드/노출을 중단하고 아직 보여주지 않은 캐시 광고는 폐기한다. 이미 공급자 화면에서 재생 중인 광고나 SDK 내부 통신을 즉시 강제 취소할 수 있다고 약속하지 않는다. 안전하게 종료된 뒤 더 이상 광고를 시작하지 않고, 해당 유효 거래는 §3에 따라 정산한다. 동의/SDK 초기화 중 정책이 바뀌는 경우에도 await 후 최신 generation/revision을 재검사한다.

의도적 OFF, 서버 조회 실패 UNKNOWN, SDK 미설정 UNAVAILABLE를 내부 상태와 진단에서 구분한다. 모두 새 광고를 실행하지 않지만, 장애를 '데모 정책'이라고 잘못 안내하지 않는다.

<a id="off-benefits"></a>
## 2. 광고 OFF 시 혜택·UI — J08 승인

**광고 스킵 비보유자에게 BASIC_ONLY를 적용**한다. 광고 OFF에는 정상 게임·기본 보상·기존 무료분을 제공하고 광고 전용 추가 혜택은 숨긴다. **ACTIVE 구매권 보유자는 OFF에서도 광고 없이 기존 룰렛과 적격 추가 리롤을 정상 사용**한다. 구매권 사용승인은 별도이며 OFF를 가짜 시청 완료·전원 구매권으로 바꾸지 않는다.

| 기능 | adsEnabled=false 확정 처리 |
|---|---|
| 작전 클리어 기본 보상 | 정상 수령, 결과 팝업 유지 |
| 보급의 기본 수령 | 정상 유지 |
| 기존 무료 리롤 | 기존 잔량·조건 유지. 무료분의 단위를 임의로 바꾸지 않음 |
| 기존 무료 연료 충전·자연회복 | 기존 정책 유지. 새 수치/횟수는 만들지 않음 |
| 광고 보급·클리어 추가 보상 | 신규 광고 버튼/기회 숨김. 기본 수령을 대체하지 않음 |
| 광고 승인에 의존하는 추가 리롤·연료 | 신규 광고 경로 숨김/명시 비활성. 무제한 무료 대체 없음 |
| 이미 승인된 기회·확정 결과 | 조회·복구·정산 유지, SDK 재생·재추첨 금지 |
| 영구 광고 스킵 신규 판매 | 최초 데모에서는 숨김/신규 결제 미활성화. 기존 소유권 삭제와 다름 |
| 이미 적법하게 보유한 영구권 | 광고 없이 상품 승인→기존 룰렛·추가 리롤 사용. 원한도·적격성 유지, OFF만으로 차단/회수하지 않음 |

기본 보상 화면은 공용 View를 재사용할 수 있지만, 기본 수령을 광고 룰렛의 랜덤 배수 지급으로 바꾸지 않는다. 광고 기능의 존재를 전투 필수 조건으로 설계하지 않는다. 광고 도입 시에도 정상 무료 플레이를 의도적으로 막는 규칙을 이 스위치에 넣지 않는다.

**전원 DEMO_FREE 대체는 채택하지 않는다.** 미보유자에게 광고 추가분을 무료 지급하지 않는다. 구매자는 무료 대체가 아니라 자신의 유효 상품권에 의한 기존 승인 경로를 사용한다.

광고 OFF와 일반 IAP 판매정책은 다른 영역이다. 모든 상품을 OFF 처리하거나 무료 게임이라는 가격 정책을 새로 확정하지 않는다. 데모의 공개 범위·향후 광고 도입·저장 승계/초기화는 공개 전에 안내하고, '평생 광고 없음'이라는 약속을 만들지 않는다.

### 2.1 광고 OFF 클라이언트 화면 — 준비 요구 확정·세부 설계안

2026-09-21 사용자의 "광고 off 상태일때에 클라 화면도 만들어야겠지?"에 따른 화면 요구 구체화다. 광고 없는 첫 공개판에 필요한 화면 상태를 정의한다. J08에서 §2의 비보유자 BASIC_ONLY와 보유자 상품 경로를 승인했다. OFF UI도 두 권한 상태를 구분한다. Unity 화면·프리팹·이미지 시안·코드는 아직 만들지 않았다.

**광고 OFF는 점검/게임 이용 불가 상태가 아니라 광고가 없는 정상 화면 상태다.** 별도의 전체 화면 '광고 비활성' 차단 씬을 만들지 않고, 기존 보상·보급·증강·연료·상점 화면에서 광고 전용 영역을 제거한 정상 레이아웃을 준비한다. 광고 ON/OFF별로 보상 지급 Controller나 화면 전체를 복제하지 않는다. [06](06_REWARDS_ROULETTE.md)의 공용 View·권한 경계를 재사용한다.

OFF 최초 화면부터 광고 배너·시청 버튼·광고 배수 미끼 문구·관련 알림 배지가 먼저 보였다가 사라지지 않게 한다. 광고 정책만 미확인인 동안 기본 화면은 먼저 표시하며, 광고 정책 로딩 때문에 전 화면을 로딩으로 묶지 않는다. 일반 인증·게임 진입·기본 보상 데이터 준비 요건을 생략한다는 의미는 아니다.

### 2.2 화면별 구성표 — 광고 스킵 비보유자 BASIC_ONLY

| 화면 | 남기는 요소 | 광고 OFF에서 숨기거나 바꾸는 요소 | 입력·결과 규칙 |
|---|---|---|---|
| 작전 승리/결과 | 작전 결과·서버 기준 기본 보상 목록·수령/완료 상태 | 신규 광고 추가 보상 버튼, 신규 광고 배수 제안, 신규 광고 룰렛 진입 | 미수령이면 '보상 수령', 서버 수령 확정 뒤 '확인'. 화면을 열었다는 이유로 수령 성공 처리 금지 |
| 보급 | 적격 기본 보급량·기본 수령·원래 수령 주기 | 광고로 보급 추가/증폭하는 신규 경로 | 광고로만 제공되던 추가 영역은 접고 기본 수령 영역을 확장. 적격 보급이 없으면 정상 대기 상태 표시 |
| 증강 선택 | 최초 3후보·선택/확정·서버가 준 무료 리롤 단위별 잔량 | 광고 승인이 필요한 추가 리롤 진입 | 무료 잔량 소진 시 '무료 리롤을 모두 사용했습니다'. 선택은 계속 가능. 광고 OFF를 이유로 무료 리롤을 자동 추가하지 않음 |
| 연료 | 현재 연료·최대치·자연회복·기존 무료 충전 조건/잔량 | 신규 광고 충전 버튼·광고 알림 배지 | 무료분 소진 시 회복 안내 등 실제 대안 표시. 무제한 충전 또는 입장 비용 면제 없음 |
| 상점 | 광고와 무관하게 제공 중인 상품·정책·계정/구매 복구 진입 | 최초 데모에서 영구 광고 스킵 신규 판매 카드 숨김 | 판매정책은 [07](07_AD_SKIP.md)과 구분. 기존 소유권·복원·확정 거래는 숨기거나 삭제하지 않음 |
| 로비·바로가기 | 작전·편성·보관함·내실·공지 등 정상 기능 | 광고 전용 바로가기·시청 가능 배지·광고 알림 | 광고 전용 카테고리가 비면 빈 타일/빈 메뉴를 남기지 않고 남은 기능으로 재배치 |
| 이미 진행한 보상 복구 | 기존 승인·결과 조회·명시 재시도·최종 수량 | 새 SDK 재생·새 룰렛 추첨 | OFF 화면의 예외가 아니라 원거래 상태의 별도 표시. 기본/광고/상품 경합의 단일 기회를 보호 |

**보유자 OFF 화면:** 서버 ACTIVE·기능 가용성이 확인되면 기존 보급/클리어 룰렛 버튼과 무료분 소진 뒤의 추가 리롤1회 버튼을 유지한다. 광고 배지·시청 문구 없이 상품 혜택임을 표시하고, 광고SDK는 호출하지 않는다. 상품 승인으로 광고 없이 이용할 수 있는 기존 혜택은 별도 상품 권한/기능 가용성으로 판단한다. `adsEnabled=false` 하나만으로 상품 사용 버튼까지 전부 제거하거나, 모든 구매자를 비보유자로 표시하지 않는다. 반대로 상품 조회 실패를 임의 ACTIVE로 보완하지 않는다.

공개 확률/정책/과거 원기회 상세를 읽는 경로는 유지한다. 숨기는 것은 현재 제공하지 않는 **신규 광고 행동**이며, 역사적 확률 안내나 법적 안내까지 삭제하는 것이 아니다. 다른 비광고 보상 시스템의 룰렛도 광고 OFF만으로 일괄 비활성화하지 않는다.

### 2.3 기본 보상 레이아웃·문구

작전 결과 화면의 기본 순서는 **작전 결과 요약 → 기본 보상 목록 → 수령 동작 → 서버 확정 결과/확인**이다. 보상 카드·배경·공통 프레임·수량 표시는 재사용할 수 있다. 신규 BASIC_ONLY 수령에는 광고 배수 추첨, 광고 시청, 공용 룰렛의 6.5초+0.6초 회전을 억지로 거치게 하지 않는다. 이는 이미 승인된 룰렛 결과 복구나 상품 승인 결과의 원래 표시 계약을 변경하는 규칙이 아니다.

| 실제 상태 | 권장 문구/버튼 | 금지하는 오인 |
|---|---|---|
| 서버 기본 보상 확인·미수령 | '보상 수령' | 광고가 없다는 이유로 수량을 늘리거나 이미 지급됐다고 표시 |
| 수령 요청 처리 중 | '수령 처리 중' | 광고 로딩·광고 재생 대기라고 표시 |
| 수령 성공 여부 불명 | '보상 처리 결과를 확인하고 있습니다' / '결과 확인' | 새 키로 다시 지급 요청, 무조건 기본 수령으로 갈아타기 |
| 수령 확정 | '수령 완료' / '확인' | 확인 버튼으로 같은 보상을 재지급 |
| 최초 광고 없는 공개판 안내 | '현재 공개 버전은 광고 없이 제공됩니다.' | '평생 광고 없음', '모든 광고 보상 무료' |
| 정상 서비스에서 광고만 정책상 중단 | '현재 광고 보상은 제공되지 않습니다.' | 전체 서비스 점검 또는 네트워크 오류라고 단정 |
| 광고 정책/공급자 상태 미확인 | 필요 시 '광고 기능 상태를 확인할 수 없습니다.' / '다시 확인' | 확인되지 않은 데모 정책을 현재 사유로 만들어 표시 |

일상 화면마다 광고 OFF 알림을 강제 팝업으로 반복하지 않는다. 최초 공개 안내는 공지 또는 설정/게임 정보의 짧은 안내로 제공한다. 일반 OFF는 중립 문구를 사용하고, 데모 문구는 실제 해당 공개판 안내가 승인된 경우에만 사용한다. 서버에 없는 새 사유 필드나 영구 무광고 약속을 UI가 추측하지 않는다.

광고 영역을 단순히 투명하게 만들지 않는다. 비활성 버튼·레이캐스트·키보드/패드 포커스·접근성 탐색 대상도 함께 제거하고, 남은 버튼 폭·간격·스크롤 끝·safe area를 재계산한다. 광고 ON/OFF가 바뀌는 프레임에 포인터 아래의 광고 버튼이 기본 수령 버튼으로 교체되어 오입력이 나지 않도록 진행 중 입력을 취소하고 안전 경계에서 레이아웃을 반영한다. 보상 4개 이상·긴 수량·작은 화면에서도 수령/확인 접근을 보장한다.

### 2.4 표시 상태는 운영 스위치·상품권·원거래와 분리

운영자가 조작하는 마스터 값은 기존 `adsEnabled` 하나를 유지한다. 다음은 클라이언트의 파생 표시 상태 예시이며 별도 운영 ON/OFF 값을 추가하는 것이 아니다. 실제 DTO/필드명은 기존 계약과 맞춰 확정한다.

| 파생 상태 | 광고 표시 | 기본 기능 |
|---|---|---|
| CHECKING / UNKNOWN | 새 광고 진입 숨김, 필요한 경우 광고 영역만 조회 안내 | 일반 진입/보상 조건이 충족되면 계속 사용 |
| DISABLED_BY_POLICY | 광고 없는 정상 레이아웃 | 기본 수령·무료 규칙 유지 |
| UNAVAILABLE | 사용할 수 없는 광고만 숨김/사유 안내 | 기본 기능 유지; 정상 OFF 사유로 위장하지 않음 |
| AD_AVAILABLE | 적격 화면에 명시적인 광고 행동 표시 | 기존 기본 행동도 유지 |

원거래 상태(PENDING/APPROVED/CLAIMED 등)와 상품권 상태는 위 표를 덮어쓰는 하나의 bool로 합치지 않는다. 원거래 복구가 있으면 해당 기회의 중복 지급을 막는 조회·재시도 화면을 우선 제공한다. 모든 상태 판단은 현재 계정·환경·세션 generation에 결속하며, 늦게 돌아온 이전 계정 응답이 새 화면을 켜지 못하게 한다.

ON→OFF를 확인하면 새 광고 입력을 즉시 막고 §3의 원거래 규칙을 유지한다. OFF→ON은 유효 정책·기능 가용성·필요 승인 이후에만 반영하고, 이미 열린 기본 수령 화면에서 광고를 자동 시작하거나 새 강제 모달을 열지 않는다. 서비스 점검이 함께 시작됐으면 [12](12_SERVICE_MAINTENANCE.md)의 점검 gate가 해당 기능의 사용을 제한하되, 광고 OFF 자체를 점검으로 해석하지 않는다.

### 2.5 화면 구현 인수 항목 — 실행 전 요구사항

- cold start의 OFF/UNKNOWN에서 광고 진입·빈 광고 공간·불필요한 배지·숨은 클릭 대상이 보이지 않는다.
- 작전 결과와 보급의 기본 수령은 기존 서버 명령을 재사용하고, 미수령/처리 중/결과 불명/완료를 구분한다.
- 증강 무료 리롤과 연료 무료분은 원래 단위·잔량을 유지하며, 소진 뒤 신규 광고로 자동 전환하지 않는다.
- 모든 무료분을 소진한 OFF에서도 증강 선택 확정·정상 뒤로 가기 등 막히면 안 되는 행동에 막힘이 없다.
- OFF의 신규 기본 수령은 광고 SDK/신규 광고 intent/광고 spin을 호출하지 않는다. 기존 승인 거래의 정산·확정 결과 조회와 혼동하지 않는다.
- ON/OFF 전환, 계정 교체, 화면 재열기, 지연 callback, 수령 중 정책 변경에도 중복 지급·무료 혜택 증가가 없다.
- 구매권/원거래 복구 진입을 보존하고 일반 상품을 일괄 숨기지 않는다.
- 360×640·720×1280·1080×1920, 세로 비율 변화·safe area·큰 글자·긴 수량·4개 이상 보상을 실제 UI 구현 후 검수한다. 이 문서 편집은 렌더 검수가 아니다.

근거: 기존 [R25](00_INDEX.md#r25)는 기본 수령/광고 복구를 구분하고, [R26](00_INDEX.md#r26)는 View가 표시·입력만 맡으며 보상 Controller의 권한을 유지한다. [R30](00_INDEX.md#r30)는 권한 UNKNOWN과 기본/무료 규칙을 분리한다. 여기의 OFF 전용 배치·카피·표시 모델은 그 원칙을 유지하며 새로 제안한 설계다.

## 3. ON/OFF 전환 중 요청·보상 일관성

서버는 광고 기회 생성과 실제 show 시작 승인에 최신 RuntimePolicy를 확인한다. 화면 bool만 끈 채 HTTP로 광고 승인을 만들 수 있게 두지 않는다. 시작 승인과 OFF 경합은 같은 권한 검사 경계에서 순서를 확정하며, OFF 이후 새 시작 승인은 거절한다.

| 상태 | OFF 이후 처리 |
|---|---|
| 기회 없음 | 새 광고 intent/시작 승인 거절 |
| 기회만 생성, 아직 시작 승인 없음 | 신규 시작 금지. 기존 기본 수령과 취소/만료 규칙으로 진행 |
| OFF 전에 유효하게 시작 승인됨 | 원계정·원배치·원기한·SSV 검증을 유지하여 완료를 처리. 스위치만으로 보상 자격 소멸시키지 않음 |
| 이미 검증/승인된 결과 | 기존 기한·원결과대로 원자 정산. 새 뽑기 없음 |
| CLAIMED | 원결과 조회만, 중복 지급 없음 |
| 요청 성공 여부 불명 | 동일 키/본문으로 복구. 새 기회/새 원장 생성 금지 |

시작 승인 필드는 신규 설계이며, 실제 공급자 callback/기존 intent 모델에 어떻게 결속할지 서버·Unity 계약에서 확정해야 한다. 지원되지 않는 SDK를 마치 안전하게 즉시 중지할 수 있는 것처럼 표시하지 않는다.

OFF는 공급자 SSV 수신 endpoint, 원기회 조회, 구매 복원, 지급 영수증 읽기를 폐쇄하는 명령이 아니다. 변조·만료·타계정 거래는 기존대로 거절하고, 기본/광고/상품 경합도 [06](06_REWARDS_ROULETTE.md)의 단일 기회 원자 정산을 유지한다. OFF 때문에 유효 기한을 임의 연장하거나 원승인 사유를 DEMO_FREE로 바꾸지 않는다.

### 3.1 Admin 변경 절차

현재 환경·현재 값·영향 기능·대상 빌드·미완료 광고 기회를 미리 보여준다. 관리자 권한, 변경 이유, expectedRuntimePolicyRevision, 중복 방지 키를 받고 값/개정/감사/원결과를 원자 저장한다. 동시 변경은 충돌 반환한다. ON 전에는 SDK·정책/배치·SSV·동의·스토어 표시 검증을 요구한다. OFF는 즉시 새 시작을 중단시키는 운영 수단이고, UI 반영의 실제 지연은 TTL/재조회/이미 열린 광고에 따라 제한됨을 명시한다.

광고 지원 코드가 없는 데모 빌드는 별도 앱 업데이트 전까지 ON 불가다. 코드가 포함된 경우에도 스위치는 스토어 신고나 개인정보 고지를 자동 변경하지 않는다. 숨은 기능으로 심사를 우회하는 용도로 사용하지 않는다.

## 4. 공지 원문과 게시 수명

Admin에서 공지를 작성·검토·게시하고, 게임과 홈페이지는 **동일 Notice의 각 공개 projection**을 조회한다. 두 곳에 공지 내용을 복사해 따로 수정하지 않는다. 일반 공지의 게시 수명은 밸런스 버전과 독립이다.

`DRAFT → 예약(SCHEDULED) 또는 즉시 게시(PUBLISHED) → 기간 종료(EXPIRED) / 철회(WITHDRAWN)`

예약은 서버 시간으로 평가한다. 시간은 UTC로 저장하고 관리자 기본 편집/표시 시간은 Asia/Seoul임을 명시한다. 유효 기간은 `[startsAt, endsAt)`이며 끝이 없으면 endsAt=null이다. 등록/임시저장은 자동 공개가 아니다. 게시 뒤 수정은 새 revision으로 남기고 이전 원문/행위자/시각을 감사 이력에 보존한다.

| 공지 데이터 | 필수 의미 |
|---|---|
| noticeId / revision | 원문 ID와 편집 버전 |
| presentationRevision | 다시 팝업으로 알려야 하는 내용 버전. 오탈자 수정만으로 증가시키지 않음 |
| type | GENERAL / UPDATE / MAINTENANCE / EVENT / KNOWN_ISSUE 등의 분류 |
| title / summary / localizedBody | 제목·목록 요약·지원 언어의 제한된 서식 본문 |
| imageAssetId / action | 승인된 이미지 자산과 명시적 이동 동작. 임의 스크립트 금지 |
| surfaces | APP / WEB / BOTH. 같은 원문이라도 노출 대상을 구분 |
| visibility | PUBLIC / AUTHENTICATED / INTERNAL. 공개 홈페이지에는 PUBLIC만 가능 |
| environment / channel / platform / min,maxVersionCode | 적격성 필터. 버전 하향 선택을 공지 본문에 적용하지 않음 |
| startsAt / endsAt / status | 게시 기간과 수명 |
| popupMode / priority / pinned | 자동 팝업 대상·정렬·상단 고정. pinned가 반복 강제 표시를 뜻하지 않음 |
| author / editor / publisher / timestamps | 권한·감사. 외부 응답에는 내부 개인정보를 투영하지 않음 |

한 사람이 여러 운영 역할을 맡을 수 있지만 공지 편집·게시·철회·광고 설정 권한은 논리적으로 구분한다. 과거 공지 전체를 무조건 공개하는 것이 아니라 대상 표면과 공개 승인을 검사한다.

## 5. 첫 접속 팝업 — J09 승인

**새 공지가 나온 뒤 해당 계정이 처음 안전한 로비에 도달했을 때1회 표시**한다. 중요한 내용 개정에만 presentationRevision을 올려 재알림하고, 단순 오탈자는 재노출하지 않는다. 계정 생성 때만 한번 또는 매일 강제팝업으로 바꾸지 않는다.

기본 `popupMode=ONCE_PER_NOTICE_REVISION`. 새로 표시할 공지가 있을 때만 한 세션에서 하나의 모아보기 팝업을 연다. 우선순위/시작시각/ID로 결정적으로 정렬하고 여러 공지는 그 안의 목록·탭·이전/다음으로 제공한다. 중요한 공지도 닫기/확인을 제공하며, 약관 동의나 광고 동의로 취급하지 않는다.

조회는 준비 과정에서 가능하지만 자동 표시는 앱 진입 승인·인증·이름/프로필·필수 콘텐츠 준비 후 실제 로비 바인딩이 성공한 안전 경계에서 한다. 계정 복구·작전 복구·선택 이벤트·보상 확정 중에는 끼어들지 않는다. 다른 필수 모달 종료 후 여전히 적격인지 확인해 표시한다. 공지 fetch 실패는 로비 진입을 막지 않으며 메뉴에서 다시 조회할 수 있다.

| 조회/읽음 상황 | 처리 |
|---|---|
| 신규 계정, 게시 중인 팝업 공지 존재 | 첫 안전 로비에 모아보기 표시 |
| 같은 계정이 같은 presentationRevision 확인 | 재실행해도 반복 자동 표시하지 않음 |
| 새 공지/중요한 내용 개정 | 다음 안전 로비에 재노출 가능 |
| 단순 문구 교정 | revision만 증가, 자동 재노출 없음 |
| 로비 재진입·짧은 백그라운드 복귀 | 같은 세션에서 모달 반복하지 않음 |
| 공지 저장 실패/읽음 ACK 유실 | UI를 가두지 않음. 계정별 로컬 pending 읽음과 서버 upsert로 재시도 |
| 계정 교체 | 이전 계정 응답·읽음을 새 계정에 반영하지 않음 |
| 예약 전·만료·철회·대상 불일치 | 팝업 대상에서 제외 |

`NoticeReadState(accountId, environment/economyScope, noticeId, presentationRevision, acknowledgedAt)`를 서버에 idempotent upsert하고, 로컬 캐시는 사용자 경험 보완으로만 사용한다. 목록을 받았다는 이유로 모든 공지를 읽음 처리하지 않는다. 실제 표시한 항목의 확인을 기록하고, '모두 확인'은 명시 행동으로 둔다. 팝업 닫기는 아직 읽지 않은 항목을 강제로 모두 읽음 처리하지 않으며 해당 세션 재자동열기만 막는다.

일반 공지는 로비 공지 메뉴와 홈페이지에서 다시 읽을 수 있다. 웹에서 읽은 사실이 앱 팝업 확인인지 자동 추론하지 않는다. 추후 웹에서 '앱에서도 확인 처리'를 지원하려면 인증된 명시 행동으로 연결한다.

### 5.1 점검·업데이트는 별도 gate

점검 공지 본문을 등록했다고 게임 진입을 차단하지 않는다. 실제 점검/필수 업데이트 허용 여부는 기존 서버 admission이 판단한다. 로그인 이전에는 그 gate에 필요한 공개 요약/링크만 보여줄 수 있고, 전체 앱이 막혀도 공지를 조회할 비차단 경로를 둔다. 점검 운영 상태·배포 독립성·클라이언트/웹 화면·기존 작전/보상 보호의 전문은 [12 서비스 점검](12_SERVICE_MAINTENANCE.md)이 소유한다. 일반 팝업 성공을 로그인·업데이트·약관 승인으로 간주하지 않는다.

### 5.2 콘텐츠 안전·화면 요구

앱과 웹 모두 허용된 서식 요소만 렌더한다. 제목/본문/링크를 문자열 그대로 HTML·TMP rich text·스크립트로 실행하지 않는다. 원격 URL에 Bearer를 넘기지 않고, 링크는 허용된 HTTPS 목적지나 등록된 인앱 action만 사용자 클릭으로 실행한다. 이미지 실패 시 텍스트 본문은 읽을 수 있어야 한다.

모바일 세로 화면·safe area·큰 글자·긴 공지에서 스크롤과 확인 버튼 접근을 보장한다. 일반 공지 모달을 전투 중 새로 열어 시간·입력을 가로채지 않는다. 내용 철회 시 목록·상세·검색·공개 캐시 갱신을 처리하고, 영구 불변 URL도 무조건 공개 보존하지 않는다.

## 6. 논리 데이터·API 책임

운영 명령의 화면은 모두 [기존 Admin Console](#admin-operations)에 둔다. 앱·공개 홈페이지에는 공지 편집/게시나 광고 설정 권한을 노출하지 않는다.

아래는 신규 역할 정의이며 실제 기존 route/DTO를 확인해 합의한다. 문자열 경로를 임의로 구현 완료라고 표시하지 않는다.

| 논리 연산 | 권한/결과 |
|---|---|
| ReadRuntimePolicy | 승인된 앱/환경 문맥의 현재 광고 정책; 부트 결과 확장 또는 별도 read |
| SetAdsEnabled | Admin 설정 권한·expected revision·사유·키; 감사와 원결과 저장 |
| Create/UpdateNoticeDraft | 편집 권한, 충돌 확인, 아직 클라 비공개 |
| PreviewNotice | 대상 앱·언어·표면별 실제 미리보기; 비공개 접근 검증 |
| Publish/Schedule/WithdrawNotice | 게시 권한·revision·예약/철회 감사; 읽음 상태 임의 초기화 금지 |
| List/GetAppNotices | 서버가 문맥·기간·공개범위 필터; 목록/상세 동일 검증 |

## 7. 인수 기준 — 아직 실행하지 않은 요구사항

1. false/UNKNOWN/지원 없는 빌드에서 SDK 신규 초기화·로드·노출 0. 화면 숨김만이 아니라 서버 신규 승인도 차단.
2. 기본 수령·무료분·정상 작전은 광고 정책 실패와 독립. OFF를 무료 광고 시청으로 위조하지 않음.
3. 광고 시작 전후 OFF, 지연 SSV, 기본수령 경합, 승인 응답 유실에서 원결과 1회. 이미 열린 SDK 화면 처리 한계 표기.
4. 잘못된 환경 캐시·stale true·동의 중 정책변경·중복 관리자 변경·미지원 schema는 안전하게 광고 비활성.
5. 최초 데모 영구권 신규 판매 비활성 및 기존 ACTIVE의 OFF 룰렛/리롤 이용·복원/소유권 보존을 검증.
6. 공지 예약 경계·기간·버전·계정·언어 필터 일치. 비공개 공지의 직접 ID 조회·미리보기 URL 유출 차단.
7. 실제 화면 표시 뒤에만 해당 항목 확인. 재실행/계정전환/ACK 실패에도 중복·오인 최소화.
8. 공지 장애·이미지 실패·모달 중첩·웹 링크 실패가 로그인/전투/기본 보상을 막지 않음.
9. 점검 공지와 실제 점검 gate 분리. 개인정보·법적 동의 ACK를 일반 읽음으로 대체하지 않음.
10. 데모·광고 도입 전후 저장 승계와 공개 안내는 별도 확정. '데모' 표기로 정책·기능 검증을 생략하지 않음.

## 9. U9 점검 운영 연결

점검은 광고 OFF나 Notice type=MAINTENANCE 등록과 동일하지 않다. 기존 Admin에서 점검 정책을 설정하고 서버가 차단·복구 허용을 집행한다. 홈페이지·클라이언트는 허용된 공개 상태만 표시한다. 상세 필드/상태/감사/공개 snapshot은 [12](12_SERVICE_MAINTENANCE.md#admin-maintenance)에 둔다.

광고 OFF 자체는 §3의 유효 거래 복구를 막지 않는다. 별도 점검이 겹쳐 저장소가 사용할 수 없으면 [12](12_SERVICE_MAINTENANCE.md#recovery)대로 원요청/증빙을 보존해 복구를 지연하며, 접수되지 않은 거래를 성공으로 표시하지 않는다. 점검 해제는 adsEnabled를 true로 바꾸지 않는다.


## 10. J07~J10 결정 현황

J07 최신 정정: 카드(슬롯)마다 무료3회·추가1회를 제공한다. 미보유자는 ON에서 검증 광고 후 추가1회, OFF에는 추가 광고분이 없다. ACTIVE 구매자는 ON/OFF와 무관하게 상품 승인으로 해당 카드의 동일한 추가1회를 사용한다. 전문은 [05](05_AUGMENTS.md).

J08: 비보유자 BASIC_ONLY·보유자 정상혜택·첫데모 광고스킵 신규판매 숨김을 승인했다. UNKNOWN은 보유로 만들지 않고, 이미 승인된 원결과를 보존한다.

J09: 새 공지별 첫 안전 로비1회·중요 개정만 재알림을 승인했다. 공지읽음·점검승인·동의는 별개다.

J10: 기존 인증 활용·텍스트 커뮤니티·Admin 운영·DEV/PROD 격리 등 제시된 범위로 진행한다. 제시되지 않았던 보존기간·다른 IAP·공개데모 정식전환 세부는 [11](11_WEBSITE_COMMUNITY.md)의 승인 전 항목으로 구분한다.

## 문의 처리 권한 부여·회수 상세 v1 — 2026-10-01 / 승인 후보

목적: 기존 Admin 안에서 S-15의 SUPPORT_TICKET_PROCESS 부여/회수 운영 경계를 확정한다. 웹 회원 권한·재화 지급·게임 제재·다른 Admin 권한을 확대하지 않는다. 소스 canProcess는 ACTIVE OWNER/OPERATOR 및 명시 grant를 모두 요구한다. OWNER도 답변 권한이 자동 부여되지 않는다. 이번은 정책 초안이며 실제 관리 API 존재·구현 완료가 아니다.

### 추천 구조와 대안
역할만으로 전원 자동 부여하면 기존 명시 grant를 무너뜨린다. 모든 변경에 2인 승인을 강제하면 초기 소규모 운영에 불필요한 선행이 생긴다. **ACTIVE OWNER가 명시적으로 부여/회수하고 모든 변경을 감사하는 방식**을 추천한다. 처리 권한과 권한관리 권한을 분리한다.

### 권한표
| 주체 | 권한 관리 | 문의 답변/메모/상태 처리 |
|---|---|---|
| ACTIVE OWNER | 해당 환경의 부여/회수/조회 가능 | SUPPORT_TICKET_PROCESS 명시 grant 필요 |
| ACTIVE OPERATOR | 부여/회수 불가 | 명시 grant 필요 |
| VIEWER·중지/삭제 운영자 | 불가 | 불가 |

최초 OWNER 생성/복구는 기존 운영자 신원 등록 절차를 따른다. 이 화면은 OWNER 역할을 생성/승격하지 않는다. 기존 ACTIVE OWNER는 자신에게 처리 권한을 명시 부여할 수 있으며 사유·감사는 동일하게 남긴다. 이는 신규 추천이며 자동 self-grant가 아니다. 자기 처리 권한 회수도 허용하며 OWNER 권한관리 역할을 없애지 않는다.

### 화면·명령
기존 운영자 관리에 대상·역할/상태·현재 처리 권한·대상 환경·변경 사유·부여/회수 동작을 추가하는 안이다. 문의 본문을 이 목록에 노출하지 않는다. 요청은 대상 principal ID, permission, 환경, 기대 권한 버전, 원명령 키와 사유를 의미 계약으로 갖고 실제 필드/route는 Server가 기존 구조에 맞춘다. 유효 권한 대상만 선택, 전송 중 중복 차단, 성공 후 서버 재조회. 관리자 UI 숨김만으로 보호하지 않는다.

서버는 호출자 ACTIVE OWNER/환경·대상 실재/ACTIVE OWNER 또는 OPERATOR·허용 permission을 확인한다. 부여는 적격 대상만, 회수는 중지된 대상에 남은 grant도 정리 가능해야 한다. 변경과 감사는 원자적으로 확정하며 감사 실패를 성공 처리하지 않는다. 같은 키/같은 요청은 원결과, 다른 내용은 충돌. 기대 버전 충돌 시 최신 상태를 읽고 재검토한다. 동일 상태로 보내는 새 명령은 변경없음으로 반환하고 새 부여 효과를 만들지 않는다.

### 회수·역할 변경·진행 중 처리
회수와 문의 쓰기는 서버 커밋 순서로 판정한다. 회수 이전 완료된 답변은 보존, 회수 이후 권한 없는 새 쓰기는 변경0. 요청 시작 때만 검사한 뒤 권한 회수 후 저장되는 틈이 없어야 한다. 회수 이후 과거 원결과 조회도 현재 권한 검사에 따라 차단하며, 권한 없는 사용자에게 이력을 되돌려주지 않는다. 결과 불확실 건은 적격 운영자가 원감사/원명령 근거로 확인한다.

운영자 중지/삭제·VIEWER 전환 시 처리 grant를 원자적으로 무효화하고, 재활성화/OPERATOR 복귀만으로 자동 복원하지 않는 안을 추천한다. 남은 담당 문의는 원담당 이력을 보존하면서 다른 적격 운영자가 명시 재배정한다. 무조건 대량 자동 재배정하지 않는다. 상태만 바뀌었는데 old grant가 다시 살아나는 경로를 검증한다.

브라우저는 권한 회수 응답 후 편집·민감 초안을 제거하고 읽기 권한도 별도 확인한다. 권한은 환경별 독립이며 DEV grant를 운영 환경으로 복사하지 않는다. 세션 캐시가 서버의 현재 권한을 대신하지 않는다.

### 감사·검수·인수
감사는 호출자/대상 내부 ID·환경·원명령·이전/이후 권한·사유·서버 시각·결과를 포함한다. 문의 본문·토큰은 넣지 않는다. 기존 15의 승인된 권한 감사 분류/보존 정책을 재사용한다.

수용 사례: OWNER 명시 부여/회수, OPERATOR/VIEWER 거절, 중지 대상 부여 거절/회수 허용, 자기 명시 부여 감사, 역할 하향→복귀 자동 복원0, 동시 부여/회수 버전 충돌, 문의 저장과 회수 경합, 응답 유실 멱등, DEV/운영 격리, 감사 실패 시 변경0. 실제 시험 NOT_RUN.

승인 후 S-15의 기존 권한 관리 잔여로 인수한다. Admin A-02는 해당 실제 관리 계약/오류/검증 근거를 받은 뒤 소비하며 별도 백오피스나 중복 Server 작업을 만들지 않는다. 현재 후보는 OWNER 단독 명시 관리·자기 부여 허용·역할 하향 시 grant 무효화이며 승인 전 권한 변경/배포/실부여하지 않는다.

## OWNER 문의 처리 권한 관리 상세 v2 — 2026-10-01 / 승인용 설계

v1의 후보를 구체화한다. 사용자 요청은 상세 기획이며 실제 권한 부여/회수 또는 신규 정책 승인으로 해석하지 않는다. 권한명 SUPPORT_TICKET_PROCESS는 답변만이 아니라 현재 서버의 처리 상세 조회·답변·내부메모·상태·담당 변경 묶음이다. 화면에는 ‘문의 처리 권한’으로 표시하고 포함 범위를 설명한다. 기존 SUPPORT_READ 읽기 권한과 별개이며 이번에 둘을 합치지 않는다.

### 1. 운영 원칙
- 인증된 ACTIVE OWNER만 관리 가능. 문의 처리 grant 없이도 권한관리 가능하므로 초기 부여가 순환 대기에 빠지지 않는다.
- 대상은 같은 환경의 ACTIVE OWNER/OPERATOR. VIEWER는 부여 불가, 역할 승격은 이 화면에서 하지 않는다. 중지된 대상의 잔여 grant 회수는 가능하다.
- OWNER 본인에게도 명시 부여/회수 가능. 다른 OWNER의 처리 grant를 회수할 수 있지만 상대의 OWNER 관리 권한을 박탈하는 기능은 아니다. 따라서 상대 OWNER의 재부여까지 막아야 하는 상황은 별도 신원/역할 관리 절차로 처리한다.
- 최초 OWNER 등록·유실 복구는 기존 관리 절차를 사용하고 공개 회원을 OWNER로 만드는 API를 추가하지 않는다.
- 시간제 권한·자동 만료·일괄 부여·2인 결재는 초기 범위에서 제외한다. 권한은 명시 회수/자격 상실까지 유지하며 변경 내역은 감사한다.

### 2. 기존 Admin 내 화면
진입: 운영자 관리 → 운영자 상세 → ‘문의 처리 권한’. 실제 기존 메뉴 이름에 맞춰 통합하되 별도 백오피스는 만들지 않는다.

읽기 정보: 운영자 표시명/내부 식별자, OWNER/OPERATOR/VIEWER, ACTIVE 여부, 현재 접속 환경, 처리 권한 유무, 마지막 변경 시각·변경자·사유. 현재 상태와 과거 감사 이력을 분리한다. 권한을 관리할 수 없는 사용자에게 이 관리 API를 공개하지 않는다. 문의 본문은 표시하지 않는다.

동작은 토글 즉시 저장이 아니라 명시 버튼이다. 권한 없음이면 ‘권한 부여’, 있음이면 ‘권한 회수’를 제공한다. 클릭하면 동일 폼 안에 대상·환경·포함 작업·변경 사유·확정 버튼을 표시한다. 사유는 trim 후1~500자 신규 추천값이며 서버/화면 동일 검증을 사용한다. 취소하면 요청0. 저장 중 버튼 잠금, 중복 클릭은 같은 명령을 재사용한다.

본인 회수 시 ‘문의 답변·처리 기능을 사용할 수 없게 됩니다. OWNER의 권한 관리 기능은 유지됩니다.’를 표시한다. 마지막 처리자를 회수하면 ‘현재 처리 가능한 운영자가 없어집니다’ 안내만 제공하고 회수를 막지 않는다. 보안상 회수가 운영 인력 수에 막히지 않게 한다. 남은 처리자 수를 확인하지 못했으면 정확한 수를 추정하지 않는다.

### 3. 부여·회수 순서
**부여:** 최신 상태 조회 → 적격 대상 확인 → 사유 입력 → 확정 → 서버가 현재 호출자/대상/환경/기대 버전 검사 → grant·권한 개정·명령 결과·감사 원자 저장 → 원결과 반환 → 화면 최신 재조회.

**회수:** 최신 상태 조회 → 사유 입력 → 확정 → 같은 검증/원자 처리로 grant 비활성화 → 원결과 반환 → 대상의 이후 문의 처리 요청 거절. 이전 답변·담당 이력은 보존한다. 기존 SUPPORT_READ까지 회수하지 않으며 각 조회의 현재 권한을 별도로 검사한다.

**역할/상태 변경:** 중지·삭제·VIEWER 하향과 함께 처리 grant 무효화. 재활성화·OPERATOR 복귀 시 부여되지 않은 상태로 시작한다. ACTIVE OWNER↔OPERATOR 간 변경은 두 역할 모두 적격이므로 grant 유지 가능하며 OWNER 관리 권한은 현재 역할로 재평가한다. 이 원자 연결은 기존 운영자 변경 서비스에 맡긴다.

### 4. 명령·저장 의미 계약
실제 API 경로/필드명은 Server가 정한다. 필요한 의미는 대상 principalId, GRANT/REVOKE, 고정 permission, 기대 권한 revision, 사유, 멱등 키다. 환경은 신뢰된 서버 배포/인증 문맥에서 결정하고 요청 body의 환경만 믿어 다른 환경을 조작하지 않는다. 클라이언트는 현재 환경만 표시한다.

권한 상태의 revision은 부여→회수 뒤에도 남겨 재부여 때0으로 되돌리지 않는다. 다른 OWNER가 회수·재부여한 뒤 오래된 화면의 요청이 우연히 통과하지 않게 한다. 신규 대상은 정의된 초기 revision으로 시작한다. 같은 키·같은 요청은 현재 관리 권한 검사를 거쳐 원결과 반환, 다른 내용은 충돌. 동일 상태 새 명령은 NO_CHANGE로 결과를 보존하며 유효 권한 변경/변경 revision을 중복 생성하지 않는다. 실제 상태 전이는 revision+1.

검증 순서: 인증/현재 OWNER → 동일 키 원결과 확인 → 신규 명령 형식·대상·현재 자격·기대 revision → 현재 상태와 비교 → 원자 변경. 같은 키 replay는 후속 revision 변화가 있어도 원결과를 반환하지만 현재 권한 없는 호출자에게 과거 결과를 노출하지 않는다. 원결과 화면과 현재 상태를 구분하고 replay가 과거 권한을 다시 부여하지 않도록 한다.

0072_support_web_answers.sql에는 principal_id/permission/created_at만 있는 grant 테이블과 답변 INSERT 시 권한을 검사하는 trigger가 있다. 권한 revision·명령 원결과·관리 감사 이력의 실제 연결은 추가 인수가 필요하다. 기존 migration을 덮어쓰지 않고 호환 migration/서비스 경계를 설계한다. 기존 trigger/가드의 보호를 제거하지 않는다.

### 5. 실패·동시 처리
| 상황 | 처리 |
|---|---|
| 권한 부족/호출자 중지 | 변경0, 관리 화면 갱신/종료. 역할 캐시로 우회 금지 |
| 대상 없음·부여 부적격 | 변경0, 최신 대상 정보 재조회. 중지 대상 회수는 별도 허용 |
| 기대 revision 불일치 | 변경0, 변경된 권한을 보여 주고 사유를 재검토한 뒤 새 명령 |
| 응답 유실 | 원키·본문 고정 재시도. 권한 조회만으로 그 명령의 성공을 확정하지 않음 |
| 감사/저장 실패 | 전체 롤백, 성공 표시 없음 |
| 저장 성공 뒤 상세조회 실패 | 원명령 성공은 유지하고 ‘현재 상태 갱신 실패’ 표시. 새 변경 자동 전송 금지 |

권한 회수·답변 저장·역할 변경의 동시 실행은 서버의 원자 커밋 순서에 따라 선형화한다. 답변 저장이 먼저면 해당 답변 보존, 회수가 먼저면 답변 변경0. 호출자의 OWNER 자격도 커밋 시점까지 유효해야 한다. 요청 시작 시 권한 확인만 하는 구현은 불충분하다.

권한을 회수받은 브라우저의 기존 표시가 즉시 원격 삭제된다고 보장하지 않는다. 다음 접근/명령·화면 재활성화 시 현재 권한을 확인하고 권한 없음이면 편집/초안을 제거한다. 서버는 UI 갱신 이전에도 무권한 요청을 거절한다. 새 실시간 권한 push 시스템을 이 기획만으로 추가하지 않는다.

### 6. 기존 담당 문의와 감사
회수 후 담당 배정은 이력으로 유지한다. 문의 처리 능력이 있는 운영자는 상세에서 담당자를 적격 운영자로 명시 변경할 수 있다. 전체 문의 자동 재배정·자동 종료는 하지 않는다. OWNER가 직접 본문을 읽고 재배정하려면 처리 grant가 필요하다. 권한 관리 권한이 문의 내용 조회 우회가 되지 않게 한다.

### 6. Admin·권한·API
미리보기에는 사건/등급·기준시각·정책버전·대상/제외/보류 수·목표총량·기지급/추가지급·확인자 표시. 미리보기와 승인 사이 조건 변경은 서버 재검증, 중요한 변경은 새 미리보기 확인이 필요하다. 개발 모드·오류조사 READ/문의답변 권한은 일괄 경제 지급권한이 아니다.

## 주말·기념일·기간 한정 정기 이벤트 운영안 — 2026-10-19 / 신규 상세 제안
사용자 요구: 주말·기념일·기간 한정 이벤트를 정기 운영한다. 이 운영 방향은 사용자 지시이며 아래 일정·규모·보상/수용 규칙은 신규 제안. 기존 월간 출석28칸·50레벨패스·일일/주간 퀘스트를 대체하거나 중복 지급원장으로 복제하지 않는다. 실제 달력 등록/자동화/운영 활성화·실재화 지급 없음.

### 1. 운영 축과 권장 주기
| 축 | 제안 일정 | 역할/구성 |
|---|---|---|
| 주말 보급 이벤트 | 매주 금요일 KST04:00~월요일04:00, 72시간 | 기간 내 기본 플레이로 누적 달성, 매일 출석 강제 없음 |
| 월간 테마 이벤트 | 월1회, 본편14일 | 요원/열차/세계관 이야기와 특수 작전·누적 임무 |
| 기념일 이벤트 | 출시/반주년/주년·선정 명절, 7~14일 | 큰 선물+누적 임무, 해당월 테마 자리를 사용 가능 |
| 업데이트 기간 한정 | 신규 콘텐츠와 함께 7~14일 | 체험·적응 지원, 별도 숙제 추가 대신 테마에 통합 |
이벤트 기간은 서버의 고정 시작/종료 시각 반개구간으로 판정. 기념일 실제 날짜는 출시일/운영 달력 확정 후 지정하며 임의 출시일을 만들지 않는다. 금요일 이전 사전 안내를 준비하되 실제 자동 공지 발행/반복 스케줄은 별도 실행 승인이다.

### 2. 겹침과 쉬는 구간
숙제가 있는 한정 메인 이벤트는 동시에1개, 주말 경량 이벤트를 더해 최대2개 제안. 무조건 한정배너 수를 늘리지 않는다. 보상 수령만 남은 항목과 신규/복귀 개인 일정은 별도 표시하되 기존 기능 지원 확인 전 구현을 가정하지 않는다.
기념일 메인이 열리면 월간 테마를 기념일로 대체/통합하고, 업데이트 임무도 같은 누적 목표에 합친다. 한달 내 나머지 기간은 기존 성장/다음 준비 구간으로 두어 연속 완주 압박을 줄인다.
4주 예시: 1~2주 월간 테마+주말, 3~4주 주말 경량+기존 성장. 주년월은 월간테마 자리에 주년 이벤트. 실제31일/5번째주말을 4주표로 삭제하지 않으며 월별 서버 캘린더가 기준이다.

### 3. 플레이 구성
주말은 기존 적법 작전/전투 완료 기록으로 누적하는 보급 임무. 초기 예시는 유효 작전1/2/3회 달성이며 '유효 완료'의 실제 모드/생산자/판정 매핑과 요구 횟수는 개별 이벤트 상세에서 확정한다. 접속 시간대별 보상·하루마다 초기화되는 핵심 임무는 기본으로 두지 않는다. 하루에 몰아서 해도 기간 내 누적 인정.
테마는 이야기+전투에서 선택이 바뀌는 특수 규칙+누적 보상의 구성. 예시는 이미 지원된 보호/관통/다중발사 등에 맞춰 우선표적·요원 구성·스킬 타이밍 선택을 바꾸는 시험 작전. 단순 적HP/보상배수 증가만으로 콘텐츠 변화라고 하지 않는다. 실제 조작과 효과 연결이 없는 시안은 playable완료로 취급하지 않는다.
특정 뽑기 요원 보유/유료 구매/광고를 기본 보상 필수 조건으로 하지 않는다. 필요한 전용요원 체험은 대여 기능·소유권/수명 계약이 검증된 뒤 사용, 지금 존재한다고 가정하지 않는다.
시작 직후 기간 종료로 핵심 보상을 못 받는 late join 부담은 누적형/낮은 핵심 문턱으로 줄인다. 개인별 기간 연장이나 무제한 몰아치기 면제 규칙은 자동 추가하지 않는다.

### 4. 보상 원칙과 경제
FREE 크리스탈·기존 성장재화·기념 외형 등 명확한 보상을 사용하며 핵심 보상을 끝부분에만 몰지 않는다. 큰 기념일은 초반 선물과 누적 보상을 함께 제안한다. 기본 보상은 신규/낮은성장 계정도 실제 지원 경로로 도달 가능하게 목표/난도를 검수하고 선택 도전은 기존순위정책과 충돌 없이 명예/외형 중심으로 설계한다.
구체 지급량은 다음 주말/테마 보상표에서 별도 제안한다. 이번 문서로 임의 이벤트 전용재화·교환상점·새뽑기권ID/풀·무료뽑기 기능을 발행하지 않는다.
월발행은 주말 실제횟수×1인 주말 최대보상 +월간테마 +기념일/업데이트의 실제추가분 +기존출석/패스/퀘스트로 산정. 통합으로 대체한 이벤트를 다시 더하지 않는다. 전원 버그보상은 예외발행으로 별도 추적하며 이벤트 예산을 이유로 기승인 버그보상을 깎지 않는다. 풍성한 보상과 실제 발행량 검증을 구분한다.

### 5. 화면·데이터·종료
로비의 기존 이벤트 진입 영역에 현재 참여 가능/남은 기간/받을 보상/진행도를 간결하게 표시. 이벤트마다 강제 팝업을 누적하지 않고 기존 안전로비 공지 정책을 따른다. 개발 진단은 dev전용, 일반 화면에 eventId/API/메모리 상태 미노출.
기존 명령의 확정 실적과 이벤트 진행을 같은 권위 원천으로 연결한다. 화면 열기 위해 실적을 재전송하거나 게임클라 카운터로 보상을 판정하지 않는다. 초기 응답/관련 명령 응답이 충분하면 재사용, 계정/이벤트 버전 변경·새기간·실무효화 때만 필요한 범위 취득.
종료 직전 START/종료 후FINISH 인정 기준, 수령 마감/미수령 처리, 점검연장·취소는 이벤트별 고정 계약이 필요하다. 기존 패스 자동정산/퀘스트14일우편을 모든 이벤트에 임의 적용하지 않는다. 추천 방향은 이미 달성한 확정 보상을 놓치지 않게 종료 정산하는 방식이나 상세 승인 전 확정 지급 계약으로 사용하지 않는다.
진행run에 영향을 주는 규칙/보상 version은 START핀/기존 명령 시점 계약을 따른다. 운영자가 중간에 값을 바꿔 이미 수락된 작전/권리를 뒤집지 않는다.

### 6. 운영·검수·다음 상세
기존 Admin에서 초안→일정/대상·보상/충돌 확인→DEV 검증→게시/활성화 승인. 별도STG를 새로 만들지 않는다. 실제 PRD활성화/반복 자동화는 기획 승인만으로 실행하지 않는다. 매 회차 고유권리/기간·정책버전, 이전회차receipt 보존·중복지급 방지 필요.
검수: 4/5주말 달력·KST경계·중복로그인/명령·오프라인 복귀·시작전/종료후·늦은가입·기념일겹침·기존패스/퀘스트 동시달성·미지원모드·실수령/정산·점검/연장/중지·새버전 도중진행·API/메모리.
후속순서 제안: (1) 주말 보급 이벤트 임무/보상/정산 상세 (2) 월간 테마 콘텐츠와 보상 (3) 기념일 선물/전체계정 기준 (4) 공통 일정·중단/연장·미수령 계약. 실제 보상표/생산자 계약이 준비되기 전 실행큐 선등록 없음. 이번은 기획 저장, 코드/이벤트 발행/자동화 없음.

## 기간 한정 이벤트 통합 방향 — 2026-10-19 사용자 정정
사용자 명시: 주말 이벤트는 제외하고 2~4주 기간 한정 이벤트를 기념일과 합치는 구성. 이 절이 #recurring-live-events-framework-proposal-20261019의 주말 정기 운영/월간14일고정/주말병행/주말상세 우선순위를 대체한다. 이전안은 역사자료이며 신규 적용하지 않는다.
