<a id="source-1d27b6aa289834f7-원칙"></a>
#### 원칙

- 독립적으로 교체·크기조절·상태제어해야 하는 요소는 별도 렌더 요소/데이터 바인딩으로 조합한다. 한 요소를 바꾸기 위해 다른 요소의 그림을 다시 생성해서는 안 된다.
- 프레임 자산은 투명 캔버스 위 프레임만 포함한다. 프레임 안쪽·바깥쪽 빈 영역은 실제 alpha이며 체크무늬를 그림으로 굽지 않는다. 금속에 고정된 마모/나사/재질은 프레임에 포함 가능하다. 별도 교체할 내부 판·배경·인물·아이콘·동적 발광은 프레임에서 분리한다.
- 독립 요소라는 것은 각각 별도 Canvas가 필요하다는 뜻이 아니다. 공통 Canvas 아래 자식 오브젝트/컴포넌트로 조합한다. 스프라이트 아틀라스와 공통 재질도 개별 영역/상태가 분리되면 사용 가능하다. 절차적 프레임/게이지 역시 독립 렌더 요소이면 허용한다.
- 마스크, 레이아웃, 입력, 상태 바인딩을 구분한다. 장식은 클릭을 가로채지 않으며 버튼의 터치 영역은 그림 크기와 별도로 관리한다.

### 모든 프로젝트 공통: 객체지향 설계·독립 리소스 제작·검수 규칙

사용자 공통 지침 / 2026-09-14. 코드 설계 기준은 신규/기존 소프트웨어 프로젝트에, 리소스 기준은 UI와 시각 리소스를 제작하는 프로젝트에 적용한다. 특정 프로젝트의 화풍·캐릭터·경로·승인 시안은 다른 프로젝트에 이식하지 않는다.

<a id="source-ebd69050958b1d99-객체지향-코드-설계"></a>
#### 객체지향 코드 설계

1. 객체지향 설계를 기본으로 책임·상태 소유권·의존 관계를 먼저 정의한다. 클래스/컴포넌트는 응집된 책임을 맡고, 한 객체에 화면 생성·입력·업무 규칙·저장·통신을 몰아넣지 않는다. 파일만 나누거나 partial class로 옮기는 것은 책임 분리가 아니다.
2. 도메인 상태와 규칙, 사용자 입력/유스케이스 조정, 화면 표현, 저장/네트워크 등 외부 연동을 구분한다. UI는 명령을 전달하고 상태를 표시하며 권한 검증·게임 판정·영속 저장을 직접 소유하지 않는다.
3. 상태는 소유 객체가 캡슐화하고 유효한 변경 경로를 제공한다. 외부에서 공유 가변 필드나 컬렉션을 임의 수정하지 않도록 한다. 편의를 위한 전역 가변 상태/거대 싱글턴을 기본 구조로 삼지 않는다.
4. 상속보다 조합을 우선한다. 상속은 실제 대체 가능한 관계가 있을 때만 사용하고, 코드 재사용만을 위해 깊은 상속 계층을 만들지 않는다.
5. 교체·테스트·외부 연동 경계에는 작고 명확한 인터페이스를 두고 의존성을 명시적으로 전달한다. 구현마다 무조건 인터페이스/팩토리/서비스 계층을 추가하지 않는다. 이벤트 구독·자원 해제·객체 수명도 소유자가 관리한다.
6. 프레임·초상화·게이지 등 UI 구성 요소는 독립된 데이터 입력과 표현 책임을 갖고 상위 화면에서 조합한다. 시각 요소별로 반드시 별도 클래스/파일/Canvas가 필요한 것은 아니며 독립 제어와 책임 경계가 기준이다.
7. 언어·프레임워크 관례를 존중한다. React 함수 컴포넌트, 순수 계산 함수, 데이터 지향 구조도 위 책임 분리·캡슐화 원칙을 만족하면 사용한다. 객체지향을 이유로 모든 코드를 class로 변환하지 않는다.
8. 변경하는 범위에서 의존성과 상태 전이를 검토하고 핵심 규칙·외부 경계·동작 보존을 적절히 검증한다. 새 기능과 무관한 전체 재작성은 하지 않는다. 기존 위반은 근거와 개선 대상으로 기록하고 승인된 작업 범위에서 단계적으로 개선한다.

<a id="source-ebd69050958b1d99-mvc-및-콜백이벤트-바인딩"></a>
#### MVC 및 콜백·이벤트 바인딩

2026-09-14 사용자 명시: UI는 MVC 패턴을 기본으로 하고, 하위 객체에 상위의 처리 코드를 복제하지 말고 콜백·이벤트로 기존 처리에 연결한다.

1. Model은 상태와 업무 규칙을, View는 표시와 사용자 입력 의도 전달을, Controller는 입력 해석·유스케이스 호출·화면 흐름 조정을 담당한다. View는 Model의 상태/변경 통지 또는 명시적으로 전달된 표시 데이터를 바탕으로 갱신한다. Controller가 도메인 규칙까지 전부 소유하는 거대 객체가 되지 않도록 한다.
2. 상위 객체가 하위 View를 알고 있고 이미 필요한 처리 기능을 소유하거나 조정한다면, 하위 View가 콜백/이벤트를 제공하고 상위 Controller가 기존 처리 메서드를 바인딩한다. 같은 동작을 하위에 다시 구현하지 않는다. 하위는 구체적인 상위 객체를 검색하거나 전역 객체를 통해 우회 호출하지 않는다.
3. 기본 흐름은 하위 View 입력 → 콜백/이벤트 → Controller의 기존 처리 → Model/Service → View 상태 갱신이다. View 내부의 순수 표시·입력 정규화는 허용하되 게임 판정·저장·통신 같은 실행 책임과 구분한다. 표시 갱신이 다시 사용자 명령을 발생시키지 않게 한다.
4. Bind/Unbind 또는 프레임워크에 맞는 동등한 등록/해제 계약을 명시한다. 재바인딩 시 중복 구독을 막고, 교체·비활성화·파괴·풀 반환 등 실제 수명에 맞춰 소유한 구독만 해제한다. 다른 소비자의 리스너까지 일괄 제거하지 않는다. 비동기 처리는 해제 이후 갱신을 막고 필요한 취소·스레드 전환을 관리한다.
5. 단일 동작 위임에는 콜백, 여러 소비자의 상태 통지에는 이벤트 등 목적에 맞는 계약을 사용한다. 전역 이벤트 버스나 모든 요소별 별도 클래스를 의무화하지 않는다. React 등의 함수형 관례에서도 동일한 MVC 책임과 외부 핸들러 연결 원칙을 유지한다.
6. 해당 코드를 변경할 때 입력 한 번에 처리 한 번, 재바인딩 중복 없음, 해제 후 호출 없음, 기존 처리 재사용을 확인한다. 기존 코드 전체의 준수를 문서 등록만으로 주장하지 말고, 위반은 근거를 기록해 승인된 범위에서 개선한다.

#### 코드 유지보수·관리

2026-09-14 사용자 승인: 다음 항목은 제안이 아닌 프로젝트 공통 적용 규칙이다.

1. **상태 소유자는 하나로 정한다.** 동일한 의미의 상태는 권위 있는 소유 객체에서 변경한다. UI 표시값·캐시·네트워크 복제본은 원본과 갱신 경로를 명시하고 독립된 진실로 취급하지 않는다.
2. **같은 규칙은 한곳에서 처리한다.** 버튼·드래그·단축키 등 같은 기능의 입력은 동일한 명령/유스케이스로 연결한다. 입력별로 업무 조건과 실행 코드를 복제하지 않는다. 클라이언트 표시용 검사와 서버 권한 검증처럼 서로 다른 신뢰 경계의 필수 검증은 유지한다.
3. **의존 방향을 고정한다.** 도메인은 UI나 구체적인 외부 연동 구현에 의존하지 않으며, View는 도메인 실행 구현 대신 정해진 표시/입력 계약을 사용한다. 순환 참조를 피하고 의존성을 명시적으로 전달한다.
4. **자원 수명에 책임자를 둔다.** 이벤트·타이머·비동기 작업·리소스·풀 객체는 생성/획득한 쪽이 해제·취소·반환을 관리한다. 소유권을 넘길 때는 계약을 명시하며 빌려 쓴 객체를 임의 해제하지 않는다. 화면 종료 뒤 작업이나 구독이 남지 않도록 한다.
5. **상태 전이를 명시한다.** 준비·실행·일시정지·종료 등 배타적인 상태는 허용 전이와 실패/취소 경로를 정의한다. 서로 충돌하는 bool 조합을 계속 추가하지 않는다. 단순하거나 독립적인 상태에 불필요한 상태 머신을 강제하지 않는다.
6. **설정과 실행 코드를 분리한다.** 밸런스 수치·문구·리소스 식별자 등 변경 가능한 설정은 목적에 맞는 데이터로 관리한다. 반복되는 의미 있는 상수는 명명하고 여러 코드에 흩어진 숫자·문자열을 정리한다. 모든 리터럴을 설정 파일로 옮기지는 않는다.

11. **추측으로 공통화하지 않는다.** 재사용 가능성만으로 추상화하지 말고 의미와 변경 이유가 같은 코드인지 확인한다. 공통화로 무관한 기능의 결합이 커지면 분리하며, 기존의 올바른 공통 처리는 재사용한다.

#### 핵심 정의

**플레이어는 증강을 선택해 단지 강해지는 것이 아니라, 열차와 요원을 운용하는 방식을 바꾼다. 선택이 쌓이면 같은 편성·같은 적·같은 맵에서도 다른 판단과 전투 흐름이 만들어져야 한다.**

기본 전투는 증강 없이도 이해하고 조작할 수 있어야 한다. 증강은 정상 플레이에 필요한 기능의 잠금 해제가 아니라 새로운 해법을 제공한다. 영구 성장·장비의 수치 성장까지 없앤다는 뜻은 아니다. 증강의 정체성을 수치 성장으로 대체하지 않는다는 기준이다.

<a id="source-9b8fb18db0c66c5c-설계-원칙"></a>
#### 설계 원칙

1. **핵심 규칙이 바뀐다.** 공격 패턴·대상 분배·준비와 방출·회복과 보호·궁극기 순서 등 적어도 하나가 바뀌어야 한다. 조건을 붙인 피해 증가만으로는 부족하다.
2. **플레이어가 의도적으로 활용한다.** 기존 속도/표적/지원/궁극기 조작 또는 준비 단계의 편성 선택으로 새로운 운영을 선택할 수 있어야 한다. 자동 발동 자체를 금지하지 않지만 자동으로 보너스가 붙을 뿐 선택이 달라지지 않으면 탈락이다.
3. **강한 순간과 선택의 대가가 있다.** 특정 상황의 판세를 바꿀 만큼 효과가 분명해야 한다. 대가는 무조건 능력치 감소가 아니라 준비시간·표적 고정·다른 기회 포기 등으로 성립할 수 있다. 과도한 상한/후딜로 파급력을 다시 지우지 않는다.
4. **반복 가능한 운영을 만든다.** 한 번의 작은 추가타보다 이후 교전에서 계속 사용하게 되는 행동 흐름이 중요하다. 드문 파손/장애물 전용 증강은 해당 콘텐츠가 충분히 등장해야 하고 그렇지 않으면 무효 후보가 된다.
5. **조합이 다음 판단을 바꾼다.** 먼저 얻은 증강의 준비/방출/표적/보호를 다음 증강이 다른 용도로 활용하도록 설계한다. 단순 곱연산뿐인 조합과 상호 무효화는 피한다. 기능 중복을 이유로 배타 그룹을 늘리기 전에 합성 동작을 검토한다.
6. **복잡도와 재미를 혼동하지 않는다.** 상태/버튼/설명만 늘어나거나 의미 없는 입력 반복을 요구하면 실패다. 카드 핵심문구에서 변화와 대가를 짧게 이해할 수 있어야 한다. 효과 준비와 결과는 실제 전투 화면에서 보여야 한다.
7. **정해진 빌드를 강요하지 않는다.** 첫 증강 하나로 이후 선택을 강제하지 않는다. 적격 후보는 동일 가중치이고 추천 표시/조합 우대 추첨은 없다. 조합을 발견하는 재미를 시스템의 추천이나 숨은 확률로 대신하지 않는다.
8. **맵과 적이 변화에 응답한다.** 범위 공격에는 무리와 단일 강적, 속도 운영에는 노출과 장애물, 선제 보호에는 예고 공격처럼 다른 해법을 쓸 상황이 필요하다. 특정 증강이 없으면 통과 불가한 필수 기믹이나 선택 직후 불리하게 바뀌는 맵을 만들지 않는다.

<a id="source-9b8fb18db0c66c5c-증강별-필수-명세와-통과-조건"></a>
#### 증강별 필수 명세와 통과 조건

모든 카드에 다음을 기록한다: 기존 운영 → 변경 규칙 → 플레이어가 바꿀 행동 → 반복 흐름 → 강한 상황 → 포기하는 기회 → 조합 변화 → 실제 화면 피드백 → 필요한 런타임 계약 → 비교 검증 결과.

예: ‘기동 사격’은 고속 장전/저속 방출을 실제로 제공해야 한다. 고속에서 카운터만 쌓고 다음 공격 피해만 조금 늘어나면 이름과 설명이 같아도 요구를 충족하지 않는다.

검수 단계는 분리한다.

- **철학 확정:** 사용자 승인된 본 문서.
- **설계 후보:** 규칙과 운영 변화는 설명됐지만 아직 실전 검증 전. 현재 16종 재설계안은 이 단계다.
- **구조 검증:** 실제 기존 입력으로 변형 동작이 수행되고 원인/준비/소비/조합을 재현함.
- **플레이 검증:** 같은 조건의 비교 플레이에서 이전과 다른 의사결정과 유효한 해법을 확인함.
- **출고 가능:** 상태 복원·입력·성능·시각 피드백·밸런스 검증까지 수행함.

문서 작성, 테스트 통과, 높은 총 피해만으로 플레이스타일 기준 통과를 선언하지 않는다. 세부 설계에서 좋은 운영 흐름을 설명해도 실제 게임에서 조작/표적/위험이 이를 지원하지 않으면 미완성이다.

<a id="source-9b8fb18db0c66c5c-조합-예시--검증할-방향-확정-밸런스-아님"></a>
#### 조합 예시 — 검증할 방향, 확정 밸런스 아님

| 운영 | 단일 효과의 의미 | 조합으로 생길 다음 판단 |
|---|---|---|
| 이동 장전 | 달려서 준비한 화력을 감속해 방출 | 후방 엄호와 조합해 달리는 동안 뒤를 억제하고 전방 화력 전환 지점 선택 |
| 방어를 공격으로 | 적 포격을 받아 반격 또는 남은 방어를 방출 | 방어막을 끝까지 버틸지 도중 공격으로 바꿀지, 두 효과 중 실행 경로 선택 |
| 분산 지휘 | 한 요원이 표식 적을 유지하고 나머지 표적 전환 | 분대 추격 일제와 조합해 강적 묶기/잡몹 집중을 교대 |
| 궁극기 운용 | 보류 변형 또는 단독 돌파로 시전 목적 변경 | 연계 시전으로 돌파를 끝내고 다음 국면으로 넘어갈 시점 결정 |

이 예시는 미리 정해진 빌드 선택 화면이나 전용 확률을 추가하지 않는다. 핵심 운영이 실제로 성립하는지를 시험하기 위한 조합이다.

<a id="source-9b8fb18db0c66c5c-현재-재설계안의-남은-핵심-위험"></a>
#### 현재 재설계안의 남은 핵심 위험

- T03 정비 우선: 객차가 자주 파손되지 않으면 체감이 희박하다. 기본 복구/파손 빈도와 함께 검증 필요.
- T04 포대 사냥꾼: 결국 같은 적을 오래 때리는 것만 남을 수 있다. 조준 중 사격 중단과 취약 시간의 지원 집중이 실제 선택인지 확인 필요.
- O01 연계 지휘/O06 전력 보류: 궁극기 유형별 변환 매핑 없이는 포괄적인 문구에 불과하다. 실사용 요원별 효과표가 우선이다.
- O05 응급 전술: 적의 공격 대상과 타이밍을 읽을 수 없으면 우연 발동으로 돌아간다. 전투 예고와 치료 대상 정책 검증 필요.
- O07 추격 명령: 정상 공격을 묶기만 해서 총 손해가 되거나 지연만 생기면 실패다. 순간 화력 집중의 실제 가치와 입력 반응을 검증해야 한다.
- 패턴 변경 증강 간 배타는 임시 설계일 뿐 확정 정책이 아니다. 통합16종 풀의 선택 폭을 과도하게 줄이지 않도록 합성 패턴을 먼저 검토한다.

<a id="source-c42b52f9d3a9059a-전수-검수-기준"></a>
#### 전수 검수 기준

<a id="source-c42b52f9d3a9059a-시안-기준과-작업-순서--사용자-범위-정정"></a>
##### 시안 기준과 작업 순서 — 사용자 범위 정정

- 전투 화면의 구성/독립 요소 명세는 최신 승인된 [**1인용 3차 최종시안**](51_UI_ART_DETAIL_CONTRACTS.md#source-61f16f3947c254bb)을 기준으로 하나만 작성한다. 1차·2차와 미채택 전투 후보를 별개의 구현 대상으로 만들지 않는다. 1차는 이미 지정된 초상화·캐릭터·재질 품질 참고를 유지하고, 2차의 계승 조작 형태는 3차 승인 범위에 따라 사용한다. 2인용 화면은 별도 기획·승인 상태를 기록한다.
- 다른 화면은 화면별 최신 확정 시안의 근거 경로/승인 상태를 먼저 기록하고 해당 시안에서 독립 요소를 정의한다. 최신 확정본을 찾지 못한 화면은 NEEDS_REFERENCE로 남기며 임의의 후보를 최종본으로 간주하지 않는다.
- 순서는 시안 식별 → 필요한 요소/분리·조합 명세 작성 → 실제 리소스와 참조 대조 → 위반/누락 목록 → 필요한 수정과 재검증이다. 실제 파일이 있는 것에 맞춰 필요한 요소를 생략하지 않는다.
- 이전/미채택 시안과 보관 리소스도 목록과 용도를 유지하지만 중복 구현 정책을 생성하지 않는다. 리소스 전수 범위는 유지하며 활성 시안과의 대응 여부 또는 reference-only 등 분류로 기록한다.
- 요소별 판정은 존재·독립 연결됨 / 존재하나 합성됨 / 존재하나 미연결 / 누락 / 미확인으로 구분한다. 파일 단위 전수 목록과 시안별 요소 목록을 연결해 고아 자산과 필요한데 없는 요소를 모두 찾는다.

1. 전체 D 프로젝트에서 리소스와 참조 컨테이너를 목록화한다. runtime, 제작 source/candidate, reference/QA capture, historical backup, third-party/generated dependency를 구분하고 누락/제외 근거를 기록한다. 라이브러리 파일을 자체 UI 원화로 오인하거나 기록에서 조용히 제외하지 않는다.
2. 자산별 경로·형식·크기·해시·역할·사용 위치·참조·분리 상태·alpha 필요/실제 여부·판정·근거·수정 담당을 기록한다. 동일 해시 중복은 내용 검수를 공유할 수 있으나 모든 경로/사용 맥락을 남긴다.
3. 프레임은 실제 투명 영역과 프레임만, 인물과 초상화 배경은 분리, 이름/HP/게이지/수치/아이콘/동적 상태는 독립이다. 단순 파일 분할뿐 아니라 실제 조립과 데이터 바인딩도 검수한다. 절차적 graphics/atlas/shared Canvas는 독립 제어가 되면 허용한다.
4. 고정 재질의 마모/장식은 해당 물체 일부일 수 있다. 배경 풍경 자체, 오디오 클립, 폰트, 메시를 의미 없이 잘게 나눌 필요는 없다. 각 역할에 맞게 판정하며 비UI 자산을 누락하지 않는다. 동적 actor/체력바/선택 상태를 배경 원화에 굽는 것은 금지한다.
5. 완성 시안/스크린샷/영상/불변 백업의 합성은 기록 목적에 적합할 수 있으나 runtime 적합 PASS가 아니다. reference-only 또는 historical-preserved로 판정하고 런타임 재사용을 막는다. 원본 덮어쓰기/삭제는 하지 않는다.
6. 상태는 UNREVIEWED, NEEDS_CONTEXT, COMPLIANT, NONCOMPLIANT, REFERENCE_ONLY, THIRD_PARTY, HISTORICAL_PRESERVED 등으로 구분한다. 파일명·alpha 채널 존재·테스트 통과만으로 COMPLIANT를 부여하지 않는다. 독립 요소 단독 표시/교체/값 변화와 실제 조합 증거가 필요하다.
7. 전수 목록 생성, 자동 검사, 실제 이미지/원본 검사, 참조/구조 검사, 수정, 재검증은 각각 별도 진행률이다. 자동 스캔 완료를 전수 품질 검수 완료라고 보고하지 않는다.

현재 사용자 지시는 전수 검수와 전역 정책 적용이다. 위반 자산 수정은 기존 승인 구역과 영향에 맞춰 순차 진행하며, 검사 때문에 기존 미커밋 작업이나 역사 자료를 덮어쓰지 않는다. 새 제작부터 즉시 이 규칙을 적용한다.

## 기존 정보 재사용·데이터 갱신 공통 규칙 — 2026-10-19 사용자 승인
사용자가 데이터 처리 전반에 적용하도록 명시한 공통 기준이다. 신규 설계와 승인된 변경 범위에서 적용하고 무관한 기존 시스템 전체 재작성 권한으로 확대하지 않는다.
1. **먼저 실제 원천과 소유자를 확인한다.** 화면에 필요한 각 값의 최초 공급, 권위 있는 상태 소유자, 유효 범위(계정/세션/작업·run/버전), 변경 경로를 추적한다. 이미 응답·메모리·저장 상태에 있는 정보를 새 API가 필요하다고 추측하지 않는다.
2. **유효한 기존 정보는 즉시 재사용한다.** 화면 열기·탭 이동·상세 보기·닫기·왕복 자체를 재조회 사유로 삼지 않는다. 최초 정보 부재, 명시적 갱신, 계정/작업 전환, 관련 상태 변경·버전 불연속, 권한 변화·결과 불명확 등 실제 무효화 사유가 있을 때 필요한 범위만 취득한다. 민감도·도메인 계약에 따른 최신성 요건을 무시하거나 임의 공통 TTL/상시 폴링으로 대체하지 않는다.
3. **확정 명령의 응답으로 갱신을 완결한다.** 명령 성공 응답에 해당 화면과 상태 소유자가 필요한 확정 결과·변경 후 값 또는 검증 가능한 변경분·영수증·소유자별 버전을 포함하도록 설계한다. 충분한 성공 응답을 받은 직후 같은 결과를 GET으로 다시 확인하는 중복 흐름은 피한다. 부족한 필드와 별도 판정 경계를 먼저 확인하며 모든 응답을 계정 전체 덤프로 만들거나 서로 다른 권한·거래를 무리하게 합치지 않는다.
4. **표시 재사용과 실행 권한 검증은 분리한다.** 클라이언트 메모리는 서버 권한을 대체하지 않는다. 변경·지급·입장 등은 서버/권위 소유자가 실제 원본으로 검증하고 필요한 원자성·멱등성을 유지한다. GET을 다시 했다는 사실 자체를 위변조 방지로 간주하지 않는다. 미리보기/선택 확정/실제 효과 적용/지급 완료는 각각 실제 단계로 구분한다.
5. **상태를 한 곳에서 일관되게 반영한다.** View는 기존 Controller의 명령과 소유 Model의 표시/통지를 사용한다. 성공 시 관련 소유자에게 최종 상태를 일관되게 반영한 뒤 통지하며 화면마다 재계산·임의 가산·복제 원장을 만들지 않는다. 부분 갱신과 전체 대체, 삭제와 미공급을 구분하고 누락을 0/빈 목록으로 처리하지 않는다.
6. **버전·경합·복구를 보존한다.** 중복/역순/오래된 응답이 최신 상태를 되돌리거나 효과·소비·지급을 중복 실행하지 않게 한다. 결과 불명확은 실패 확정이 아니며 원요청·원키로 복구한다. 정상 후속 조회를 줄여도 재접속·응답 유실·버전 충돌·권한 재확인 등에 필요한 조회와 명령은 유지한다. 계정/작업/화면 세대가 바뀐 뒤의 응답과 구독을 격리한다.
7. **필요한 데이터만 소유하고 수명을 관리한다.** 정적 정의·공유 자산은 ID/버전으로 재사용하고 필요한 동적 상태만 전달한다. 전체 응답 JSON·목록·이미지를 화면마다 복제하거나 과거 응답을 메모리에 무한 보관하지 않는다. 임시 버퍼/파싱 객체/콜백은 사용 후 참조를 해제하되 필요한 불변 원본·복구 영수증·저장 정책은 보존한다. 필요한 복사·불변 snapshot을 무조건 제거하지 않는다.
8. **효과는 실제 경로로 검증한다.** 동일 조건에서 외부 API/내부 호출·정상/복구·논리 요청/재시도를 구분해 전후 횟수를 측정한다. 데이터 일치·권한·동시성·재진입을 함께 확인한다. 상주/순간 최대/누적 할당/반복 후 잔류 메모리와 리소스 사용량을 구분하며 API 감소를 메모리·서버비용 감소로 환산하지 않는다. 이론값·실측·미검증을 명시한다.
후속 작업 프롬프트와 인계에는 이 절의 원문 경로 및 필요한 데이터 원천·소유자·무효화·응답/복구 계약을 포함한다. 문서 저장과 현재 다른 세션의 재독·다른 기기/프로필 적용은 구분하며 자동 동기화나 기존 코드 전체 준수를 주장하지 않는다.

## 원격 리소스 공급·메모리 수명 — 2026-11-11 사용자 확정
제품 리소스는 최초 인터넷 연결 없이 보여야 하는 시작/네트워크 오류/재시도/다운로드 동의·진행 안내 UI와 그 최소 폰트·재질·이미지 의존성만 로컬에 포함한다. 그 외 게임 화면·아이콘·인물·배경·효과·오디오 등 콘텐츠는 승인된 원격 Addressables에서 다운로드한다. 코드/플러그인/플랫폼 필수 실행 데이터와 리소스 콘텐츠를 구분하며 Editor 로컬 자산 모드는 개발 전용이다. 과거 Resources/직접 직렬화 참조는 자동 예외로 인정하지 않는다.
- 서버는 콘텐츠 승인 버전·카탈로그 주소/hash 및 도메인별 안정 키를 공급한다. 클라이언트 키 사전은 승인된 주소·영역 metadata만 보관하며 서버 문자열을 임의 파일/URL로 실행하지 않는다.
- 기존 승인 카탈로그/인증/다운로드 코디네이터를 사용한다. 최초 준비에는 launch_required 의존 번들을 디스크 캐시에 받되 모든 Texture/Audio/Prefab를 메모리에 미리 로드하지 않는다. 유효한 동일 bundle hash는 재사용한다. 비필수 콘텐츠도 원격 공급하며 실제 필요 전 동일 준비·동의 경계를 통과한다.
- 화면 또는 기능 소유자가 필요할 때 승인 locator와 캐시를 확인하고 비동기 로드한다. 화면 밖 직접 네트워크 다운로드나 Resources fallback은 두지 않는다. 누락/실패는 준비 실패·재시도로 표시하며 준비 전 입장을 허용하지 않는다.
- 공유 사용은 한 로드와 대여 수명으로 관리한다. 종료/비활성/교체 시 UI 참조를 비우고 자신의 Addressables handle만 해제한다. 마지막 사용 후 해제하되 디스크 캐시는 유지한다. 완료가 늦은 작업은 이전 화면/계정에 적용하지 않고 handle을 회수한다. 재진입은 현재 세대로만 표시한다. 상시 Update/상시 폴링 없음.
- 번들은 독립 해제 수명을 기준으로 나눈다. 장비 아이콘은 remote_equipment_icons 별도 번들이지만 launch_required label에 포함한다. 목록·상세는 한 아틀라스를 공유한다. 같은 번들의 타소비자 때문에 해제가 막히는 배치를 피한다.
- 전환 완료 조건은 각 실제 소비자 변경, Resources 경로 제거, bootstrap/Resources의 전이 의존성에서 원격 자산 제외, 원격 build layout 중복 확인, 초기/재다운로드·실패·취소·재진입·참조해제 검사다. 설정 등록만으로 다운로드 배포/전체 변환/실메모리 절감 완료를 주장하지 않는다.
