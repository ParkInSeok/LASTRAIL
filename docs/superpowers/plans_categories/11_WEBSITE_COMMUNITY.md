# LAST RAIL | 공식 홈페이지·데이터 위키·확률 공시·커뮤니티

작성/검토: 2026-09-21. 상태: **사용자 요구 U7·운영 일원화 U8·환경/점검 U9 반영 + 신규 상세 기획안**. 사이트·API·DB·도메인 배포/연결은 실행하지 않았다. 주소 `lastrail.app`은 사용할 홈페이지 도메인 기준이지 현재 서비스가 열려 있다는 주장이나 실제 DNS 변경이 아니다.

핵심 요구: 게임의 증강·인챈트·장비 등 데이터 테이블을 조회하는 공식 위키, 확률 공시, 커뮤니티, 공지사항을 제공한다. 브랜드 표기는 LAST RAIL / 한식게임즈(Hansik Games)를 사용한다.

[08 밸런스 배포](08_BALANCE_RELEASE.md)는 실제 게임용 데이터와 호환성을, [10 광고·공지](10_LIVEOPS_NOTICES.md)는 광고 스위치와 공식 공지 원문을 소유한다. 이 문서는 외부에 무엇을 어떻게 공개하는지와 커뮤니티 사용자 기능·기존 Admin 연결을 정의한다. 운영 화면과 운영 권한의 공통 경계는 [10 §0](10_LIVEOPS_NOTICES.md#admin-operations)을 따른다. 공식 데이터를 홈페이지에서 다시 수동 편집하는 별도 정답으로 만들지 않는다.

## 1. 목적·출시 범위

공식 홈페이지는 소개용 랜딩 하나가 아니라 **공식 정보·버전별 설명·확률·피드백의 진입점**이다. 처음부터 유저가 공식 수치와 개인 공략을 구분할 수 있어야 한다.

현재 개발·통합·브라우저·실기기·내부테스트는 DEV 하나에서 수행한다. U9로 STG 환경은 폐기한다. DEV 사이트·위키 미리보기는 승인된 테스터만 열람하며 로그인/서버 권한으로 막는다. robots/noindex만으로 비공개를 보장하지 않는다. DEV를 일반 사용자에게 개방하거나 테스트 계정·경제를 PROD로 이동시키지 않는다. 광고 없는 첫 공개 데모는 별도 운영 환경·보안·정책·콘텐츠 승인 뒤에 배포한다.

공개 홈페이지는 공식 위키·공지·확률·정책을 비로그인으로 읽을 수 있게 한다. 글/댓글 작성과 계정별 문의·설정에는 적절한 인증이 필요하다. 커뮤니티를 요청 범위에서 제외하지 않되, 실제 공개 전에 신고·차단·운영 검수 기능까지 함께 준비한다.

공식 앱 다운로드 링크가 승인되지 않았으면 '준비 중'으로 표시하고 임의 스토어 URL이나 실행되지 않는 버튼을 만들지 않는다. 공개 전 진행 중인 데모라는 표현은 광고가 나중에 생길 수 있다는 안내와 분리해 정확하게 작성한다. 체험 시간·유료 가격·전체 콘텐츠 개방·계정 초기화를 이번 요구에서 추정하지 않는다.

### 1.1 홈페이지는 사용자 표면, 운영은 기존 Admin — U8

홈페이지에는 유저용 읽기·작성·신청·본인 결과 조회 기능을 둔다. 고객문의 답변, 신고 심사, 공지/FAQ/알려진 문제 편집, 위키·확률 공시 검수·게시와 같은 운영 기능은 모두 기존 Admin Console에 메뉴로 연결한다. 별도 홈페이지 운영 백오피스나 CMS를 추가하지 않는다.

홈페이지/앱이 보내는 문의·신고·신청은 서버가 저장하고 Admin은 같은 원본을 조회·처리한다. 사용자에게는 공개된 결과나 본인에게 허용된 답변만 제공한다. [03 §6](03_SUPPORT_DIAGNOSTICS.md#admin-support)의 문의 계약을 재사용하며 공개 게시판에 비공개 상담 내용을 복제하지 않는다. U8은 유저의 자기 글 수정/삭제·신고·개인 차단 기능을 제거하는 지시가 아니다.

## 2. 공개 데이터 구조

**Admin/검증된 원본 → 공개용 변환기 → 검증된 공개 스냅샷 → Public Read API·캐시 → 홈페이지 위키/확률 화면**

게임 API 전체나 Admin DB를 브라우저에 직접 노출하지 않는다. 공개 데이터용 허용 필드 목록을 사용한다. '게임 API와 동일한 DB 서버를 쓰는가'는 물리 배치 선택이고, 공개/관리/게임 쓰기 권한은 반드시 논리적으로 분리한다. 초기에는 기존 서버 프로젝트에 작은 공개 read 계층을 추가할 수 있으며, 무조건 새 대형 서비스로 쪼개지는 않는다.

| 객체 | 역할 |
|---|---|
| PublicCatalogSnapshot | publicSchemaVersion, sourceBalanceVersion, sourceDigest, contentReleaseId, 문서 template/locale 버전, 공개 항목 |
| ProbabilityDisclosureSnapshot | 실제 추첨 policy 버전과 조건·확률·반올림·변경 이력·공시 승인 |
| PublicReleaseIndex | 실제 공개 운영 배포 문맥/기준점 → 공개 catalog/공시 snapshot 목록 |
| EditorialPage | 수동 작성 초보자 안내·설명. 시스템 데이터와는 별도 원문/편집 이력 |
| OfficialNotice | 새 테이블 복제 없이 10의 Notice에서 WEB+PUBLIC만 투영 |

### 공개 허용/제외

공개 허용은 현재 제공되는 항목의 이름·분류·설명·단위·수치표·효과조건·중첩/상한·호환 대상·획득 경로·정확한 공시 확률·적용 버전이다. 필요한 공개 아이콘/설명 자산도 검증된 리소스에서 참조한다.

Draft, 미공개 콘텐츠/미승인 확률, 내부테스트용 설정, SDK 비밀키, 보상 원장, 계정 개인정보, 운영자 메모, 보안탐지 기준, 실제 진행 run seed/미공개 보상 결과는 공개하지 않는다. 위키에 수치를 숨기기 위해 보안 정책이라는 설명을 남용하지 않는다. 공개가 필요한 확률과 조건은 명시적으로 공개한다.

목록 필터만이 아니라 상세·직접 ID 조회·검색·비교·번역·이미지·캐시까지 같은 공개 검사를 한다. `channel=INTERNAL`을 쿼리에 넣어 공개 endpoint를 통해 테스트 표를 받을 수 없어야 한다.

### 2.1 현재/구버전 구분

08의 환경·채널·앱 버전코드별 선택을 유지한다. 홈페이지는 전체 환경에서 번호가 가장 큰 BalanceVersion을 선택하지 않는다. 공개 운영 배포의 승인된 버전 목록만 제공한다. '최신'은 기본 보기일 뿐 유일한 정답이 아니다.

앱에서 연결할 때는 현재 작전의 고정 balanceVersion 또는 현재 승인된 선택 결과와 해당 공시 ID를 함께 지정한다. 홈페이지가 이 식별자를 보고 게임 접근권한을 부여하는 것이 아니라, 이미 공개된 해당 버전 설명만 찾는다. 임의 입력한 비공개 ID는 거절한다. 일반 웹 방문자는 버전/빌드 필터로 적용 범위를 볼 수 있다.

구버전 유효 작전과 지원되는 구형 앱을 위해 공개 이력과 정확한 버전별 permalink를 보존한다. 데이터 롤백은 현재 공개 index를 새 개정으로 이전 공개 snapshot에 연결하는 것이며 과거 원문을 덮어쓰지 않는다. 공개 오류 수정은 정정 이력을 남긴다.

| 지휘관 스킬 | 직접 강화 원천은 내실과 명시 증강. 장비 계열과의 경계 |
| 맵·전투 | 합류 가능한 분기 노드, 사건 종류·선택 결과, 일반/엘리트/특성 추가 조건 |

고유효과16종·인챈트16종의 현행 작성표는 [13](13_EQUIPMENT_ENCHANTMENTS.md), 맵/드랍 작성표는 [14](14_MAP_EVENTS_DROPS.md)다. 이 표는 실제 출시 가능한 효과 처리기/카탈로그가 모두 연결됐다는 뜻이 아니다. 참조된 증강40종도 마찬가지다. 미구현 행을 '사용 가능'으로 공개하지 않는다. 공식 위키는 검증된 실제 릴리스 행만 사용하고 계획 설명은 '개발 중' 영역에 분리한다.

카테고리/효과/역할/스킬자원·시술성급·세트 필터, 한글 이름·ID 검색, 단위와 상한 표시, 관련 효과의 상호 링크를 제공한다. 복잡한 동작은 단순 숫자만으로 설명하지 않고 효과 template과 명시 파라미터로 문장을 생성한다. template·단위·번역 변경도 재생성/검수 대상이다.

기본 보기에서는 문서 버전과 게임 적용 버전을 눈에 보이게 표시한다. 데이터 조회 실패는 0%/효과 없음으로 채우지 않고 오류/재시도와 현재 사용 중인 검증된 snapshot을 구분한다. 홈페이지 계산 도구는 저장/합성/보상 권한을 갖지 않는다.

## 4. 확률 공시

**추첨에 쓰는 원본과 공개에 쓰는 원본을 같은 버전에 연결한다.** 운영자가 홈페이지 표의 퍼센트만 수동 수정할 수 있게 하지 않는다. 공시용 변환기에서 실제 policy를 읽어 정규화·단위·조건·정확한 확률·표현 정밀도를 생성한다.

| 대상 | 표시해야 할 구분 |
|---|---|
| 장비 드랍 | 노드종류·진행구간·획득개수·성급·카테고리·세트 각각의 조건과 확률 |
| 장비 고유효과 | 3성 최초 추첨, 직접 고성급 생성 규칙, 중복 등급 합산, 적용 가능한 후보 |
| 인챈트 | 이벤트 종류 선택과 실제 효과 선택을 분리, 대상 장비 조건·시술성급은 확률인지 확정 값인지 구분 |
| 증강·리롤 | 후보 적격성, 현재 후보 제외, 중복 없는 선택, 실제 풀 크기와 가중치, 무후보 무소모 |
| 맵 이벤트 | 기본 가중치와 배치 제약 적용 후의 의미를 구분. 기본 가중치를 최종 경로 확률로 부르지 않음 |
| 지휘관 내실 영향 | 추가 드랍 등 변경되는 확률·조건. 기본값과 적용 후 값 구분 |
| 보급/클리어 룰렛 | 각각 독립 policy, 결과별 배수와 확률, 배수 제외 보상. OFF면 현재 미제공/과거·예정 구분 |

각 공시에는 policyId/version, 공개 catalog 버전, 적용 시작·종료 또는 배포 이력, 해당 앱/콘텐츠 범위, 비용/제공 조건, 확률의 분모와 조건, 확률 변동 조건, 과거 버전 링크를 표시한다. 같은 balance 안에서도 별도 보상 policy가 있으면 그 ID를 추가로 고정한다. 실험이 있다면 어떤 공개 규칙이 적용되는지 식별 가능해야 하며 숨은 개인별 결제 유도 확률을 만들지 않는다.

### 4.1 조건부 확률 예시 — 실제 운영값 아님

16종 모두 적격이고 동일 가중치로 한 번 추첨하는 경우에만 개별 확률이 1/16=6.25%다. 장착 적격성 때문에 후보가 10종이면 균등 추첨의 개별 확률은 10%다. 모든 상황을 6.25%로 표시하지 않는다.

동일 가중치 N개에서 서로 다른 후보3개를 뽑는 경우 '한 추첨 위치의 확률'과 '3후보 안에 한 번 이상 포함될 확률'은 다르다. 후자는 조건을 만족하는 균등 비복원 추첨에서 3/N이다. 가중치·제약이 있으면 그대로 쓸 수 없다. 현재 후보를 제외한 리롤의 N도 다시 계산해야 한다.

다단계 획득확률은 실제 조건부 분포를 결합하고, 독립성이 정의되지 않은 단계의 주변확률을 임의로 곱하지 않는다. 맵 제약 때문에 최종 사건 확률의 정확한 계산이 어려우면 기본 가중치·실제 알고리즘·조건을 명확히 표기하고, 필요한 정확 공시를 충족할 수 있을 때까지 해당 유료화/확률기능 활성화를 보류한다. Monte Carlo 결과는 관측/추정일 뿐 법정/실제 설정확률을 대체하지 않는다.

확정적인 합성 승급/세트 승계는 '확정 결과'로 구분하고, 새 고유효과처럼 무작위 부분만 별도 공시한다. **J03 승인:** 확정 고유효과의 합산은 미리 보여주고 새로 붙는 효과는 무작위로 표시한다. 합성/승급 성공 후 고정된 실제 결과를 공개한다. 미리보기 조회는 난수를 소비하지 않으며, 확정 결과의 재조회는 재추첨하지 않는다. [13](13_EQUIPMENT_ENCHANTMENTS.md#preview)을 따른다.

### 4.2 공개 검증과 활성화 순서

`밸런스/확률 policy 확정 → 공개 허용 필드 변환 → 공시 snapshot 생성 → 참조/확률/설명/접근성 검증 → 버전 URL에서 서비스 준비 → 실제 게임 배포/기회 생성 활성화 → 공개 index 갱신 확인`

분산 CDN과 게임 DB를 하나의 트랜잭션이라고 주장하지 않는다. 불변 공개 파일을 먼저 준비·검증하고 그 식별자를 활성화의 필수 입력으로 삼는다. 서버의 배포 변경과 해당 승인 식별자는 동일 DB 경계에서 기록한다. 최신 목록 캐시가 잠시 늦더라도 앱의 버전 고정 링크가 올바른 자료를 열어야 한다. 준비 실패 시 신규 해당 기능 활성화를 차단하되 이미 확정된 지급은 삭제하지 않는다.

공시 페이지와 게임 내 확률 보기 모두 로그인 없이 필요한 정보를 읽기 쉽게 제공하는 것을 목표로 한다. 임의 다국어/지역 기본값으로 다른 확률을 보여주지 않는다. 정밀한 내부 weight/분수와 표시 백분율을 함께 검증하고, 작은 확률을 0으로 반올림하거나 합계 오류를 숨기지 않는다.

### 4.3 법정 공개와 자율 투명성의 구분

본 기획은 법정 의무 여부를 확정하는 법률 의견이 아니다. 공개 대상은 유상성·연계 재화·상품·예외·제공 국가에 따라 출시 전 검토해야 하며, 광고 OFF나 '데모' 명칭만으로 면제라고 단정하지 않는다. 웹 공시만으로 게임 내/광고 표시 등 모든 요구를 충족했다고 보지 않는다.

제품 정책으로는 **무료 작전 드랍을 포함해 플레이어가 판단에 쓰는 확률도 자율 공개**하는 안을 권장한다. 법정 대상/표시 방식은 별도 검토 상태를 두며, 신규 과금·광고 연계 상품 추가 시 재검토한다. 확인한 문체부 공식 배포 안내는 2024-02-19 해설서이며, 이 문서 작성에서 최신 법령 전체나 개별 모델의 면제/해당 여부를 확정하지 않았다. 외부 참고는 §10.

## 5. 커뮤니티 최소 기능

커뮤니티 제공은 확정 요구다. J10에 따라 초기 게시판은 자유게시판, 질문/답변, 공략·빌드, 건의/피드백 네 종류의 추천 범위로 진행한다. 공지는 유저 게시판과 같은 권한으로 편집하지 않는다. 버그 중 공개해도 되는 항목은 알려진 문제로 게시하고, 계정·결제·로그·보안 제보는 비공개 문의로 분리한다.

| 범위 | 초기 포함 |
|---|---|
| 열람 | 공개 글/댓글·카테고리·검색·페이지/커서 이동 |
| 작성 | 인증된 계정의 글·댓글, 수정·삭제, 미리보기, 스포일러 표시 |
| 공략 | 관련 wiki ID와 balanceVersion 표시. 구버전 공략 경고 |
| 사용자 제어 | 글/댓글/사용자 신고, 사용자 차단·콘텐츠 숨김 |
| 운영 연계 | 검토 대기, 숨김/복원, 댓글 잠금, 수동 이용제한, 사유·이력·이의제기는 기존 Admin Console에서 처리 |
| 남용 방지 | 계정/요청률 제한, 신규계정 대량링크 제한, 중복 요청 처리 |

**J10 승인:** 첫 버전은 제한된 Markdown 텍스트와 승인된 링크 중심으로 진행한다. 사용자 이미지 업로드는 파일검증·용량·메타데이터 제거·악성/부적절 이미지 신고·삭제 경로까지 준비한 뒤 확장한다. DM, 실시간 채팅, 유저 간 아이템 거래, 현금 거래, 유료 공략, 활동에 따른 게임 재화 보상은 초기 범위에 넣지 않는다.

공식 데이터 위키는 운영 승인 원본에서 생성되는 읽기 전용이다. 유저가 공략을 쓰거나 오류 수정을 제안할 수는 있지만 게임 수치·공시 확률·공식 공지를 직접 편집하지 못한다. 공식 설명과 유저 의견에는 눈에 보이는 출처 표식을 둔다.

### 5.1 인증·계정 연계

기존 LAST RAIL 계정 체계를 재사용하되 브라우저 세션 adapter는 별도 검증이 필요하다. 앱 토큰을 URL·공지 action·localStorage 공유만으로 전달하지 않는다. 웹에는 Secure/HttpOnly cookie와 CSRF 방어, origin 검증·명시적 로그아웃/세션 만료를 사용하는 안을 기본으로 둔다. 프레임워크·구현 패턴은 실제 저장소 구조에서 확정한다.

계정 닉네임이 같다는 이유로 같은 사람으로 연결하지 않는다. 공개 authorId/닉네임과 내부 accountId를 분리하고 이메일·원장·저널을 공개하지 않는다. 게임 게스트 계정을 웹 계정으로 임의 대체/병합하지 않는다. 게스트 연동은 기존 소유권 보존 계약이 준비됐을 때만 제공하고, 초기 웹 작성은 소유권이 검증된 기존 계정 인증 경로로 제한한다.

기존 Admin은 일반 회원 웹 세션과 구분된 운영 인증·역할·세션을 사용한다. 운영·모더레이션 권한을 가진 사람도 해당 작업은 Admin에서 수행한다. 공개 사이트의 침해가 바로 관리 API 호출로 이어지는 공유 자격증명을 두지 않는다. 운영 알림/마케팅 수신 동의는 커뮤니티 이용 동의와 분리한다.

### 5.2 운영·안전 정책

글 작성 전에 서비스 약관·커뮤니티 규칙에 동의하도록 한다. 괴롭힘·개인정보 노출·불법 콘텐츠·아동 착취·스팸·사칭·권리침해를 금지하고 누구나 쉽게 신고할 수 있게 한다. 신고량만으로 계정을 자동 영구정지하지 않는다. 자동화는 rate limit, 임시 격리, 검토 큐에 활용할 수 있지만 **영구 제재는 권한 있는 운영자의 직접 검토 후 수동 실행**한다. 게임 제재와 커뮤니티 제재는 범위를 분리하고 자동 연쇄 제재하지 않는다.

사용자 차단은 그 사용자의 콘텐츠·상호작용을 적절히 숨기며 자기 보호 기능이다. 운영자의 제재나 공식 공지를 숨기는 권한과 다르다. 신고자 정보는 게시자에게 공개하지 않는다. 접근성 있는 신고/차단·운영 대응이 준비되지 않았으면 게시 기능 공개를 미룬다.

홈페이지 커뮤니티를 앱에서 보여주거나 연결할 때는 UGC 관련 스토어 정책을 별도로 확인한다. 외부 브라우저로 열었다는 이유만으로 관련 정책에서 자동 제외된다고 간주하지 않는다. 본문과 댓글은 제한된 서식으로 sanitize하고, 외부 링크의 임의 fetch는 SSRF/개인정보 위험을 검증하기 전 사용하지 않는다.

### 5.3 삭제·보존·문의

회원 글/댓글 삭제, 계정 삭제, 내부 신고 증거·법정 보존자료는 범위와 처리방식을 각각 정한다. '계정 삭제'를 단순 잠금으로 대체하지 않는다. 개인정보 최소 수집·보관기간·삭제·사고 대응 연락처를 실제 서비스에 맞게 정하고 임의 보존기간을 이 문서에서 확정하지 않는다.

게임 내 계정 생성이 가능한 제품의 웹 외부 삭제 요청 경로를 마련한다. 소유권 확인 없는 닉네임 입력만으로 삭제하지 않으며, 게임 접속이 불가능한 사람에게 게임 재설치를 유일한 삭제 경로로 요구하지 않는다. 실제 제출이 접수됐는지 확인 가능한 응답과 후속 절차를 제공한다. 기존 문의를 사용하면 [03](03_SUPPORT_DIAGNOSTICS.md)의 사생활·원요청 보존·영수증 정책을 유지한다.

## 7. Admin·API·데이터 책임

아래 관리 명령의 UI는 기존 Admin Console에 둔다. 서버 도메인/저장소는 재사용하고, 공용 읽기·자기 데이터 쓰기·운영 쓰기는 각각 서버 권한을 검사한다. 홈페이지 별도 운영 체계를 만들지 않는다. 공통 규칙은 [10 §0](10_LIVEOPS_NOTICES.md#admin-operations)을 참조한다.

| 확률 공시 | ProbabilityDisclosureSnapshot, DisclosureAudit | GenerateFromPolicy, ValidateDisclosure, ReadVersionedDisclosure |
| 공지 | 10의 Notice/Revision/ReadState | 동일 원문 WEB projection. 새 CMS 원문 복제 금지 |

| 문의/권리 | 기존 Support 확장 | 앱/웹은 비공개 접수·본인 결과 조회, 기존 Admin은 문의 조회·답변·처리. 상세는 [03 §6](03_SUPPORT_DIAGNOSTICS.md#admin-support) |

표의 이름은 신규 논리 계약이다. Game API의 기존 DB/route/auth를 읽고 명칭과 경계를 확정해야 한다. 공개 CRUD가 balance·wallet·inventory에 쓰기 권한을 가지지 않는다. 네트워크 호출은 기능 단위이며 브라우저에 Admin API 키를 포함하지 않는다.

홈페이지는 반응형·의미 있는 문서 HTML·키보드/스크린리더 접근·검색 가능한 주소를 지원하는 설계를 권장한다. 특정 프레임워크 도입은 이번 기획으로 강제하지 않는다. 검증된 공개 JSON과 화면 렌더링을 캐시할 수 있지만 draft/private 응답을 같은 공개 캐시 키에 넣지 않는다.

| DEV 커뮤니티 | 글/댓글·신고·차단·운영 검수 | 계정 격리·권한·XSS·중복요청·신고/삭제 동작 |

## 11. 점검 중 홈페이지 화면 — U9

점검 정책·상태 원본과 두 표면의 상세 화면 요구는 [12 서비스 점검](12_SERVICE_MAINTENANCE.md)에만 정의한다. 운영은 기존 Admin이며 공개 홈페이지는 점검 조회·안내만 담당한다. 게임 점검만으로 위키·확률·공지까지 일괄 닫지 않는다.

## P-13 커뮤니티 공개·본인·운영 계약 v1 — 2026-09-29 / 상세 작성·신규 정책 승인 대기

목표는 승인된4게시판을 기존 홈페이지와 Admin에 안전하게 연결할 수 있는 단일 서버 계약이다. 기존 홈페이지 미술·공식 위키·문의 원본은 보존한다. 본 절의 논리 DTO/명령은 구현 인수 명세이며 실제 HTTP 경로/DB 컬럼/권한 상수의 존재를 주장하지 않는다. S-13 웹세션과 S-16 실제 schema 매핑/검증이 필요하다. 글쓰기 공개/운영 배포는 이번 작업이 아니다.

### 1. 범위와 권한
기존 승인: 자유/질문·답변/공략·빌드/건의·피드백, 제한 Markdown과 승인 링크, 본인 수정·삭제, 신고·차단, 기존 Admin 운영, 비공개 문의 분리. 업로드/DM/거래/좋아요 보상/게임재화 추가 없음.

| 주체 | 읽기 | 쓰기 |
|---|---|---|
| 비로그인 | 공개 상태 글·댓글만; DEV는 별도 tester 인증 필요 | 없음. 신고 진입에서 로그인/비공개 문의 안내 |
| 인증 회원 | 공개 + 자신의 처리상태/신고 접수 결과 | 자기 글·댓글 작성/수정/삭제, 신고, 자기 차단 목록 |
| 작성자 | 자기 숨김/검토중 글은 상태와 공개 가능한 사유만 | 타인 댓글 편집·운영 복원·잠금 해제 불가 |
| 운영자 | Admin 전용 검토 권한의 증거/감사 | 권한별 숨김·복원·댓글잠금·수동 이용제한 |
| 서버 | 세션→계정 매핑·소유권·상태·공개 projection | 게시 상태·개정·원 receipt의 유일한 권위 |

신고자/내부 accountId/이메일/연결정보/내부 메모는 공개 DTO에서 제외. 공개 authorId는 불투명 식별자로 accountId와 분리한다. 로그인했다고 INTERNAL 자료를 받을 수 없다. 본인/운영 응답 no-store, 공개 캐시에는 본인 권한/차단 결과를 섞지 않는다.

### 2. 논리 객체·필드와 상태
- Board: boardId, 공개 이름, allowedContentTypes, writeEnabled, policyVersion.4게시판의 실제 ID는 S-16이 기존 명칭과 매핑한 표를 인계하며 문자열 표시명으로 권한 판단 금지.
- Post: postId, boardId, publicAuthorId, title, sanitizedBody, spoiler, wikiRefs[], sourceBalanceVersion?, visibility, commentLocked, revision, createdAt, updatedAt. 위키 참조는 실제 공개 버전/ID만, 미공개 ID의 이름·존재를 응답에 유출하지 않는다.
- Comment: commentId, postId, publicAuthorId, sanitizedBody, visibility, revision, createdAt, updatedAt. **v1 추천은 단층 댓글**. 답글/중첩 thread 자동 추가 없음.
- 공개 visibility=VISIBLE만 본문 제공. 내부 상태 REVIEW_PENDING/VISIBLE/HIDDEN/AUTHOR_DELETED를 구별한다. 댓글 잠금은 글 숨김과 독립, 게시 종료는 글과 댓글의 접근검사를 함께 수행한다.
- Report: receiptId, targetType, targetId, reasonCode, optionalDescription, submittedAt, reporterFacingStatus. 신고 원문/신고자/증거는 Admin 전용. 같은 신고자가 같은 target에 미종결 신고를 반복하면 원 case 참조, 댓글 편집마다 신고권을 새로 지급하지 않는다.
- Block: blocker account 소유, blocked publicAuthorId, revision. 자기 차단 금지. block/unblock은 멱등.
- ModerationAction: caseId, target/revision, action, publicReason, internalNote, actor, at, previous/next state. 회원에게 운영자의 계정정보/내부Note를 내보내지 않는다.

추천 전이: 적격 정상 작성은 VISIBLE, 검토 규칙에 걸린 작성은 REVIEW_PENDING. 운영 검토만 VISIBLE/HIDDEN으로 전환. 글쓴이 수정은 새 revision이고 검토중/숨김을 스스로 VISIBLE로 바꿀 수 없다. AUTHOR_DELETED는 회원 경로에서 복원 불가; 운영 증거는 별도 보존 정책. 공개 삭제 자리에 본문 없는 안내만 남기고 댓글 작성은 차단한다. 부모가 비공개이면 공개 direct-ID 댓글 조회도 거절한다. 댓글잠금은 새 댓글만 막고 본인 삭제·신고는 허용한다.

### 3. 입력·명령·경합
모든 변경은 commandId, expectedRevision(기존 객체 변경), 서버 세션의 actor를 사용한다. actorId를 요청 본문으로 신뢰하지 않는다. create 재전송 동일키·동일payload는 원 receipt, 다른payload는409. 다른키 반복은 별도 남용 제한이며 같은 명령으로 임의 합치지 않는다. update/운영 경합은409 후 최신본과 사용자 입력을 보존해 재검토한다.
논리 명령: ListPosts/ReadPost/ListComments, Create/Update/DeletePost, Create/Update/DeleteComment, SubmitReport, Block/Unblock, AdminReview/Hide/Restore/LockComments/RestrictCommunity. 공개 CRUD에서 경제/게임제재 쓰기0.
리스트는 안정 커서(createdAt,id 및 필터/공개범위 버전)를 사용한다. 숨김/삭제는 다음 조회 즉시 필터, 오래된 커서로 비공개 본문 복구 불가. 개인 차단 적용 응답은 공유 캐시 금지.

입력 제한 신규 추천: 제목1~100자, 본문1~10000자, 댓글1~1000자, 신고설명0~2000자, 페이지20/최대50. 공백만 거절, 서버 Unicode 문자수 기준을 schema에 고정. HTTP 입력 byte 상한은 별도 transport 설정으로 검증. 허용 서식은 문단/목록/강조/인라인·블록코드/승인 https 링크이며 raw HTML/임베드/자동 외부 fetch/이미지 렌더 금지. escape/sanitize는 저장 경계와 출력 context에 맞게 적용한다.
남용 제한 신규 추천: 글60초1회·시간당10개, 댓글10초1회·시간당60개, 신규 신고분당3회·일20개. 인증 actor별 서버 카운터, 재전송 원receipt는 중복 소비0;429+retryAfter. 숫자는 버전 설정이며 승인 전 출시값 아님. 자동 영구정지 없음. 신규계정 링크 허용 기준은 명시 정책/승인 allowlist 없으면 링크 신규 입력만 거절하고 텍스트 작성은 가능.

### 4. 차단·신고·운영 복구
개인 차단은 **자신이 보는 상대의 글/댓글을 숨기는 방향**을 추천한다. 상대의 전체 공개 웹 열람을 차단했다고 안내하지 않는다. v1은 DM/멘션 알림이 없으며 차단 상태가 상호 게임 매칭/게임제재로 확장되지 않는다. 작성자 이름 대신 “차단한 사용자의 콘텐츠” 자리표시 후 명시적으로 확인할 수 있게 하는 안은 UI 후보이고 자동 노출하지 않는다. 공식 공지/운영 필수 안내는 차단되지 않는다.
신고 접수와 콘텐츠 삭제는 별개. OPEN→IN_REVIEW→ACTIONED/DISMISSED, 신고자에게 접수/처리됨만 공개하고 내부 판단자료는 노출0. 신고 수만으로 자동 영구제재0. 운영 숨김은 검색·목록·상세·캐시를 같은 revision으로 무효화; 실패시 새 공개를 차단하고 재시도 가능한 운영 오류를 남긴다. restore는 원 공개자격/부모 상태 재검사 후 새 revision, 삭제 글 부활이나 제재 해제 자동연쇄 없음. 이의는 기존 비공개 문의에 case 참조로 접수.

### 삭제/숨김 처리의 검증 경계
- 공개 숨김·작성자 삭제 결과는 공개 목록/검색/상세/댓글 direct-ID/공유 캐시에서 같은 권한 상태로 일치해야 한다. 보존된 내부 증거가 있다는 이유로 본문을 공개하지 않는다. 캐시 전파 실패를 처리 성공으로 숨기지 않고 기존 운영 오류/재시도 경계에 연결한다.
- 작성자 삭제·운영 숨김·계정 삭제·보존 만료는 다른 사건이다. 회원 복원 불가인 AUTHOR_DELETED를 운영 숨김 복원으로 되살리지 않는다. 계정 삭제를 로그인 잠금만으로 대체하지 않는다.
- 실제 설정이 허용한 증거 보류가 있다면 대상 범위·이유·권한·해제 조건을 확인한다. 임의 전자료 영구보류나 공개 복원을 허용하지 않는다. 기간/예외 근거 자체는 별도 운영 설정 확정 대상이다.
- 삭제 실행은 대상 ID/원 revision·policy version·원명령 결과를 추적한다. 재시도·부분 실패에서 이미 완료한 처리를 다시 공개하거나 다른 사용자 자료를 삭제하지 않는지 검증한다. 본문을 제거한 뒤에도 감사 로그에 그대로 복사돼 있으면 그 사본도 설정 범위에 포함한다.
- 백업 복구 검증은 삭제/숨김 상태가 함께 재적용되는지 확인한다. 원문이 복구됐다는 이유로 공개 가능 상태로 기본 초기화하지 않는다. 서버 설정/실행 로그와 소비 화면 결과를 함께 보며 실제 확인하지 못한 복제본의 삭제까지 주장하지 않는다.

### 공개 활성화 전 인수 사례
1. 본인 삭제 후 과거 공개 URL·댓글 URL·목록/검색·오래된 커서에서 본문 비노출.
2. 숨김과 수정이 경합해도 작성자 수정으로 공개 상태가 복원되지 않음.
3. 신고 증거는 승인된 운영 권한에서만 조회되며 신고자/일반회원 응답에 포함되지 않음.
4. 정책 누락/손상/환경 오지정에서는 공개 활성화를 거절하고 원인을 운영자에게 제공함.
5. 정책 기준 사건/만료 경계 전후 결과가 실제 확정값과 일치하고 무기한 기본값으로 바뀌지 않음.
6. 계정 삭제 후 공개 author 연결·본문·신고 증거가 각 확정 정책대로 처리됨. 소유권 확인 없는 닉네임 요청은 삭제를 수행하지 않음.
7. 삭제 재시도/중단 복구 및 검색·캐시·백업 재구성에서 삭제한 본문이 다시 공개되지 않음.

전 항목 실행 상태 NOT_RUN. 실제 보존기간·설정 승인 근거·환경 매핑이 아직 인수되지 않아 P-13 최종 완료는 아니다. 원담당이 위 표의 실설정과 근거를 제시하면 Plan은 원문과 대조하고, S-13까지 완료된 시점에 기존 후속 절차로 S-16 착수 경계를 확인한다. 새 실행 큐/자동 메시지/운영 삭제는 이번 작업에 포함하지 않는다.

| 신고·분쟁 증거 | 처리 중 필요한 최소 자료, 최종 처리 통지 후 최대90일 | 이의 대응이 계속 필요한 최소 자료만 제한된 증거 영역에 보존. 필요가 먼저 끝나면 일찍 파기. 삭제된 일반 글을 신고 가능성만으로90일 보관하지 않음 |
| 일반 운영 조치 감사 | 조치 발생 후 최대180일 | 사건/조치/시각/담당 역할/결과의 최소 메타데이터. 본문·이메일·불필요한 IP·토큰 복제 금지. 법정 보안기록과 별도 분류 |
| 복구용 백업 | 생성 후 최대7일 순환을 목표 | 무기한/장기 사본 축적 금지. 삭제요청의 일률적7일 유예가 아님. 실제 개별 파기 또는 동등하게 복구 불가능하게 만드는 수단과 공급자 지원 확인 필요 |

핵심 추천은 삭제 자료를 전부30/90일 보관하는 안보다 일반 본문을 바로 파기하고 실제 사건에 필요한 증거만 분리하는 방식이다. 최소 메타데이터라도 사람을 연결할 수 있으면 개인정보 검토 범위에서 제외하지 않는다. 기간이 짧다는 이유만으로 적법한 처리 근거가 생기는 것은 아니다.

### 신고·이의·보류의 종료 조건
- 신고 접수 시 원대상/revision과 필요한 최소 증거만 고정한다. 전체 사용자 활동/전체 수정본을 한꺼번에 수집하지 않는다. 신고 기각 후 추가 보존 목적이 없으면90일을 채우지 않고 파기한다.
- 90일은 최종 처리 결과를 통지한 시점부터 계산한다. 단순 조회·운영 메모·반복 신고가 종료일을 다시 연장하지 않는다. 실제 새 이의가 들어오면 필요한 증거에 한해 원case와 연결하고, 처리 사유/종료 시점을 따로 기록한다. 자동 무기한 갱신은 금지한다.
- 처리 중이라는 이유로 영구 보관하지 않도록 미종결 case는30일마다 필요성 검토 대상으로 표시하는 안이다. 이는 자동 사건 종결/사용자 이의신청 기한이 아니다. 운영자가 검토하지 못했다는 이유만으로 보존 근거가 만들어지지 않는다.
- 법령상 보존 또는 유효한 별도 보류 근거가 확인되면 해당 자료 범위·근거·시작/해제 조건·접근 역할을 등록한다. 모든 자료에 일괄 보류를 걸지 않는다. 사용자 삭제/탈퇴 요청 시 남겨야 하는 자료와 이유를 실제 정책대로 구분한다.

### 파기·저장·복원 계약
공개 응답에서 본문을 숨기는 것과 실제 저장 자료 파기는 다르다. 삭제 명령은 공개 차단→권위 있는 삭제 작업 등록→활성 저장소/색인/캐시/해당 사본 파기→확인된 범위 완료를 추적한다. 작업 실패는 원명령으로 재시도하고 이미 파기된 본문을 재생성하지 않는다. 완료되지 않은 백업까지 삭제 완료라고 안내하지 않는다.

백업7일은 복구 정책의 상한 후보일 뿐 파기의 법적 예외가 아니다. 실제 백업이 선택 삭제를 못한다면 공급자 기능/보관기간 단축·백업 대상 최소화·키 폐기 등의 실효성을 검토해야 하며, 단순 접근 차단/복원 시 필터만으로 물리적 파기가 끝났다고 판정하지 않는다. 삭제 이력을 복원에 재적용해 재공개를 막는 계약은 추가 방어로 유지한다. 이 저장소 기능 검증이 끝나기 전 백업 파기 적합성은 미확인이다.

목적이 유지되는 자료의 최대 기간은 승인 설정의 기준 사건으로 계산한다. 기간 만료/삭제 사건은 서버 시각으로 처리하며 클라이언트 시계나 페이지 열람이 연장하지 않는다. 정책 개정이 기존 만료일을 자동 연장하거나 이미 파기한 자료를 복구하지 않도록 버전 적용표를 둔다. 동시 수정/삭제/신고의 순서는 기존 revision·원영수증 계약으로 판정한다.

### 승인 및 출시 인수
신규 승인 요청: 일반 삭제/탈퇴 시 본문 파기, 일반 과거 수정본 미보존, 사건별 필요 증거 최종 통지 후 최대90일, 일반 운영 감사 최대180일, 미종결30일 검토, 백업 최대7일 목표. 백업 기술 구현·각 자료 처리 근거·법정 보안기록 분류/실기간·실제 처리방침 반영은 기간 승인과 별도로 확인한다. 개인정보 보호책임/운영 검토자가 실제 서비스의 처리 근거와 고지 내용을 확인한 뒤 공개 활성화한다. 이 문서는 적법성 전체 검토 완료 선언이 아니다.

P-13의 현황은 ‘한국 범위 확정·신규 수치안 제시’다. 승인 전 publishable 정책으로 발행하지 않는다. 승인 후 Plan 정책값과 실제 Server 설정/환경 매핑을 대조하고 기존 S-13/S-16 경계를 정리한다. DEV 검증은 가상 자료로 수행하며 실제 사용자 자료 파기·PROD 변경은 이번 요청에 포함하지 않는다. 현재 문서 검토만 완료, 실행 사례는 NOT_RUN이다.

## 홈페이지 로그인 상세 흐름 v1 — 2026-10-01 / 신규 UX 정책 승인 대기

목적: 기존 홈페이지를 유지하면서 본인 문의/커뮤니티에 기존 게임 계정으로 접근한다. 신규 회원 체계·계정 병합·SNS 로그인 확대는 만들지 않는다. 신규 UX 선택과 실제 서버 동작을 아래처럼 구분한다.

### 근거·선택
확인한 소스: Server apps/game-api/src/web-session-routes.ts, web-session.ts, support-private-read-routes.ts. 비밀번호/Google 기존 ACTIVE 계정 인증, Secure/HttpOnly/SameSite=Lax cookie·고정1시간 만료·CSRF, /me·/csrf·/logout이 있다. Google은 이미 연결된 subject만 허용하고 미연결/중지/잘못된 인증은 공통 web_login_invalid다. 실제 Origin/OAuth 설정·브라우저 성공은 이번에 검증하지 않았다.

추천은 기존 홈페이지 내 로그인 페이지와 ‘문의 작성 화면 안 재인증’의 동일 인증 Controller 재사용이다. 새 계정센터 구축은 범위가 크고, 매번 전체 페이지 이동은 메모리 초안을 잃기 쉽다. 새 레이아웃/아트 제작을 전제로 하지 않는다.

### 진입·정상 흐름
1. 초기 화면은 인증 확인 중이며 /me 결과 전 본인 문의/작성 버튼을 인증 완료로 표시하지 않는다. PRD 공개 읽기는 기존 공개 정책 유지. DEV의 tester 검사는 로그인 성공과 별도로 처리한다.
2. 로그인 버튼 또는 보호된 기능 진입 → 로그인 화면. 복귀 목적지는 허용된 사이트 내부 경로만 사용하며 외부 URL·프로토콜 상대 URL·로그인 반복 경로를 거절한다. 자격증명/문의 본문을 URL에 넣지 않는다. 목적지가 삭제/권한 없음이면 원인을 표시하고 해당 기능 목록으로 복귀한다.
3. 기존 아이디/비밀번호 또는 Google을 선택한다. 비밀번호 표시 토글·입력 라벨·오류 위치·전송 중 중복 방지를 제공한다. 로그인 유지 체크박스는 현 고정 만료 계약에 없으므로 추가하지 않는다.
4. 인증 성공 → /me로 서버 소유 계정 확인 → 필요한 CSRF 준비 → 복귀 화면 재조회. 세션 토큰은 JS 저장소로 옮기지 않는다. 비밀번호·Google ID token은 작업 완료 후 폐기한다. 로그인 뒤 미전송 쓰기 명령을 자동 실행하지 않는다.
5. 닉네임 DTO가 없는 경우 accountId를 공개 이름처럼 표시하지 않고 ‘로그인됨’ 등 중립 표시를 사용한다. 로그아웃/계정 전환은 별도 명시 행동이다. 웹 로그인으로 게임 단일 세션을 교체하지 않는다.

### 작성 중 만료·계정 전환 — 신규 제안
홈페이지의 미제출 문의/글 초안은 현재 탭 메모리에만 보관한다. 만료 시 본문을 가리고 입력·제출을 잠근 뒤 같은 페이지에서 재인증한다. 같은 서버 accountId가 확인된 경우에만 초안을 복원하고 사용자가 제출한다. 다른 계정이면 즉시 폐기한다. 명시 로그아웃/계정 전환·페이지 종료/새로고침은 초안 폐기이며 가능한 범위에서 이탈 전 안내한다. 영속 자동저장/크로스탭 복원은 제공하지 않는다. OAuth가 전체 페이지 이동을 요구하는 환경에서는 초안 보존을 약속하지 않고 이동 전에 알린다. Admin 답변 폼의 만료 시 초안 제거 규칙은 그대로 유지하며 일반 홈페이지 초안과 섞지 않는다.

탭 간 로그아웃 통지는 토큰/본문 없이 갱신 신호만 전달하고 서버 /me를 다시 확인한다. 화면 종료/계정 세대 변경 전 요청의 늦은 결과는 반영하지 않는다. 타 탭이 새 계정으로 바뀌면 현재 초안을 새 계정으로 제출하지 않는다. 이미 서버로 보낸 문의는 초안과 별개이며 03의 원계정/원키 결과 확인 상태를 보존한다.

### 책임·검수·인수
Model은 인증 상태/초안 소유 계정·명령 상태, Controller는 로그인/복귀/재시도, View는 표시/입력만 담당한다. HTTP/쿠키/CSRF 처리는 기존 adapter에서 공통 처리하며 문의/커뮤니티별로 로그인 코드를 복제하지 않는다.
