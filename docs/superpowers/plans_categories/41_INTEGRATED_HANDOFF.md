## 1. 먼저 실제 작업공간을 확인하라

현재 작업 디렉터리와 실제 프로젝트 루트, 연결된 작업공간/저장소, 기존 프로젝트 지침(예: 실제 존재하는 AGENTS.md 등), 현재 변경 상태, 기획·상세 설계·API·데이터·검증·인계 폴더를 먼저 읽어라. 사용자가 별도로 모아 둔 MD 폴더와 data 폴더도 실제 경로를 찾아 확인하라.

문서가 있을 것으로 예상한 경로와 실제로 발견한 경로를 구분하라. 채팅의 sandbox 경로, 이 전달 파일의 다운로드 위치, 과거D:/E: 경로를 현재 실행 경로로 가정하지 마라. 프로젝트 이름만으로 원격 저장소나 브랜치를 임의로 선택하지 마라.

문서 정리를 위해 사용자의 미커밋 작업을 reset·discard·stash하거나 원본을 먼저 삭제하지 마라. 작업 중인 파일과 중복 사본을 식별하고 현재 내용을 보존한 상태에서 필요한 문서만 변경하라. 저장소 상태나 실제 파일 읽기로 해결할 수 있는 사항을 먼저 사용자에게 되묻지 마라.

자료가 제공되지 않았거나 실제로 찾지 못하면 파일명/예상 용도/필요한 확인을 누락 자료 목록에 기록하라. 발견하지 못한 파일을 읽었다고 쓰거나 빈 파일·요약으로 원문을 대체하지 마라. 자격증명·비공개 계정 정보는 보고서에 노출하지 마라.

## 3. 실제 자료 목록을 작성하라

각 파일의 **실제 경로, 종류, 담당 분야, 승인/제안/구현/검증 상태, 관련 원문, 중복 여부**를 목록으로 작성하라. 날짜·수정 시각·문서 길이·‘최종’ 제목은 보조 metadata이지 권위 판정 기준이 아니다.

기준 문서와 같은 제목의 여러 사본이 있으면 내용을 대조하라. 완전히 같은 복사인지, 서로 다른 세부를 가진 버전인지, 실제 사용자 작업 파일인지 구분하라. 구버전 원문은 현행 편집 대상에서 분리하되 출처와 필요한 검증 이력은 보존하라.

이 단계의 목록과 계획 경로는 실제 파일 내용에 근거해야 한다. 아직 이동하지 않은 파일을 이동 완료로 적거나, 존재하지 않는 담당 문서를 만들어진 것으로 표시하지 마라.

## 4. 정책 비교의 우선순위와 상세 보존

다음 순서로 적용하라.

1. 사용자의 가장 최근 명시적 결정·정정.
2. 그 결정 뒤 사용자에게 승인받은 상세안. 승인 당시 제시한 범위를 넘기지 않는다.
3. 위 내용과 충돌하지 않는 기존 상세 기획·API/데이터 계약.
4. 미승인 제안·시험값·과거 구현 설명은 각각의 상태를 유지한다.

같은 파일 안에서도 확정 정책·추천·비교값·구현 보고·검증 결과가 섞일 수 있다. 문서 전체를 하나의 ‘확정’ 표시로 평탄화하지 마라. 승인 근거가 있는 절과 제외된 항목을 나누어라.

**새 요약에 없다는 것은 폐기 근거가 아니다.** 기존 API 필드·직렬화 방식·오류 코드·적격 조건·권한·원요청·재시도·복구·과거 호환·원화 정의를 원문과 대조해 보존하라. 공통 요약이 상세 계약을 충분히 담지 못하면 담당 문서에서 그 계약으로 정확히 연결하거나 필요한 내용을 통합하라.

반대로 사용자에게 명시적으로 폐기된 정책은 옛 코드·테스트·합본에 있다는 이유로 복원하지 마라. 과거 구현이 존재한다면 ‘현재 구현은 구정책, 적용해야 할 정책은 최신 결정, 남은 작업은 차이 해소’로 구분하라.

모순을 해결할 근거가 없을 때만 질문/보류 목록에 남겨라. 이미 결정된 지원 버튼 수·컷신 모드·기준 외형 등을 다시 묻지 마라. 새 수치·새 스킬·새 API를 만들어 모순을 메우지 마라.

## 6. 이번 아트의 승인 범위와 회귀 방지

10인 외형 방향과 차별화 보완은 **중립 전신 설계 기준으로 채택**되었다. 아직 모든 개인 외형이 미승인이라고 되돌리지 말고, 기준 방향 채택과 완성 시안 검수를 구분하라. 원문은00의 아트 판단 및17의 개인 목록·20~29 상태 절이다.

Reina는 기존 보존 정체성과 채택 상세안을 유지한다. Kyle은 성인 남성·크롭컷 우선·넓은 상체·중형 방호·짧은 패널·건메탈/올리브 방향이 채택되었다. 그러나 **Kyle의 무기·방패 유무·주 손은 미확정이며, 단축형 라이플/근접 대응은 후보**다. **Rin의 단창도 우선 비교 후보**다. 실제 무기·공격·Block/Taunt/Interrupt/Breaker와 대조하라.

Eve·Sera·Nyx·Cipher·Iris의 역할 도구를 기본 공격 무기로 단정하거나 비공격 요원으로 바꾸지 마라. Mira의 재장전/과열, Vex의 보스 부위 자동 선택, Nyx의 속박/집결, Cipher의 탈취, Iris의 무적/반사 같은 효과를 아트 표현으로 새로 만들지 마라. 기존 실제 계약이 확인되는 부분만 연결하라.

가칭4인의 성인 인상·큰 외형 방향은 개인 기준안을 따르되 이름·이름 종속 문양/로고·새 ID를 고정하지 마라. Rin의 과거 Military/Mercenary 언급은 실제 태그 미확인 이력이며 이번 승인으로 데이터에 올리지 않는다.

HEX·비례·480px/240px·96/128/160 표시·원화 크기·프레임 수·컷신 길이는 비교값이다. 원화→SD는 단순 축소가 아니며 독립 움직임/깊이 기준 파츠와 가려진 형태 복원, BackLeg/FrontLeg 각각 부츠 포함을19에 연결하라. 영상이 없으면 다시 본 것처럼 보고하지 마라.

공통 아트 전문을 개인마다 복사하지 마라. 개인의 얼굴 구조·머리 외곽·옷 여밈·손과 장비·컷신 구도를 보완하고 다른 시스템의 수치/계약은 담당 원문을 참조하라.

### 최신 컷신 계약 확인 지점

04 §14를 단일 원문으로 유지하고18 및 개인 문서는 제작과 구도만 구체화한다. 다음은 원문을 잘못 되돌리지 않기 위한 확인 항목이다.

- ON/ALWAYS는 매번 표준 전체화면이고, 실제 재생 중 전투 유효 배속0이다.
- DAILY는 첫 표준 재생 대상에서 전체화면, 이후 OFF와 같은 요약이다.
- OFF는 연출 삭제가 아니라 요약이다. 요원은 부분 컷인, 일반 지휘관은 명령/전장 반응을 사용한다.
- 별도 허용된 초토화급 요약이 전체화면이면 그 동안 동일 정지를 적용한다.
- 전투 시계와 표현 시계를 분리하며 스킵·종료에서 피해/비용/보상을 새로 처리하지 않는다. 자신이 소유한 정지만 해제한다.
- 포탑 궁극기는 없고 오른쪽 실제 지원 버튼3개를 유지한다.
- DAILY 집계 단위·초기값·서버 게임일자·시청 시작/스킵 기록은 이후 명시 승인 없으면 권장안이다.

위 목록으로 상세 입력·원사건·중첩 정지·오류·복원을 대체하지 마라.04의 전문을 보존하라. J04 노드/웨이브 수치와 다른 미확정 게임 정책도 아트 승인으로 확정하지 마라.

## 7. 기획과 실제 구현을 나누어라

각 불일치에 대해 다음을 별도 열로 기록하라.

| 항목 | 기록할 내용 |
|---|---|
| 적용할 기획 | 최신 승인 원문·절·근거 |
| 현재 구현 | 확인한 소스/API/데이터 경로와 실제 동작, 미확인 부분 |
| 필요한 작업 | 차이를 해소할 변경 범위·의존성·담당 |
| 검증 | 확인한 테스트의 시점/범위, 새 정책에서 다시 검증할 사항 |

기존 소스 열람은 가능하다. 그러나 **문서 통합을 이유로 게임 코드·실제 API·DB·스키마·Unity 자산·배포를 수정하지 마라.** 새 엔드포인트·마이그레이션·배포 명령·원격 운영 변경은 이 작업에 포함하지 않는다. 문서·색인·문서 경로를 가리키는 프로젝트 지침만 필요한 범위에서 갱신한다.

작성용 JSON에 명시적 승인값과 불일치가 발견되면 먼저 해당 원문과 데이터의 책임을 확인하라. 근거 없는 숫자·ID를 채우지 말고, 현재 작업 범위에서 허용되는 명시적 작성 데이터 정합성 수정만 분리해 기록하라. runtime/운영 데이터 변경으로 확대하지 않는다. `publishable=false`를 문서 정리 완료만으로 true로 바꾸지 마라.

과거 테스트가 당시 구정책에서 통과한 사실을 삭제하거나 새 정책의 테스트 결과로 다시 쓰지 마라. 문서 검사·fixture·로컬HTTP·에디터·Android 빌드·실제 기기·실광고/결제·운영 배포는 서로 다른 증거다. pass를 합산하거나 skip을 pass로 취급하지 마라.

## 8. 폴더 구조와 중복을 정리하라

실제 조사 후 현재 폴더 구조를 최대한 재사용하라. 이미 담당 기준 문서가 있으면 같은 전문을 새 ‘최종’ 폴더에 복사해 두 개의 현행 원본을 만들지 마라.

현재 정책/기획, 상세 계약/구조화 데이터, 구현 계획/현황, 과거 검증/출처/폐기 이력의 역할을 구분하라. 반드시 네 개의 새 폴더를 만들어야 한다는 뜻은 아니다. 기존 구조에서 역할이 분명하면 그대로 사용하라.

한 규칙의 전문은 한 담당 문서에 두고 다른 문서는 실제 절로 링크하라. 문서를 합칠 때 고유 API 필드·조건·오류·복구·상태·원화 요소가 누락되지 않았는지 비교하라. 같은 문장을 반복하는 부분만 정리하고 필요한 상세를 ‘중복’이라는 이름으로 삭제하지 마라.

이동/개명이 필요하면 **기존 경로→최종 담당 경로, 이유, 보존 위치**를 기록하고 색인·상대 링크·앵커·프로젝트 지침의 경로를 함께 갱신하라. 실제 Unity asset의 .meta/GUID 또는 소스 참조 변경이 필요하면 별도 작업으로 분리하여 이 문서 작업에서 실행하지 마라.

원본과 사용자 작업 파일을 일괄 삭제하지 마라. 폐기된 정책은 현행 본문에서 제거/교체하되 필요한 출처·과거 검증 사실은 접근 가능한 이력으로 남겨라. 파일을 옮겼다는 이유로 모든 옛 문서가 무효가 되거나 최신 문서가 모든 상세를 대체한다고 보고하지 마라.

## 9. 실제로 수행할 문서·데이터 검사

변경 전후 대상 파일 목록과 해시 또는 diff를 기록하라. 바이트를 얻지 못한 추출본은 추출 텍스트 기준임을 표시하고 원본 바이트 동일성을 주장하지 마라.

파일 존재, 내부/상대 링크, 명시 앵커, 문서 번호/색인, 담당 원문 참조, 명칭/ID를 실제 파일에서 검사하라. 아직 원 ID를 확보하지 못한 경우 임의 ID를 넣지 말고 미확인으로 분리하라. 단순 문자열 일치와 실제 런타임 유효성도 구분하라.

JSON은 실제 구문과 명시 스키마/필드/참조를 확인하고 MD의 승인값과 비교하라. 데이터가 없거나 권한/스키마가 없어 검사하지 못하면 ‘미확인’으로 보고하라. 문서 링크가 살아 있다는 이유로 API 계약·밸런스·실기기 검증이 완료됐다고 하지 마라.

기존 문서의 상대 링크를 보존할 필요가 있으면 실제 앵커를 유지하거나 정확한 대응으로 갱신하라. 링크 오류를 숨기기 위한 빈 문서·가짜 앵커·무내용 placeholder를 만들지 마라.

이번 전달에 포함된 DOCUMENT_VALIDATION_20260921.md는 채팅 작업 컨테이너의 문서 검사 결과다. 사용자 저장소·사용자 보유 최신 사본에 대해 그대로 PASS로 재사용하지 말고 실제 프로젝트에서 새로 실행한 범위를 보고하라.

## 10. 요청하는 최종 결과물

실제 작업을 마친 뒤 다음을 제공하라. 프로젝트에 이미 같은 목적의 보고서/색인이 있으면 갱신하고 불필요한 날짜별 중복본을 늘리지 마라.

1. **실제 자료 목록:** 프로젝트 루트·문서 폴더·별도 MD/data 폴더, 파일별 경로·종류·용도·상태.
2. **경로 대응표:** 기존 파일→최종 담당 경로, 유지/이동/통합/이력 보존/보류 이유. 계획과 실제 실행을 구분.
3. **현행 담당 MD와 필요한 작성 데이터:** 최신 승인 반영과 상세 보존, 실제 변경 파일 목록. 데이터 미변경이면 그대로 명시.
4. **판단 근거:** 통합·교체·보존·보류한 내용, 원문/사용자 결정/코드 근거와 승인 범위.
5. **남은 사용자 판단:** 자료로 해결되지 않는 실제 충돌과 선택만 포함. 이미 결정한 사항 재질문 금지.
6. **기획/구현 차이와 후속 작업:** 실제 확인 경로·미연결 범위·검증 필요성을 분리.
7. **검사 결과:** 실행한 명령/검사·대상·결과·실패·미확인·제외 범위. 미실행 결과 창작 금지.
8. **프로젝트 지침의 진입점:** 실제 현행 문서 위치와 유지 규칙. 한 규칙 한 원문, 승인 순서, 이력 보존, 구현/검증 분리를 반영.

현재 기획 기준 정리 완료 여부와 전체 게임의 구현/출시 상태를 따로 결론 내라. 문서 링크 통과만으로 ‘프로젝트 완료’라고 보고하지 마라.

## 11. 이 전달본의 자료 한계

이번 문서 제작에서 원본 업로드00·16·17·19·20·21을 사용했고04·11·18은 라이브러리 전체 추출 텍스트로 확보했다. 원본 raw 바이트는 확보하지 못했다. 04·11은 추출 본문을 보존하고18은 개인 참조를 보완했다.

01·02·03·05·06·07·08·09·10·12는 링크/앵커 확인용 추출 텍스트를 확보했지만 실제 저장소와의 최신 일치는 검증하지 않았다. 13·14·15와 일부 JSON은 검색 메타데이터만 확인되고 본문 확보에 실패했다. JSON4종 전체·원문32개·과거validation·참고 영상·실제 자산·소스·API는 이번에 새로 전부 읽거나 검증한 것이 아니다.

이 누락은 현재 전달한 정책의 빈칸을 임의 생성하라는 뜻이 아니다. 실제 프로젝트에 자료가 있으면 읽어서 해결하고, 없으면 필요한 파일과 확인 목적을 명시하라. 이전 안내/인계문 원본은 확보하지 못해 사용자의 명시적 인계로 다시 정리했다. 이 안내를 과거 모든 원문을 검토했다는 증거로 사용하지 마라.

문서 정리 결과와 남은 실제 구현을 분리해 보고하라. 새 이미지·Unity 코드·서버/DB·스키마·배포를 이 지시의 후속으로 자동 실행하지 마라. 코드 변경·자산 제작이 필요한 경우 필요한 작업을 보고하는 데서 끝내라. 기존 검증과 원본을 보존하고, 실제 수행한 것만 완료로 표시하라.
