# LASTRAIL 게임 업데이트 운영 절차

작성: 2026-10-01. 상태: 운영 절차·리허설·상세 운영·정기 주기 사용자 승인(2026-10-01). 기존 승인 정책은 유지하고 아래 회차 기록/진행 게이트를 정리했다. 문서 작성은 배포·점검 전환·실권한 변경 승인이 아니다. 실제 업데이트 회차에는 대상과 실행 권한을 확인한다. 이 문서는 운영 순서의 진입점이며 원정책을 복제해 새 원본으로 만들지 않는다.

## 2. 업데이트 종류와 필요한 준비
| 변경 | 필요한 확인 | 점검/클라이언트 업데이트 판단 |
|---|---|---|
| 안내 문구/공지 | 공개 범위·기간·원문 개정 | 공지 게시만으로 점검하지 않음 |
| 밸런스/드랍 데이터 | 실제 지원 handler·데이터 schema·구START·공시 | 호환 확인 시 데이터 연결 변경. 미지원 효과 추가는 데이터 교체만으로 출시 불가 |
| 리소스/콘텐츠 | 승인 catalog/bundle hash·참조·다운로드·구캐시 | 기존 앱 호환과 핀 유지 확인. 진행 작전 중 새콘텐츠 강제 치환 금지 |
| 서버/API | 구/신 클라이언트·원거래/세션·현재DB 호환 | 무점검 가능 여부를 실제 검증으로 결정. 모든 배포에 점검 강제/무점검 보장 없음 |
| DB 변경 | 호환 migration·데이터 보존·쓰기 경합·복구 | 파괴적 변경 별도 승인. 적용 중 쓰기 제한 필요성을 정함 |
| 앱 바이너리 | 서명·설치코드·정확빌드 등록·실기기·다운로드 경로 | 실제 배포 가능 확인 후 지원 하한 결정. 스토어별 실행 규정은 해당 배포 때 확인 |

한 회차에 여러 유형이 포함되면 영향 합집합을 검증한다. 전체 소프트웨어를 무조건 재작성하거나 모든 기능을 점검으로 막지 않는다.

## 3. 회차 기록 — 기존 QA/릴리스 이력에 기입
- 회차 ID·목적·변경 범위·제외 범위, 책임자/실행자/승인 근거.
- 환경·서비스, 서버 source commit/deployment ID, DB migration 시작/목표, 실제 앱 설치코드/산출물 hash, 콘텐츠/밸런스/공시 ID·digest, 현재/목표 index revision.
- 영향받는 신규/진행 작전·재접속·정산·협동/월드·웹/어드민 범위.
- 변경 전 호환 조합, 변경 후 조합, 구앱 허용/차단 조건, 롤백 가능한 조합과 불가능한 단계.
- 필요한 점검 대상·예정 시각·미완료 작전 처리·연장 시 안내, 검증 항목/담당/결과 위치.
- 실제 시작/종료·각 단계 결과·잔여 문제. 비밀키/토큰/고객 원문은 넣지 않는다.

관련 없는 항목은 ‘해당 없음+근거’로 기록한다. 미확인을 해당 없음으로 바꾸지 않는다. 로컬 성공과 원격 성공, dry-run과 실배포를 구분한다.

## 4. 순서와 진행 게이트
1. **범위 고정:** 정확한 변경 파일/정의·호환 조합·영향·복구 경로를 준비한다. 코드/데이터 변경 시 관련 검증 근거를 갱신한다.
2. **DEV 검증:** 변경 단위 및 연관 회귀→실제 API→해당 실제 클라이언트/콘텐츠 조합 검증. 게임 진행에 영향을 주면 출발/진행/정산·중복/단절 복구를 포함한다. 전체 테스트 통과가 실연결 누락을 덮지 않는다.
3. **배포 준비 확인:** 실제 설치 가능한 앱, 검증된 자산과 원정의, 승인 공개자료, 서버/DB 호환 및 중단 시 복구 수단을 갖춘다. 원격 백업/복구 가능 여부는 실제 근거로 확인하며 백업을 이유로 모든 DB 되돌리기가 가능하다고 보지 않는다.
4. **해당 회차 실행 승인 확인:** 대상 환경·정확 후보·영향 범위에 대한 기존 사용자 승인이 있으면 재질문하지 않는다. 범위 밖 운영 승격/파괴적 작업은 분리한다. 초안 문서 승인을 실제 배포 허가로 확대하지 않는다.
5. **필요한 차단/안내:** 12에 따라 신규 출발 차단과 본점검을 구분한다. 차단 전 승인 작전의 선택/정산/원결과 복구를 단순 POST 일괄 차단으로 막지 않는다. 긴급 점검이면 안전 정지/원상태 보존을 우선한다. 예상 종료시각 도달만으로 자동 해제하지 않는다.
6. **적용:** 호환 schema 확장→구/신 데이터 읽기 서버→검증된 콘텐츠/앱 배포→실제 설치/접근 가능 확인→필요시 minimumVersion gate→비호환 동작 활성 순서. 해당 없는 단계는 근거와 함께 생략한다. 검증된 원본과 승인 revision을 사용하고 각 단계 실패 시 후속을 진행하지 않는다.
7. **적용 후 확인:** 실제 배포ID/스키마/포인터를 읽고 아래 필수 사례 확인. 새 코드 배포 성공과 현재 활성 데이터/공개 자료 성공을 따로 확인한다. 응답 유실 시 현재 원결과 확인 후 판단하며 무조건 재배포하지 않는다.
8. **서비스 재개:** 점검을 사용했다면 실제 gate/정상 진입·작전·정산 검증 후 해제한다. 웹·게임을 각각 확인하고 공지/상태 표시 갱신. 광고 스위치나 미승인 보상을 자동 활성화하지 않는다.
9. **회차 종료:** 불변 성공 이력과 현재 포인터, 알려진 잔여, 검사 범위/제외를 기록한다. 배포 성공 뒤 이력 기록만 실패했다면 ‘배포 성공·기록 복구 필요’로 남기고 같은 배포를 무작정 반복하지 않는다.

PASS/FAIL/BLOCKED/NOT_RUN과 실제 버전을 남긴다. 성능·오류율은 회차의 기존 기준과 비교하고 측정 없는 임의 허용률을 만들지 않는다. 완료 판수만으로 밸런스 확정을 선언하지 않는다.

## 6. 중단·롤백·긴급 수정
인증/진입 장애, 데이터 손상, 중복 지급/차감, 비공개 노출, 진행 작전 복구 실패가 관측되면 영향 범위의 추가 활성화를 멈추고 필요 gate를 적용한다. 원요청/버전·증거를 보존한다. 보상 지급으로 오류를 덮지 않는다.

- 데이터/공개 포인터: 검증된 같은 환경의 이전 호환 snapshot에 새 revision으로 연결. 과거 원본 덮어쓰기 없음.
- 서버 코드: 현재 DB·enum·원장·멱등·콘텐츠를 이전 코드가 읽을 수 있다는 근거가 있을 때만 롤백. 없으면 현재 schema를 보존한 전진 수정.
- DB: 기본은 forward migration/감사된 correction. 전체 백업 복원으로 이후 정상 거래를 날리는 동작을 일반 롤백으로 쓰지 않는다.
- 앱: 이미 설치된 바이너리를 원격으로 내릴 수 있다고 가정하지 않는다. 호환 서버 유지/수정 빌드 배포와 실제 admission 정책으로 대응한다. minimumVersion을 자동 하향하지 않는다.
- 긴급 수정도 원인·정확 변경·영향 검증·실결과를 남긴다. 사용자 보상·데이터 정정은 별도 권한과 원거래 근거로 처리한다.

## 7. 담당·현재 상태
Plan은 정책/공지 내용·기획 대조, Server는 DB/API/admission·배포 및 원결과, Unity는 실제 빌드/콘텐츠/플레이 호환, Admin은 기존 운영 명령/권한·상태, Homepage는 승인 공개자료 표시를 맡는다. 실제 회차 총괄/실행자 이름은 회차마다 지정하며 문서의 역할명이 실제 권한을 부여하지 않는다.

이 문서 §1~7의 회차 기록·게이트·담당 인수 절차는 2026-10-01 사용자 승인으로 확정했다. 신규 시간/보상/강제 업데이트 하한은 정하지 않았다. 현재 내부 테스트/전체 업데이트 리허설 완료를 주장하지 않는다. 실제 회차를 시작할 때 해당 기능의 실행 계약과 승인 범위를 확인해 기존 담당 큐로 진행한다.

## 8. DEV 업데이트 리허설 상세 v1 — 실행 전 검토안

§1~7은 사용자 ‘ㄱㄱ’으로 승인. 아래는 그 절차를 검증할 신규 사례 구성안이며 실제 배포/점검 실행 결과가 아니다. 첫 리허설은 게임 일반 솔로와 해당 업데이트의 실제 지원 범위에 한정한다. 협동/월드를 함께 변경하면 해당 모드 사례도 필수이며, 지원되지 않은 모드를 정상으로 간주하지 않는다.

### 준비 입력과 격리
실제 현재 조합 A와 업데이트 후보 B를 지정한다. A/B는 설명용 기호이며 실제 버전ID가 아니다. 앱 설치코드·서버 source/deployment·DB migration·콘텐츠/밸런스/공시·index revision 및 결과 경로를 회차 기록에 기입한다. 기존 DEV에서 시험 창과 영향 범위를 조율하고 격리 계정/데이터만 사용한다. 별도 STG나 실서비스 데이터를 복제하지 않는다.

A가 실제 실행 가능한지 먼저 확인한다. 신규 START·전투/거래·복구 지원이 미완료라면 해당 사례를 BLOCKED로 남기고 단위 fixture 결과로 통합 PASS를 만들지 않는다. 기존 전체테스트/실통신 증거는 동일 범위·버전일 때 재사용하고 변경 영향만 추가 검증한다.

### 순서별 실행 카드
| ID | 조건·행동 | 기대 결과·근거 | 담당 |

| UP-02 출발 경계 | 승인된 DRAINING 전후 동일 START 재시도와 새 START 비교 | 기존 원결과 재현, 차단 후 신규 run·비용 생성0, 기존 선택/정산 허용 | Server+Unity |

## 10. 업데이트 회차·예약·진행 작전·부분 실패 상세 v2 — 사용자 승인

2026-10-01 추가 상세 요청. §1~8 승인과02/08/12/36 원정책은 유지한다. 아래 회차 상태·예약 실행 방식·구작전 호환 판단·운영 화면·원자성 경계는 구현 인수용 신규 설계다. 실제 API/관리 화면 존재를 뜻하지 않는다. 기존 릴리스/점검/공지 기능을 연결하며 별도 배포 엔진이나 경쟁하는 진입 gate를 만들지 않는다.

### 10.1 회차 단위와 상태
업데이트 회차는 환경·앱·변경 대상·정확 후보 digest·호환 표·실행 단계·복구 방식·검수 결과·승인 근거를 참조한다. 코드 배포/DB/콘텐츠/점검은 각 기존 서비스가 원상태를 소유하고 회차는 참조와 실행 결과를 모은다. 같은 환경·앱의 충돌하는 현재 포인터를 바꾸는 실행은 한 회차만 허용한다. 무관한 문구 편집까지 전역 잠금하지 않는다.

| 회차 상태 | 진입 조건·허용 작업 | 다음 |
|---|---|---|
| DRAFT 작성 | 후보·대상·영향·복구 경로 작성 | 검증 요청→VALIDATING, 폐기→CANCELLED |
| VALIDATING 검증 | 정확 후보의 실제 결과 수집 | 필수 근거 충족→READY, 실패/변경→DRAFT |
| READY 실행 준비 | 후보 승인·호환·환경/권한·선행 충족 | 명시 예약→SCHEDULED, 즉시 실행→APPLYING, 수정→DRAFT |
| SCHEDULED 예약 | 예약 시각/시간대·점검/공지 연결 저장 | 시각 도래 후 재검증→APPLYING 또는 BLOCKED; 취소→CANCELLED |
| APPLYING 적용 | 단계별 원명령/배포ID·결과 저장 | 전체필수 적용→VERIFYING, 실패/결과미확인→BLOCKED |
| VERIFYING 적용 검증 | 실제 조합·진입/복구/현재 포인터 검수 | 필수통과 및 서비스 상태 확인→COMPLETED, 실패→BLOCKED |
| BLOCKED 보류 | 실패 단계·실제 적용분·미확정 요청 표시 | 원결과 확인·수정 후 해당 단계 재개, 명시 복구→RECOVERING |
| RECOVERING 복구 | 승인된 호환 되돌림/전진 수정 | 검증된 이전 서비스 복귀→ROLLED_BACK; 전진 수정 성공은 VERIFYING; 실패는BLOCKED |
| COMPLETED/ROLLED_BACK/CANCELLED | 불변 결과·이력 조회 | 변경 필요 시 새 회차 |

이 명칭은 논리 계약이다. 기존 release 상태와 매핑하며 같은 상태 테이블을 중복 소유하지 않는다. 배포 승인과 실제 서비스 활성 상태는 별개다. 초기 단계부터 미실행인 회차만 CANCELLED로 끝낼 수 있다. 한 단계라도 외부 변경됐으면 취소로 되돌아갔다고 표시하지 않고 복구/보류로 처리한다.

### 10.2 업데이트 방식 결정표
| 유형 | 선택 조건 | 기존 작전/플레이어 처리 |
|---|---|---|
| 무점검 호환 업데이트 | 구/신 앱·실행 서버·DB·원거래·구콘텐츠 조합 모두 지원; 실제 혼재 검증 | 기존 run 원핀 유지, 새 START만 새승인 정의. 검증되지 않은 호환을 가정하지 않음 |
| 신규 출발 차단 후 적용 | 기존 run은 구버전으로 완료 가능하나 새기능 전환에 경계가 필요 | DRAINING으로 신규 출발 차단, 원선택/정산/복구 유지 |
| 본점검 후 적용 | 혼재 처리 불가 또는 쓰기 중지 필요, 검증된 안전 정지/복원 가능 | 12의 안전 정지·checkpoint·미확정 원거래 보존. 웹/문의는 실제 영향 범위만 제한 |

기준 선택은 회차 승인에 포함한다. 단순 수치 변경도 handler/구판 원정산과 호환되지 않으면 무점검으로 분류하지 않는다. 운영 가능한 기존 작전을 임의 시간 경과만으로 패배/삭제하지 않는다. 점검 시작 시 남은 run 수·지원 여부를 확인하고 보존 가능하면 본점검, 불가능하면 정상 업데이트를 연기한다. 긴급 차단의 손실/미확인 건은 별도 복구 대상으로 유지한다.

### 10.3 예약·수정·취소
시각은 UTC 저장·Asia/Seoul 편집/표시, 날짜·시간대 포함. drain/시작/예상종료는 각각 별도이며 시작 전후 순서 검증을 한다. 무점검 회차에는 drain을 강제하지 않는다. 예약에 정확한 후보와 승인 revision을 결속한다.

예약 시각에는 새 승인 질문을 자동 생성하지 않고 이미 승인된 범위 안에서 환경·권한·잠금·원본 digest·현재 revision·검증 유효성을 다시 확인한다. 미충족이면 BLOCKED, 자동 우회/다른후보 선택0. 점검 자동 활성은 기존12의 예약 정책을 따르며 회차 보류만으로 이미 발효한 점검이 자동 해제됐다고 가정하지 않는다. 원상태를 조회하고 권한 있는 실행자가 조정한다.

후보·대상환경·적용버전·복구 방식·영향 범위 변경은 검증/승인 무효화 후 DRAFT로 반환. 일정 변경도 명시 승인·새revision·공지 수정이 필요하되 변경 없는 코드검사를 무조건 반복하지 않는다. 예상종료 연장은 실제점검 정책의 별도 명령/감사로 처리하며 새 배포 성공이나 자동 정상복귀를 의미하지 않는다. 실행 전 취소도 예약 점검/공지 상태를 각각 확인·정리하고 일부 실패를 기록한다.

### 10.4 필수 업데이트·구작전 호환
실제 배포 경로에서 설치 가능한 후보·정확 코드·서명/콘텐츠 호환을 확인하기 전 하한을 올리지 않는다. 스토어 버튼을 눌렀다는 사실은 설치 완료가 아니다. 복귀한 앱은 실제 설치코드·admission·콘텐츠를 다시 확인한다. 일부 기기/배포대상에 후보가 아직 제공되지 않으면 해당 범위를 지원 불가 상태로 몰지 말고 전환을 보류한다.

필수앱 업데이트가 예정된 회차는 반드시 다음 세 조합을 확인한다: (a) 구앱/구run, (b) 신앱/구run, (c) 신앱/신run. 신앱에서 구run의 checkpoint·효과·원정산을 복원할 수 없으면 하한 전환을 연기하거나 검증된 호환 계층을 먼저 제공한다. 하한 미달 앱의 예외 API를 즉석에서 만들거나 원run을 현재 버전으로 변환하지 않는다. 긴급 강제차단 시 복원 불가능한 run을 성공/폐기로 단정하지 않고 원기록과 복구 과제를 남긴다.

공지/공개 자료는 목표 적용범위·현재/이전 버전을 구분한다. 일반 데이터 패치는 신규 출발부터 적용된다는 점을 안내하고, 기존run 유지 예외를 실제정책과 다르게 표현하지 않는다.

### 10.5 단계별 명령·부분 실패
모든 변경 명령은 회차ID·단계ID·대상·불변 요청digest·원키·기대 revision·실행자·실제결과 참조를 갖는 의미 계약으로 인수한다. 권한은 서버에서 검사하고 관리 화면은 토큰/CLI 비밀값을 보유하거나 직접 DB를 쓰지 않는다. 실제 endpoint/필드명은 기존 서비스에 맞춘다.

외부 배포·DB migration·콘텐츠 발행·공개 index 변경은 전체가 하나의 DB transaction이 아니다. 각 단계의 적용 여부를 독립 기록하고 결과 미확인일 때 다음 단계로 넘어가지 않는다. 재시도는 동일 단계의 원결과부터 조회하며 이미 완료한 migration/배포를 새 키로 반복하지 않는다. DB 안의 상태 변경·원영수증·감사는 각 서비스의 원자 경계로 처리한다.

| 일부 결과 | 다음 처리 |
|---|---|
| DB 확장 성공/서버 배포 실패 | 기존 코드가 확장schema와 호환되면 유지하고 같은후보 재시도·호환복구. 무조건 schema 삭제 금지 |
| 서버 배포 성공/기록 저장 실패 | 실제 deploymentID 확인, 기록 복구. 배포실패라고 재배포하지 않음 |
| 콘텐츠 업로드 일부 성공 | 미완성 catalog 활성화 금지. 기존 포인터 유지, 업로드 완료/hash 확인 후 진행 |
| 코드 성공/밸런스 활성 실패 | 실제 현재 index와 코드의 호환 확인. 호환이면 이전 활성본 유지, 비호환이면 영향 gate/복구 |
| 공개공시 필수자료 연결 실패 | 그 자료가 필요한 신규 기능/정책 활성화 보류. 문구 공지 전체를 무조건 게임장애로 확대하지 않음 |
| 적용 후 검증 실패 | 영향 신규진입 제한 유지/필요시 차단, 호환 롤백 또는 전진 수정 명시 선택 |

장애가 지속된다는 이유로 minimumVersion 자동하향·DB전체복원·원보상 재지급을 하지 않는다. 자동 되돌림은 이번 초안에서 기본 사용하지 않고 회차에 지정된 호환 복구를 담당자가 실행한다.

### 10.6 기존 Admin 운영 화면 상세
기존 릴리스/점검 메뉴 안에 회차 요약과 관련 링크를 묶는다. 목록은 환경·회차·후보·실행상태·현재서비스 상태·최근 결과를 구분한다. 상세는 변경전/후 조합, 단계 진행/원결과, 남은 작전·미확정 거래의 집계 근거, 공지/공시/점검 링크, 검증/복구 가능성을 표시한다. 실제 집계가 없으면0이 아니라 미확인이다.

버튼은 상태별로 검증 요청/예약/즉시 실행/예약 취소/원결과 확인/재개/복구/검증 완료를 제공하되 실제 인수된 관리 명령만 활성화한다. 후보변경·환경·범위·원본revision을 확인하고 서버 재검증 결과로 상태를 갱신한다. 브라우저 종료는 배포 취소가 아니며 재진입 시 원회차를 읽는다. 권한 없는 조작·동시 변경은 거절하고 최신 상태를 보여준다. 문의 처리 grant를 배포권한으로 사용하지 않는다. 구체 역할별 release 권한은 기존 실제 계약 확인 후 인수하며 이 화면으로 새권한 자동부여하지 않는다.

### 10.7 사용자 안내·종료 판단
사전 안내에는 대상/작업 내용/신규출발 차단·점검 시작/예상종료/구작전 처리/필수업데이트 여부를 담는다. 점검 없는 업데이트에 점검 종료시각을 만들지 않는다. 시간 미정은 미정으로 표시하고 종료를 보장하지 않는다. 연장은 변경 시각·사유·현재 이용 가능 범위를 안내하며 구현 안 된 저장/복구를 약속하지 않는다.

완료 안내는 실제 활성 버전/적용 대상/재접속 또는 업데이트 필요 여부/알려진 잔여를 포함한다. 보상은 별도 승인·원거래 처리 전 자동 지급이나 지급예정을 약속하지 않는다. 정산결과 불명확 건은 담당과 원근거를 남겨 운영완료 기록에서 숨기지 않는다.

재개는 실제 gate·필수 smoke·오류/거래 무결성 확인 후 명시 실행한다. 오류율/관찰시간의 운영 고정값은 실제 기준선 없이 새로 정하지 않으며 회차별 지표·대상·관찰창·판정근거를 사전에 기록한다. 데이터 손상/중복경제/인증 우회가 확인된 범위는 관찰시간이 지났다는 이유로 정상화하지 않는다.

### 10.8 추가 수용 조건·승인 범위
기존 UP-01~10에 다음 변형을 연결한다: 예약 뒤 후보변경 차단, 예약시권한회수, 점검만발효/배포보류, 외부배포성공/기록실패, 구앱→신앱 구run복원, 후보 설치불가 하한상향 차단, 콘텐츠 일부업로드, 공시필수연결 실패, 두 운영자 활성revision 경합, 브라우저종료 후 원회차 복구. 새중복 시험목록 대신 원사례 하위로 추적한다.

## 11. 정기 업데이트 주기·작업량 기준 — 2026-10-01 / 사용자 승인
